# Brief: Assistant Practice Recommendation

Используй этот документ в новом чате, когда задача касается ИИ-ассистента, оркестратора, карточки рекомендованной практики, выбора практики backend-логикой или запуска практики из чата.

## Цель сценария

Пользователь нажимает кнопку обсуждения под рекомендациями дня. Ассистент ведет короткий живой диалог:

1. Понимает состояние и контекст дня.
2. Соединяет активную чакру дня с реальной ситуацией пользователя.
3. Помогает сформулировать инсайт.
4. Спрашивает тип практики и доступное время.
5. Предлагает конкретную практику.
6. Объясняет, почему именно эта практика сейчас уместна.
7. Показывает красивую карточку с кнопкой "Начать практику".

Тон: живое, человеческое, теплое общение без ощущения анкеты и без лекторских штампов.

## Уже есть в проекте

- API: `_legacy_web/app/api/communicator/v2/dialog/route.ts`.
- Фазы daily dialog: `contextual_greeting`, `collect_state`, `deepen_inquiry`, `offer_insight`, `ask_practice_intent`, `suggest_practice`, `confirm_and_close`.
- Оркестратор считает insight/TTM метрики и не должен слишком рано перескакивать к практике.
- Backend уже умеет выбрать практику через `choosePractice`, но пока фильтр грубый: по чакре дня и рейтингу.
- Responder использует маркер `[PRACTICE_PICK: id="..." reason="..."]`.
- Клиентский `Communicator` принимает `practicePicked`.
- `modules/communicator/ui/PracticeCard.tsx` уже отображает простую карточку.

## Главный продуктовый инвариант

Ассистент может объяснять и обрамлять выбор, но не должен выдумывать ID практик. Конкретная практика выбирается backend-логикой из каталога.

## Первый виток реализации

### Шаг 1. Проверить текущий end-to-end сценарий

В новом чате сначала попросить агента:

- запустить/проверить диалог до фазы `suggest_practice`;
- посмотреть, приходит ли SSE `complete.practicePicked`;
- проверить, появляется ли `PracticeCard`;
- зафиксировать, какие данные сейчас отсутствуют для запуска.

### Шаг 2. Расширить контракт `PracticePicked`

Минимальный контракт для первого витка:

```ts
interface PracticePicked {
  id: string;
  slug?: string;
  name?: string;
  kind?: "breath" | "meditation" | "yoga";
  reason?: string;
  durationSec?: number | null;
  minDurationSec?: number | null;
  maxDurationSec?: number | null;
  chakraIds?: number[];
  launch?: {
    route: string;
    params: Record<string, string>;
  };
  hasDescription?: boolean;
  hasInstructionVideo?: boolean;
}
```

Для дыхания `launch.route` должен вести на `/breath-coherence`.
Для медитации на первом витке можно вести на `/sacred-symbol-stream`.
Для асан пока допустим `/asana-practice?practiceId=...`.

### Шаг 3. Улучшить карточку рекомендации

Карточка должна быть легкой и красивой:

- eyebrow: "Практика на сейчас";
- название;
- тип и длительность;
- причина выбора;
- иконка/кнопка информации, если есть описание;
- иконка видео, если есть инструкция;
- кнопка "Начать практику".

На первом витке достаточно модального окна для описания и не обязательно делать видео-инструкции.

### Шаг 4. Запуск практики

В `onPracticePicked` или обработчике карточки:

- если есть `launch`, открыть route с params;
- если `kind=breath`, собрать fallback params: `practiceId`, `durationMs`, `chakra`;
- если `kind=meditation`, открыть Symbols;
- если `kind=yoga`, открыть экран асаны или заглушку.

### Шаг 5. Поведение после возражения пользователя

Если пользователь после карточки пишет "не хочу", "давай другую", "мне это не подходит":

- не начинать новый общий диалог;
- не возвращаться к долгому сбору контекста;
- удерживать фазу выбора практики;
- предложить альтернативу, желательно того же типа/чакры/длительности или мягко уточнить один недостающий параметр.

Технически это можно решить вторым витком через:

- `conversation.trigger_meta.last_practice_offer`;
- recent rejected practice ids;
- специальную ветку оркестратора, если последняя ассистентская реплика имела `practicePicked`.

На первом витке достаточно проверить, что диалог не ломается и карточка может появиться повторно.

## Алгоритм выбора практики

На первом витке:

- фильтр по чакре дня или выбранной чакре;
- фильтр по типу, если пользователь назвал тип;
- приблизительная длительность, если пользователь назвал время;
- сортировка по `rating desc`;
- fallback на первую доступную практику.

На втором витке:

- asana stack: исключать последние 15 выполненных асан;
- breath/meditation stack: размер равен количеству активных практик этого типа;
- длительность асан: допуск примерно 15%;
- внутри одинакового качества сначала более ранние `recorded_at`.

## Промпты и язык

Промпты должны поддерживать русский сейчас и быть переводимыми на английский позже. Не завязывать логику на русские слова в коде, кроме эвристик, которые явно отмечены как временные.

Особенно проверить фазу `phase_suggest_practice`:

- последнее текстовое сообщение должно объяснять ценность практики;
- затем идет карточка;
- текст не должен дублировать технические детали карточки;
- ассистент не должен давать длинную инструкцию по выполнению.

## Вопросы перед реализацией

- Как должен называться CTA: "Начать практику", "Начать сейчас", "Перейти к практике"?
- Нужна ли отдельная кнопка "Другая практика" прямо в карточке, или пользователь отвечает голосом/текстом?
- Должна ли карточка фиксироваться под последним сообщением или быть отдельным сообщением в истории?
- Нужно ли сохранять факт "практика предложена" отдельно от "практика начата"?

## Критерии приемки первого витка

- Диалог доходит до рекомендации.
- Карточка практики отображает название, причину и кнопку запуска.
- Кнопка запуска открывает соответствующий экран.
- Backend не выдумывает практики, а выбирает из каталога.
- После отказа пользователя можно получить новую рекомендацию в той же сессии.
