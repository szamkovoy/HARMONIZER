# Spiral Plan: Day 1-2

Цель этого документа: дать маршрут разработки на ближайшие 1-2 дня так, чтобы двигаться по спирали. На первом витке мы не доводим каждый модуль до идеала, а создаем работающие контракты, экраны-заготовки и точки интеграции. На следующих витках углубляем UX, алгоритмы и данные.

## Как пользоваться в новых чатах

В каждом новом чате прикладывай:

1. Этот файл, если нужно удерживать общий маршрут.
2. Один профильный brief из `docs/planning/`, соответствующий текущему пункту.
3. Скриншоты, ошибки, экспорт JSON или список Vimeo, если задача их требует.
4. Коротко напиши: "Мы на шаге X, нужно сделать Y, не трогать Z".

Если чат посвящен исправлению ошибки, прикладывай тот же профильный brief плюс описание ожидаемого поведения и фактического результата.

## Текущее состояние проекта

- Основной клиент: React Native Expo Router. Главный экран: `app/(tabs)/index.tsx`.
- Нижняя навигация технически есть как `Tabs`, но скрыта в `app/(tabs)/_layout.tsx`.
- Модуль Breath уже имеет каталог дыхательных практик и маршрут `app/breath-coherence.tsx` с параметрами `practiceId`, `durationMs`, `chakra`.
- Медитация "Symbols" сейчас живет как экспериментальный экран `app/sacred-symbol-stream.tsx`.
- В Supabase уже есть база для каталога практик: `practices`, `practice_chakras`, `practice_sessions`, `user_daily_stats`, `user_practice_preferences`.
- Communicator уже умеет вести потоковый диалог, сохранять `conversationId`, получать `practicePicked` и показывать `PracticeCard`.
- Текущая модель тарифов слишком грубая: `free/premium/trial`, а продуктовая сетка требует `free/oracle/practitioner/master`.

Vercel API проверен по `https://harmonizer-ten.vercel.app/api/ai/global-content`: deployment отвечает, GET возвращает `405`, то есть endpoint существует, но метод не GET.

## Первый виток спирали

### 1. Практики: единый каталог и контракты запуска

Документ: `docs/planning/practices_module_brief.md`

Что сделать на первом витке:

- Уточнить модель `practices` без тяжелого усложнения БД.
- Завести единый тип практики на клиенте: meditation, breath, asana/yoga.
- Описать поля для каталога, запуска, длительности, чакр, качества, Vimeo.
- Создать экран каталога практик с группами: "Медитации", "Дыхание", "Асаны".
- Подключить запуск дыхания через существующий `app/breath-coherence.tsx`.
- Подключить запуск медитации через существующий `app/sacred-symbol-stream.tsx`.
- Для асан на первом витке можно сделать экран-заглушку или карточку с Vimeo metadata, если импорт еще не готов.

Критерий готовности витка: пользователь видит каталог, может открыть доступные группы и запустить хотя бы медитацию и дыхательную практику из каталога.

### 2. ИИ-ассистент: рекомендация практики как продуктовый сценарий

Документ: `docs/planning/assistant_practice_recommendation_brief.md`

Что сделать на первом витке:

- Протестировать текущий диалог до фазы `suggest_practice`.
- Проверить, появляется ли `PracticeCard` в чате и содержит ли нужные данные.
- Расширить контракт `PracticePicked`: тип практики, duration, chakra, description/media flags, launch params.
- Сделать красивый, но простой блок рекомендации с кнопкой "Начать практику".
- Обеспечить запуск рекомендованной дыхательной практики/медитации.
- Зафиксировать поведение после отказа пользователя: не начинать новый "разговор о жизни", а держаться в контексте выбора практики.

Критерий готовности витка: ассистент доводит пользователя до рекомендации, карточка практики отображается, кнопка запуска открывает правильный экран.

### 3. Тарифы и feature gates

Документ: `docs/planning/access_tiers_navigation_brief.md`

Что сделать на первом витке:

- Ввести продуктовую модель тарифов: free, oracle, practitioner, master.
- Сделать единый механизм `canUseFeature(tier, feature)`.
- Добавить dev-переключатель всех тарифов.
- Поставить gates в ключевых местах: персональный прогноз, ассистент, каталог практик, асаны, вебинары.
- Не подключать оплату, но сделать так, чтобы UI вел себя как при реальных тарифах.

Критерий готовности витка: разработчик может переключить тариф и увидеть, как меняются доступные функции без переписывания экранов вручную.

### 4. Нижняя навигация и профиль

Документ: `docs/planning/access_tiers_navigation_brief.md`

Что сделать на первом витке:

- Включить нижнюю навигацию для тарифов, где она нужна.
- Минимальные вкладки: Home, Practices, Profile. Webinar/Community можно скрыть или показать только Master как заглушку.
- В Profile показать текущий тариф, dev-переключатель тарифа, базовую зону настроек.
- Не углубляться в оплату, Apple Health и сложную статистику на первом витке.

Критерий готовности витка: пользователь не теряется между главным экраном, каталогом и профилем; состав вкладок зависит от тарифа.

### 5. Vimeo import и асаны

Документ: `docs/planning/vimeo_asanas_import_brief.md`

Что сделать на первом витке:

- Согласовать формат списка, который будет выгружен из Vimeo-инструмента.
- Подготовить импорт в `practices` + `practice_chakras`.
- Учесть несколько чакр на одну практику.
- Качество и дата записи должны быть nullable.
- Пока не делать сложный Vimeo player, если нет подтвержденного UX. Достаточно сохранить metadata и определить, какой экран будет запускать практику.

Критерий готовности витка: есть понятный формат импорта и можно безопасно наполнить каталог асан.

## Второй виток

- Ранжирование практик: фильтр по типу, чакре, длительности, quality, recorded_at, recent stack.
- Сохранение завершенных практик в `practice_sessions`.
- Простейшая статистика: минуты практик по дням из `user_daily_stats`.
- Улучшение промптов оркестратора: естественный переход от инсайта к действию и новая практика после отказа.
- Информационные и видео-инструкции в карточке практики.

## Третий виток

- Полноценный Vimeo player/asana screen.
- Фидбек после практики: лучше/так же/хуже.
- Биометрия в `metrics` для Breath и, возможно, Meditation.
- Отчеты по типам практик, чакрам, регулярности и Apple Health overlay.
- Реальная оплата и subscription sync.

## Важные принципы

- Не усложнять БД раньше, чем понятно, какие отчеты реально нужны пользователю.
- Для данных практики оставить расширяемые поля `params`, `metrics`, `context`, но основные фильтры держать структурно: kind, duration, chakra, quality/rating, video_external_id.
- Все проверки доступа должны идти через один слой feature gates.
- Ассистент не должен выдумывать ID практик. Он может объяснять выбор, но конкретную практику выбирает backend.
- Русский UX делаем сейчас; английскую версию поддерживаем через локализуемые поля и промпты, а не через дублирование логики.
