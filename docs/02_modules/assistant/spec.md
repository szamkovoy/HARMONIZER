## 1. Назначение

Серверный слой **LLM-ассистента**: монологи (один запрос Gemini → JSON или текст) и **диалог дня на явном конечном автомате (FSM)**. С июня 2026 переусложнённый «мозг» (мега-промпт `dialog_system_v3` v7 + эвристический оркестратор `decideTurnMode` + история-инференс + двухмодельная эскалация по `[READY_FOR_RECOMMENDATION]` + отложенная reconcile-очередь) **заменён** на детерминированный автомат: сервер хранит, в какой ветке диалога он находится, и на каждый ход запускает **ОДНУ** ветку с **ОДНИМ** коротким промптом, парсит **ОДИН** тип маркера и переходит дальше детерминированно. Старый «мозг» удалён из активного кода (восстановим из git-истории; дословные v7-промпты — в `docs/05_archive/migrated/assistant/dialog_v7_prompts-reference.md`).

Три последовательные ветки: **summarizing** (подытоживание прошедших событий по одному), **planning** (сбор действий дня + общий фокус), **practice** (одна поддерживающая практика или отказ). Состояние автомата лежит в `conversations.trigger_meta.dialog_fsm` (`flow`, `branchIndex`, `branch`, `summaryAsked`, `planningFinalized`, `practiceDecided`, `noPractice`, `noGreeting`, `targetChakra`, `workingLocalDate`). Диалог держит **тексты беседы на клиенте**, а на сервере сохраняет действия в одной таблице `planned_events` (со статусами `planned` / `summarized`), дневные агрегаты в `daily_matrices`, кэш отчётов в `profile_report_snapshots`, минимальные `conversation_summaries` и `user_daily_forecasts.day_target_*` на локальный день. Клиентский UI чата и транспорт SSE — модуль `communicator`; астроданные — `astro` / `daily_forecast`; усреднение калибровки по голосу — `calibration`.

## 2. Публичный контракт

Набор **HTTP API** на Vercel (`_legacy_web`), авторизация Bearer JWT Supabase.

### Монологи

- `**POST /api/ai/monologue`** (`_legacy_web/app/api/ai/monologue/route.ts`)
  - Тело: `{ scenario_id: string; variables?: Record<string, unknown> }`.
  - Резолвит строку `**scenarios**` по `scenario_id`, берёт активный промпт по `monologue_prompt_key`, подставляет переменные, вызывает Gemini JSON (`generateGeminiJson`).
  - Кеш: таблица `**scenario_cache**`, стратегия из сценария (`per_user_per_day`, `per_user_per_calibration`, `no_cache`). Утренний сценарий инвалидируется при смене модели или отсутствии `modelUsed` в кэше (`isStaleMorningCache`).
  - Специальные сценарии в коде:
    - `**morning_recommendation**` — собирает переменные из последнего `user_daily_forecasts`, натала, калибровки, пользователя; строит топ-3 планеты (`buildTopPetals`), `**math_level**` (`buildMathLevel`), голос автора, подсказку обращения (`address_form` → hint).
    - `**psychological_portrait**` — добавляет `portrait_target_chars` из `CONTENT_LENGTHS`.

Клиент: `**callMonologue(scenarioId, variables)**` в `services/aiClient.ts` → тот же endpoint.

### Диалог дня — явный автомат (актуальная архитектура)

URL и SSE-контракт не изменились (клиент не трогали). Изменился **только «мозг»**.

- **Один ход — одна ветка — один промпт — один маркер.** `POST /dialog` грузит контекст дня (`loadDialogDailyContext`), читает/инициализирует FSM (`dialogFsm.ts`), строит **один** короткий промпт текущей ветки (`dialogBranchPrompts.ts`), делает **один** вызов `streamGeminiText` (всегда **standard**-tier `DIALOG_MODEL_TIER` → `AI_MODEL_STANDARD`, на КАЖДОМ ходе и для opening из `greeting/route.ts`, независимо от подписки — единообразие держит prefix-cache DeepSeek v4 тёплым; главная-страница `recommendation-text`/`monologue`/`morningRecommendation` сохраняют свой tier), без двухмодельной эскалации), парсит маркеры и детерминированно переходит дальше. Старые `decideTurnMode`, `[READY_FOR_RECOMMENDATION]`-эскалация и отложенная reconcile-очередь **не используются**; `inferPlannedEventsFromUserHistory(...)` теперь служит узкому planning-backstop'у: route собирает канонический список действий из **всей planning-ветки текущей беседы** (client `turnHistory` + текущая реплика), а не только из последнего user-turn и не как самостоятельный history-driven «мозг».
- **Инициализация FSM** (`initFsmState`) по точкам входа: `dayTabMode='add'` → `flow=['planning']` (без приветствия, без practice); `dayTabMode='plan'` → обычный day-start/home-flow `flow=[summarizing?, 'planning', 'practice']`; `daySummaryRequested` → `flow=['summarizing']` (закрытие после резюме). В home/day-start summarizing включается только если есть **незавершённые `planned_events` предыдущего локального дня**, а не просто любые `expected_at <= now`; текущий день не должен самопроизвольно открываться в summary из-за времени суток. Верхняя overdue-кнопка `Подытожить` на вкладке `День` теперь отправляет `dayTabMode='plan'` и `daySummaryRequested=false`, поэтому после закрытия хвоста прошлых действий диалог продолжает planning и practice как Home `Что делать?`; нижняя CTA `Подытожить этот день` остаётся `daySummaryRequested=true` и summary-only. Для `daySummaryRequested` backend грузит **все** неподытоженные rows с `planned_local_date <= workingLocalDate`, так что current-day summary не цепляет будущий planning-flow. `targetChakra` берётся из `user_daily_forecasts.day_target_chakra` и держится весь локальный день. Состояние пишется в `conversations.trigger_meta.dialog_fsm` (`writeFsmState`).
- **Время суток в промпте** (`dialogTimeOfDay.ts`, `sharedPreamble` всех веток — planning, summarizing, practice): приветствия — ночь 22:00–03:00 («Доброй ночи»), утро 03:00–10:00, день 10:00–17:00, вечер 17:00–22:00. После полуночи до 03:00 запрещена только **контекстная** риторика («уже вечер», «самое время оглядеться»), не само приветствие. `phaseTimeFor` для meta: 01:00 → `morning`, не `evening`.
- **Тональный регистр** (`dialogTonalRegisters.ts` → `tonalRegisterInstruction` в `sharedPreamble`): полный текст по планете дня + правило держать окрас во всех ветках без явного названия (как в архивном `dialog_system_v3`).
- **Summarizing FSM guards** (`dialogTurnGuards.ts`): thin-ответ или inconsistent model-output вида «видимый уточняющий вопрос + `[SUMMARIZE_EVENT]`» → отложить преждевременный маркер, пометить уточнение заданным и подставить один из доменно-зависимых детерминированных вопросов (`buildSummaryClarifyingQuestion`: work/rest/social/creative/tiny/generic); вопросы и bridges не цитируют названия действий в кавычках, а вплетают их разговорно. После исчерпания уточнения — закрытие без `outcome_cells`; несостоявшееся действие (`userSaysEventDidNotHappen`: голое «нет/no/не» ИЛИ выверенный набор формулировок — негированные occurrence/action-глаголы «не пошёл/не почитал/не успел/не получилось», идиомы «не до того / не было времени / не хватило сил», skip/cancel/forget «пропустил/перенесли/забыл», EN-эквиваленты; намеренно без одиночного «не было», чтобы не ловить «ничего особенного **не было**» у состоявшегося события) закрывается сразу, **независимо от числа заданных уточнений** — без матрицы (`outcome_cells=""`) и с коротким deterministic bridge к следующему событию. Если пользователь сигналит «ничего особенного / обычные ритуалы», промпт просит не допытываться о состояниях. Summary marker принимается только по точному `ref = current planned_event.id`; если модель перескочила к следующему событию без закрытия текущего, guard удерживает текущее событие открытым и возвращает уточнение вместо молчаливого auto-close. Ходы summarizing, где guard ещё может заменить model-output уточнением, буферизуют SSE `chunk` до server-side решения, чтобы пользователь не видел сначала финальный текст, а затем подмену на вопрос. Practice-like `PLANNED_EVENT` фильтруется до persist.


- **PLANNING** (`buildPlanningPrompt`): собираем только действия (без времени, без «в каком состоянии», без техдеталей), сохраняем порядок упоминания и не добираем лишние детали про первую/вторую половину дня. Сегментация `[PLANNED_EVENT]`: два независимых действия в одной фразе — два события; цель вместе со средством — одно; совместный повод (встретиться с кем-то, чтобы сделать что-то вместе) — одно событие; при сомнении склоняться к одному. На этапе сбора (WHILE GATHERING) можно мягко пригласить добавить ещё, но не более ~дважды за всё планирование, затем тепло предложить собрать план — без бесконечного чек-листа мелких дел. Ветка planning всегда относится к **текущему локальному дню из day-context**, поэтому prompt жёстко держит формулировку `сегодня`, а не `завтра`, если пользователь сам не просит планировать завтра. Промпт включает блок `LIFE SPHERES` (`ctx.lifeSpheresBaseline`) + domain-карту сфер (дом/порядок/уборка/сон/тело→1; отдых/прогулка/природа/велосипед/еда→2; работа/деньги→3; люди/отношения→4; творчество→5; обучение→6; вера→7) и явный анти-копи: пример `spheres` — формат-only (`<sphere>:<weight>`), числа не копировать, sphere 4 НИКОГДА не дефолт (раньше Flash тиражировал seed `1:0.6;4:0.4` → ложная 4-я сфера в «Дне»). Add-flow opening: `existingActionCount` считается из `triggerMeta.dayActions` (видимый список вкладки «День» через `countDayTabActionsFromTriggerMeta`), а не из overdue `dueEvents`. При `existingActionCount>0` первое сообщение **детерминированно** отдаётся из layer-C `planningAddOpening` (`planningAddOpeningText`) без LLM — одно короткое «что ещё добавить?» на locale ответа; промпт остаётся fallback для редких случаев без dayActions. Add-flow больше **не** hard-finalize-ится на первом названном действии: после первого добавления он остаётся в gathering-цикле, может один-два раза мягко спросить, не хочется ли добавить ещё, и закрывается только по явному сигналу пользователя (`userSignalsPlanningDone`: standalone done-фразы с Unicode word boundaries — «все» внутри «все-таки хочу…» не считается done; плюс «всё/хватит/nothing else») или по настоящему видимому финалу модели. Если модель забыла невидимые маркеры, salvage `extractPlanningMarkersFromVisibleFinalize` парсит numbered list по locale-native `recommendationLabel` из dialog scaffold (все 8 `AppContentLocale`, label trim + regex-escape), допуская нумерацию `1.`/`1)`, опциональный пробел перед двоеточием (типографика FR), markdown-bold/буллеты вокруг подписи; режет `desc` по границе слова (`clampPlanningDesc`, ≤60, без обрезки посреди слова) и инферит сферы из текста (`inferPlanningSpheresFromText`, fallback sphere 1, не sphere 4). Текст рекомендации к действию капитализируется (`polishPlanningRecommendation`→`capitalizeFirstLetter`). Финал — когда пользователь закончил: по каждому действию `[PLANNED_EVENT: desc(≤40, без «…») recommendation display_order spheres]` + общий `[CORRECT_RECOMMENDATION: short_text]`. Общая рекомендация на день — приглашение направить внимание (не «прогноз энергии»). Если сервер распарсил planning-маркеры, visible-final собирается детерминированно из подтверждённых артефактов: intro/`short_text` сверху, затем список действий с рекомендациями, затем широкий вопрос о практике (медитация/дыхание/асаны, примерная длительность или отказ). В add-flow (`noGreeting`) финал собирает только `buildPlanningAddFinalVisibleText` по marker-backed actions (детерминированный счётчик, без доверия free intro модели). Отказ пользователя планировать сейчас (`userDeclinesPlanning`) → `buildPlanningDeclinedReply`, `shouldClose`, ветка practice не запускается. `extractPlanningIntro` отбрасывает intro с неверным числом действий (`introHasWrongActionCount`). Вступительные “есть ли ещё что-то добавить?”-вопросы модели отбрасываются из deterministic-final: после сохранения planning-маркеров финал не должен звать пользователя добавлять новые действия. На потенциальных planning-final ходах сервер буферизует SSE до разбора маркеров, чтобы пользователь не видел raw LLM-текст с последующей заменой на deterministic-final. Visible planning-final обязан явно назвать **каждое** действие и его рекомендацию; рекомендации нормализуются в вежливые предложения с пунктуацией до записи в `planned_events`. Рекомендации соразмерны масштабу действия (длительная активность → фоновая настройка на процесс; короткое одноразовое действие → один точный маленький сдвиг), должны быть логически выполнимы в рамках самого действия и мягко выводить пользователя из привычного шаблона к тону чакры дня. Общий абзац дня дополнительно получает безымянную «глубинную оптику» по чакре дня (`chakraExpertLens` в `dialogBranchPrompts.ts`): мыслители, связанные с целевой чакрой, формируют мировосприятие финала, но НЕ называются и не цитируются; тональный регистр по планете дня (`dialogTonalRegisters.ts`) при этом не меняется. **Практики (медитация/дыхание/асаны) никогда не попадают в `[PLANNED_EVENT]`** — server-side `dialogTurnGuards.ts` фильтрует practice-like `desc` перед `persistPlanningFinalize`. Общий день-рекомендация полностью пишется LLM: модель сама называет чакру дня **числом**, но как ЖИВОЕ приглашение использовать энергию дня («Сегодня стоит направить внимание на седьмую чакру…» / «Сегодня сильнее обычного звучит седьмая чакра, и это шанс…»), а не плоский ярлык «Сегодня седьмая чакра — день, когда…», и несёт мотивационно-эмоциональный посыл (каждый день — уникальная, неповторимая возможность меняться и расти; почему это важно именно сегодня и что человек получает). ОДИН компактный абзац (~150–230 симв.). Видимый planning-final intro и сохранённый `short_text` вкладки «День» — это **один и тот же текст**: `extractPlanningIntro` дословно предпочитает `short_text` (канонический день-рекомендация), если он ≥80 симв., иначе извлекает intro из visible-текста. `prependChakraAttention` — ТОЛЬКО safety-net: добавляет «Внимание на N чакру.» лишь если модель вообще не упомянула чакру (guard ищет `чакр|chakra` в любом месте текста). После planning-final (`planningFinalized=true`) повторные ходы не персистят planning-маркеры и не перегенерируют wrap-up: ответ на вопрос о практике детерминированно переводит FSM в ветку `practice` (`coerceFsmBeforeTurn`). **Важно:** `coerceFsmBeforeTurn` блокирует planning и уводит в practice **только** после реального planning-final (`planningFinalized` либо visible numbered-wrap-up с practice-offer, `assistantFinalizeWithoutMarkers`); он НЕ опирается на loose `assistantOfferedPractice(lastAssistant)`, иначе финал summarizing (упоминает прошлые практики и заканчивается вопросом) + первое planning-сообщение пользователя с инцидентным «потом»/«позже» ложно скипнули бы всю ветку planning и не сохранили бы ни одного действия. Если модель забыла маркеры на ходе «достаточно», `extractPlanningMarkersFromVisibleFinalize` salvage-ит numbered list из visible-текста, а `extractDayFocusFromVisibleFinalize` salvage-ит сам день-фокус (самый длинный подходящий абзац перед нумерованным списком), когда `[CORRECT_RECOMMENDATION]` не эмитнут, чтобы Day-tab header всё равно обновился (**два прохода:** на `finalizeIntent` — из сырого visible; **post-assembly backstop** в greeted-flow (`!noGreeting`) после `buildPlanningFinalVisibleText`, если `recommendationCorrected` ещё пуст — повторный salvage из собранного `cleanText` с числом practice-filtered маркеров, `persistDayFocus` и пересборка visible). Подписи рекомендаций к действиям в deterministic-final (`buildPlanningActionsVisibleBlock`) — locale-native `recommendationLabel` из dialog scaffold (напр. FR «Recommandation:», не EN «Recommendation:»). После merge/polish тот же `resolvedPlanningMarkers` — единый источник и для persist, и для `planningMarkersForVisible` на finalize-turn (без повторного filter/map). **Накопительная planning-персистенция:** route больше не рассматривает последнюю user-реплику как единственный fallback-источник. На каждом planning-ходе он собирает канонический список действий из **всей planning-ветки текущей беседы**: client `turnHistory` несёт assistant `branches`, `collectPlanningBranchUserHistory()` выделяет именно planning-user turns, `inferPlannedEventsFromUserHistory(...)` детерминированно восстанавливает действия из этого накопленного корпуса, а `inferPlanningSpheresFromText()` заполняет sphere-only `cells`, если модель их не дала. Затем этот накопленный список мержится с явными `[PLANNED_EVENT]` и, при необходимости, с видимым numbered finalize (`mergeHistoryPlanningMarkers()` / `mergePlanningMarkersWithVisibleFinalize()` backfill-ит `recommendation_text`; при расхождении planning-inference locale и `responseLocale` оба merge вызываются с `{ preferCurrentByDisplayOrder: true }`, чтобы target-locale salvaged markers заменяли history-derived items по `display_order`, а не дублировались через fuzzy `samePlannedEventIdentity`). `persistPlanningFinalize` на каждом ходе upsert-ит **канонический список всей ветки**, а не только текущий turn: для обычного planning `appendToExisting=false`, чтобы эта беседа переписывала свой собственный план целиком; для `dayTabMode='add'` остаётся `appendToExisting=true`, чтобы новые действия шли хвостом после уже существующего дневного списка. Удаление осиротевших `planned`-строк больше не завязано на marker-backed финал: authoritative source — накопленный user-history этой planning-ветки, поэтому stale rows **этой же беседы** можно безопасно убирать и на промежуточных ходах; add-flow по-прежнему не удаляет чужие rows дня. Если текущий assistant-turn уже успел эмитить только лёгкие `[PLANNED_EVENT]` без `recommendation`, `mergePlanningMarkersWithVisibleFinalize()` backfill-ит недостающие рекомендации из salvaged visible numbered list перед `persistPlanningFinalize`, чтобы `planned_events.recommendation_text` не оставался `null`. Когда явных planning-markers на финале нет, после persist route дочитывает rows этого `conversation_id` за текущий день и строит deterministic visible-final уже по реально сохранённому набору действий, а не по потенциально урезанному free-text wrap-up модели. Флаг `planningFinalizedThisTurn` гейтит детерминированную сборку visible-final, чтобы накопительные промежуточные сохранения не превращали короткий ack в преждевременный финал. `persistPlanningFinalize` синхронно пишет `planned_events` **всегда на текущий локальный день (`context.localDate`)**, а не на summary `workingLocalDate`: в overdue `Подытожить`→plan-цепочке turn-level `workingLocalDate` ещё равен подытоженному прошлому дню, и без этого новые дела дня записались бы на вчера (исчезали из current-day секции и снова всплывали как overdue). Дедуплицирует и уже существующие rows (`samePlannedEventIdentity`), и повторы маркеров в одном assistant-turn, сохраняет `display_order` по порядку упоминания и sphere-only `cells`; `persistDayFocus` пишет `user_daily_forecasts.recommendation_short_text` (с `prependChakraAttention` как safety-net). Затем FSM → `practice` (или `done` для day `add`). В add-режиме приветствия и общего фокуса нет, `[CORRECT_RECOMMENDATION]` запрещён, practice не предлагается. **Отмена действия через диалог (light, не афишируется в UI):** при явной просьбе пользователя убрать/отменить запланированное действие («отмени перекус», «cancel the bike ride») модель эмитит невидимый `[CANCEL_EVENT: ref="<слова пользователя>"]` (одна на действие) и тепло подтверждает; сервер в начале planning-ветки (и в add-flow, и в обычном планировании) вызывает `dismissPlannedEvents` — fuzzy-сопоставляет ref с ОТКРЫТЫМИ (`status='planned'`) событиями дня через `samePlannedEventIdentity` и ставит `status='dismissed'` (подытоженные события не трогаются; `/api/day` читает только `planned`/`summarized`, поэтому отменённое сразу исчезает из «Дня»). Эти `dismissed` rows дополнительно исключаются из history-derived канонического списка, чтобы накопительный fallback не "воскрешал" снятое действие на следующем planning-ходе. Маркер вырезается из видимого текста; отменённые id попадают в `planningPersistence.cancelled` и учитываются в `persistenceConfirmed`.

- **PRACTICE** (`buildPracticePrompt`): это отдельная ветка только про практику, без пересказа дня и без подмены типа практики. Модель либо коротко уточняет `kind + duration` одним вопросом (или `buildCatalogReconciliationInstruction` при конфликте типа и длительности: медитация 1–5 мин, дыхание 5–20 мин, асаны 20–70 мин), либо сразу завершает ветку маркером `[PRACTICE_PICK: id="" reason duration_min chakra card_blurb]`; карточку резолвит `resolvePracticeCard` (порт `resolvePracticePublic`, тот же `choosePractice`, верный `kind`, чакра дня, редактируемая длительность для дыхания/медитации). На confident pick-turn и на отказных practice-ходах сервер буферизует SSE до резолва/очистки. Visible pick-turn берёт `practice_picked.reason` — мотивационный мост “зачем выполнить практику сейчас”; карточка получает отдельный `practice_picked.card_blurb` с описанием самой практики. Fallback-строки избегают падежных подстановок чакр (`зона шестой чакры`, не `зона шестая чакра`). При отказе — `[PRACTICE_DECLINED]`, `turnMode=final_without_practice`, `shouldClose` (UI показывает кнопку «Выйти»), служебный sentinel не должен появляться в стриме. Отказ распознаётся также детерминированно в `route.ts` (`userDeclinesPractice`): без JS `\b` (не работает с кириллицей), фразы «ничего не надо/нужно», bare-«нет» только если реплика не запрашивает практику (тип/длительность/«минут»). Если practice-ход не дал ни карточки, ни visible-текста (например catalog-inconsistent «дыхание 30 мин»), сервер подставляет детерминированный `buildPracticeClarificationFallback` вместо пустого ответа. После карточки практики или `branch=done` последующие сообщения получают короткий wind-down без LLM (`buildPostDialogReply`); FSM не реинициализируется в новый planning. Клиент блокирует ввод при `shouldClose` (`dialogWindDown`).

- **SUMMARIZING** (`buildSummarizingPrompt`): строго по одному событию за ход. В видимом тексте **запрещены** календарные даты и относительные слова «вчера»/«сегодня»/«завтра» (и en-аналоги); события называются разговорно, без кавычек вокруг заголовков. До `[SUMMARIZE_EVENT]` в одном сообщении — только текущее событие; уточняющий ход — один вопрос без перехода к следующему, с понятным контекстом «какие состояния были прожиты» вместо выбора «правильного» момента; после закрытия нефинального события — короткий мост + один вопрос о следующем, без интерпретаций. **ONE-OR-THE-OTHER per turn (CRITICAL):** ход — это ЛИБО один уточняющий вопрос о текущем событии (без маркера, без упоминания следующего), ЛИБО закрытие маркером + bridge к следующему — никогда оба сразу (иначе ответ пользователя смешивается между двумя событиями). **DEFAULT TO CLOSING:** если в ответе уже читается любое прожитое состояние — закрывать; уточнение — исключение для совсем «тонких» ответов; не расщеплять близкие состояния/чакры. Bridge — короткая связка («Понятно.») без пересказа/оценки/эха закрытого события. Запрос формулировать «как говорят носители» («удалось ли почитать книгу», не «устроить чтение книги»); инструкция естественности языка в преамбуле языко-независима (`languageName`). Финальный ход summarizing получает `maxOutputTokens=4500`, промежуточные — `900`. Если клиент ошибочно передал `workingLocalDate` = сегодня при пустом `dueEvents`, POST перезагружает overdue-rows через `loadDuePlannedEvents` и выравнивает `workingLocalDate` по фактической дате хвоста. Курсор детерминирован статусом в БД — текущее событие = первый `planned_events.status='planned'` рабочего окна summary: в home-flow это **последний незавершённый локальный день до сегодняшнего**, а в `daySummaryRequested` — весь хвост `planned_local_date <= workingLocalDate` по возрастанию даты и затем `display_order`. `summaryAsked[eventId]` ограничивает уточняющий вопрос одним; факт «состоялось / не состоялось» определяют **LLM по смыслу** (промпт требует — если действие не сделано, не задавать уточняющих вопросов о состояниях, тёпло посочувствовать одной фразой и закрыть маркером `[SUMMARIZE_EVENT … outcome_cells=""]`; если пользователь сигналит «ничего особенного / обычные ритуалы / как всегда», не допытываться о состояниях) **и** детерминированный backstop `userSaysEventDidNotHappen` (голое «нет/no/не» ИЛИ выверенный набор формулировок несостоявшегося действия — негированные occurrence/action-глаголы, идиомы «не до того / не было времени / не хватило сил», skip/cancel/forget, EN-эквиваленты; намеренно без одиночного «не было», чтобы не ловить «ничего особенного **не было**» у состоявшегося события): при срабатывании backstop событие закрывается сразу, **независимо от числа заданных уточнений** — без матрицы и с bridge к следующему. Если после единственного уточнения lived-state всё ещё не собран, сервер тоже закрывает событие без `outcome_cells`. Уточняющий вопрос **не пересказывает** реплику пользователя (запрет «Рабочие дела — это когда…/Вы сказали, что…»): он двигает мысль вперёд — одним коротким клаузом поясняет, что детали помогают зафиксировать состояния, и сразу спрашивает про состояния с 2-3 конкретными опциями под это действие. Если день новый и за summarizing последует planning (`continuesToPlanning`), opening одним предложением обозначает, что это взгляд назад на запланированное ранее, без календарных дат и «вчера/сегодня». Решение о финале принимается по **остатку событий после закрытия текущего**, поэтому ветка не должна оставаться в `summarizing` без `currentEvent` и уходить в абстрактные follow-up вопросы. Если `daySummaryRequested` пришёл, но `dueEvents` уже пусты, backend не строит новое summary-opening без события, а сразу завершает ход коротким terminal-ответом, что неподытоженных действий не осталось. Prompt дополнительно требует выбирать `outcome_cells` по **буквальному домену события и явно названному состоянию**, а не по далёкой символической ассоциации: `sphere/chakra 7` допустимы только при прямом религиозном/духовном/смысловом контексте; переговоры и попытка понять другую сторону должны сначала рассматриваться как `sphere 3` с chakra `3/5/6`, а прогулка/сон/отдых/свежий воздух/природа — как `sphere 1/2` с chakra `1/2`, если пользователь явно не описал обучение/инсайт или духовную практику. Каждое закрытое событие → `[SUMMARIZE_EVENT: ref outcome outcome_cells]`, `persistSummarizedEvent` ставит этому же действию `status='summarized'`, записывает `summarized_at` / `outcome_text` / `outcome_cells` и, если есть `outcome_cells`, мержит вклад в `daily_matrices` с последующей пересборкой `profile_report_snapshots`. Для прошлых локальных дней row удаляется сразу после успешной персистенции/merge, чтобы не всплывать в `planned_events`; current-day summary остаётся видимым до конца дня как `summarized` и серый item. Финал-резюме (последнее событие) даёт одну цельную психологическую рефлексию по целевой чакре (`chakraExpertLens`, variant `summarizing`) + наблюдения из Health/йоги строго по переданным данным; labeled per-event recap («Пo событиям»/«By events») запрещён — server `stripSummaryEventsBlock` удаляет такой блок, если модель его написала. Финальный summary post-sanitize-ится: ведущие разделители (`——`) удаляются, day-words (`сегодня/вчера/позавчера`, `today/yesterday/the day before yesterday` и производные) вырезаются через Unicode look-arounds (не JS `\b`), затем `capitalizeParagraphStarts` восстанавливает начало абзацев. Health-provider коды вроде `short` нормализуются в русские смысловые подсказки до промпта и не цитируются. Если в контексте есть практики или health-метрики, visible reply должен назвать **конкретные** практики/минуты/числа, а не ограничиться общим wellness-абзацем; при нуле практик — одно мягкое приглашение к практикам йоги/медитации приложения. В полном home-flow, когда за summarizing следует planning (`continuesToPlanning`), модель завершает рефлексию без planning-invite; server `ensureSummaryToPlanningBridge` добавляет детерминированный мост «Что важного вы хотите запланировать на текущий день?». `mergeSummarySessionItems` объединяет summary-артефакты из `conversationMeta` и `messages.meta.planning_persistence` turn-history.

- **SSE без изменений**: `chunk` (стрим текста), `complete` (UI-поля: `fullText` sanitized, `shouldClose`, `turnMode`, `practicePicked`, `targetChakra`, `phaseTime`, `branches=[ветка хода]`, `recommendationCorrected`), затем `turn_artifacts` (`messageId`, `planningPersistence`), при ошибке — `error`. `turnMode` ∈ `opening|inquiry|final_recommendation|final_without_practice` (совместимо с клиентскими `turnModeCarriesPractice`/`isFinalLikeTurnMode`). Событие `orchestrator_decision` больше не шлётся (клиент трактует его как опциональное). Финал FSM убирает свои приватные сентинелы (`stripBrainSentinels`). Поверх prompt-запрета на спонтанный английский в русском тексте применяется детерминированный `replaceSpontaneousEnglishRu` (для не-en локалей): заменяет курируемый набор частых «протечек» (`task/tasks`, `quietly`, `mindfully/mindfulness`, `flow`, `focus`, `balance`…) на русские эквиваленты с сохранением капитализации; незнакомые латинские токены не трогаются (могут быть названным пользователем термином).
- **Кэширование под DeepSeek (важно):** для каждого хода `systemInstruction` = **только** стабильная общая преамбула (`sharedPreamble`, идентична на всех ходах и во всех ветках одного дня; при совпадении языка ввода и ответа строка `inputLanguageDecouplingInstruction` пуста), а все ветко- и походо-зависимые инструкции уходят в финальное user-сообщение (`userInstruction`). Запрос — `[system(стабильный), …history(растёт), userMsg, directive]`, поэтому автоматический prefix-cache DeepSeek держит `system + history` «тёплым» на каждом ходе после первого. Явный Gemini-кэш (`ensureDialogCache`) к DeepSeek не применяется (`supportsExplicitLlmCache=false`) и FSM-маршрутом не используется. **Нельзя** возвращать походовые данные в преамбулу — это сбросит кэш на каждом ходе.
- **Карточка практики:** текст карточки (`practice_picked.card_blurb`) формирует `practiceCardSummary.ts` — сначала валидируется model-generated `card_blurb` из `[PRACTICE_PICK]`, иначе fallback по `kind`. Generic fallback для meditation/yoga и `buildPracticeAssistantReason` — locale-native для всех 8 `AppContentLocale`; детальные breath-slug blurbs — только RU/EN (de–nl получают generic breath copy). `practiceSelection.ts` локализует `practice_picked.name` через `getCoherenceBreathStrings` / `getPracticeCatalogStrings` и jsonb `title` по `context.user.locale`. `practice_picked.reason` отдельно формирует короткий видимый мост ассистента к состоянию дня.
- **GET `/dialog`** — синхронизация сессии: TTL простоя `sessionResumeTtlMs()`; по `conversationId` или последней открытой беседе `entry_source`, фильтр по `isConversationExpired`; в ответе только сообщения внутри окна TTL, иначе `reset: true`. Исключение: `debugExport=1` вместе с явным `conversationId` разрешает прочитать уже закрытую/протухшую беседу для dev-export и дополнительно вернуть `dialogStateAfter` (`planning_created_in_this_conversation`, `planning_open_now`, `planning_closed_recent_48h`, relevant `daily_matrices`, forecast snapshot) даже если тексты сообщений уже были удалены при `closeConversation()`. При создании **новой** беседы без `conversationId` backend предварительно закрывает другие открытые беседы того же `entry_source` + `use_case`, чтобы fresh day/home-session не цеплялись за “висящую” старую conversation при последующей hydration/sync. Два URL (`/api/ai/dialog`, `/api/communicator/v2/dialog`) обслуживаются одним кодом.

> **Архив v7.** Прежний «мозг» (мега-промпт `dialog_system_v3`, `decideTurnMode`, история-инференс, двухмодельная эскалация, отложенная reconcile-очередь) удалён из активного кода. Дословные тексты v7-промптов и описание старого алгоритма — в архиве `docs/05_archive/migrated/assistant/dialog_v7_prompts-reference.md`; код восстановим из git-истории. В активном спеке держим только FSM-реальность выше.

### Вспомогательные LLM-маршруты (тот же продуктовый контур)

- `**POST /api/communicator/v2/greeting**` — короткое приветствие без полного диалога (промпты + контекст профиля / прогноза).
- `**POST /api/communicator/v2/recommendation-text**` — генерация короткого/длинного текста по строке прогноза (`prompt_key` из БД).
- `**POST /api/communicator/v2/dialog/reconcile-plans**` / `**POST /api/ai/dialog/reconcile-plans**` — **совместимый no-op**. FSM пишет `planned_events` / `daily_matrices` / day-focus синхронно на финале ветки (`dialogBrainPersistence.ts`), отдельной отложенной очереди больше нет. Клиент по-прежнему debounce-вызывает endpoint на close/unmount (и терпит его отсутствие), поэтому маршрут оставлен и просто отвечает `{ applied: false }`.
- `**GET/PATCH/POST /api/day**` — read/write endpoint вкладки «День`. `GET` теперь отдаёт не плоский список на один день, а **режим экрана** `mode = "empty_today" | "overdue_summary" | "current_day"` плюс `sections[]` по локальным датам. `GET` читает `users.locale` (`asContentLocale`) и локализует `sphereStats[].title` (`getLifeSphereTitle`), `sphereHint` и подписи practice-log (`getDayStrings`, `getCoherenceBreathStrings`). Если есть неподытоженные `planned_events.status='planned'` на датах `< today`, endpoint возвращает `mode="overdue_summary"`: только эти прошлые даты, по одной секции на дату (`actions`, практики, sphere-stats), сортировка секций — более свежая сверху, более ранняя внизу, `summaryTargetLocalDate` = верхняя overdue-дата, `hasOverdueSummary=true`, а текущий день в ответ **не подмешивается**. Если хвоста прошлых дней нет, endpoint возвращает один current-day section и отдельно `canSummarizeCurrentDay` для CTA `Подытожить этот день`; при полном отсутствии действий/практик/pending-practice — `mode="empty_today"`. Для current-day `dayRecommendation` отдаётся только при `user_daily_forecasts.is_corrected_via_dialog=true` на `forecast_date` текущего дня — это артефакт ветки **planning** (`[CORRECT_RECOMMENDATION]` → `persistDayFocus`), а не summarizing. Debug-export summary-only беседы отдельно помечает `today_forecast_when_summary_only`, чтобы текст из `forecast_for_local_date` не путали с выводом диалога. В `actions[].cells` backend отдаёт только sphere-only набор `{ sphere, weight }`, без chakra-хвоста, потому что он используется только для day-diagram. PATCH редактирует/удаляет только неподытоженные planned rows и отменяет pending practice; POST заменяет одну pending practice на день. На каждом `GET` backend также отменяет (`status='cancelled'`) pending `day_practice_offers` с `local_date < today`, чтобы карточка практики прошлого дня не висела на новом дне.

### Не входят в этот spec

- `**POST /api/ai/global-content**` — раздача прекомпутированного глобального контента по тарифу; связан с подпиской и утренним UX, но не является оркестратором ассистента.
- `**/api/calibration/extract**` — модуль `calibration` (extract / averaging), может использоваться параллельно голосовой калибровке.

## 4. Конфигурация и параметры

- `**_legacy_web/config/contentLengths.ts**` — целевые длины слогана, короткого и длинного текста, портрета.

- **Режим тестирования интервалов (опционально):** `TEST_MODE_FAST_INTERVALS=1` сжимает anti-replan 4ч и `sessionResumeTtlMs()` для reopen/sync, но **не** меняет persistence `planned_events`: auto-expiry по `expected_at` отключён, due-rows не удаляются автоматически. **TTL conversation внутри активного POST-диалога остаётся 2ч** (`sessionTtlMs()`). `TEST_MODE_TIME_DIVISOR` (дефолт 600); `TEST_MODE_FORCE_PHASE` (`morning` \| `day` \| `evening`) подменяет `phaseTime`, переменные приветствия в промпте (`local_hour`, `time_of_day`) и effective local hour для разбора пользовательских planning-time фраз внутри POST, а cutoff `dueEvents` в самом диалоге выравнивает по representative часу forced-phase, чтобы untimed/daypart-планы не выглядели уже прошедшими только из-за реального позднего часа устройства. `DEBUG_DIALOG_EXPORT=1` включает расширенную отладочную выгрузку диалога. Клиент `Communicator` вне test mode держит `responseLocale = app/profile locale` и STT hint = `getTranscribeLocale()` (active locale); `EXPO_PUBLIC_I18N_TEST_MODE` включает противоположный QA-путь: voice-turn может опустить STT hint, автоопределить язык речи и временно override-ить `inputLocale` + `responseLocale` детектированным поддержанным языком, не меняя системную локаль приложения. - **LLM / cache:** модели через `AI_MODEL_STANDARD`, `AI_MODEL_PREMIUM`, `AI_MODEL_FALLBACK`, опционально `AI_MODEL_LOW` (если не задан — low-cost reconciliation берёт `AI_MODEL_STANDARD`). `generateGeminiJson` / `generateGeminiText` / `streamGeminiText` принимают либо старый строковый `prompt`, либо structured request (`systemInstruction`, `contents`, `cachedContent`); имя файла `gemini.ts` историческое, runtime уже работает и с DeepSeek через тот же wrapper. Отдельная новая summary-таблица не используется: подытоженные действия остаются в `planned_events` со статусом `summarized` до конца текущего локального дня, после чего backend автоматически очищает старые `summarized` rows при следующей загрузке day/dialog-контекста. После этого `daily_matrices` становятся каноническим compact day-rollup слоем для диалога и отчётов, а `profile_report_snapshots` — быстрым read-cache для двух profile reports. Миграции `dialog_system_v3` (v5 → v7, `2026051..`/`20260608203000_dialog_system_v3_v7.sql`) остаются в `public.prompts` как история. **С июня 2026 daily dialog больше не рендерит DB-промпт `dialog_system_v3`**: «мозг» переехал на код-side промпты `dialogBranchPrompts.ts`, и активная строка `dialog_system_v3` в `public.prompts` для нового FSM-пути не используется. Монологи и прочие LLM-маршруты по-прежнему читают свои `prompt_key` из `public.prompts`.
- **Baseline-данные промптов:** `_legacy_web/data/life_spheres_baseline/{ru,en}.json` (загрузчик `lifeSpheresBaseline.ts`) — заголовки сфер 1–7 согласованы с `PLANET_THEME_LABELS_RU` в `_legacy_web/app/api/_utils/dto.ts`; `prompt_hint` расширены под домены отдыха, отношений, финансов, переговоров, духовности. `_legacy_web/data/chakra_states_baseline.json` — семантические маркеры для калибровки и matrix-classifier. `_legacy_web/app/api/_utils/dialogTonalRegisters.ts` — тональные регистры по планете дня (`tonalRegisterForPlanet` в `route.ts`).

## 5. Известные ограничения

- Два URL диалога (`**/api/ai/dialog**` и `**/api/communicator/v2/dialog**`): клиент без `scenario_id` всё ещё использует старый путь (`services/communicator-client.ts`).
- `choosePractice` теперь предпочитает `user_daily_forecasts.day_target_chakra`, если она уже зафиксирована; fallback всё ещё идёт в `planet_of_the_day`.
- `day_target_chakra` фиксируется отдельно от `windows_of_opportunity`: полный пересчёт окон по новой цели дня в текущем коде пока не выполняется автоматически, если не пришёл явный `[CORRECT_RECOMMENDATION]` с `windows_correction`.
- Explicit Gemini cache сейчас хранится только в in-memory store процесса Node; меж-инстансного Redis/Upstash-контура в репозитории нет.
- Ошибка монолога `**morning_recommendation**` при `< 3` лепестков защитная; при нормальном прогнозе на 7 планет после ранжирования не возникает.
