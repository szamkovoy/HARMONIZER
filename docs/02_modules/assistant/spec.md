## 1. Назначение

Серверный слой **LLM-ассистента**: монологи (один запрос Gemini → JSON или текст) и диалог дня v3/v5 с единым системным промптом `dialog_system_v3`, коротким rule-based оркестратором, двухступенчатой эскалацией `standard → premium` по маркеру `[READY_FOR_RECOMMENDATION]` и новым двухфазным контуром `summarizing -> planning`. Начиная с v5 диалог держит **тексты беседы на клиенте**, а на сервере сохраняет только краткоживущие live-планы в `planned_events`, дневные агрегаты в `daily_matrices`, кэш итоговых отчётов в `profile_report_snapshots`, минимальные `conversation_summaries` для anti-replan/TTL и `user_daily_forecasts.day_target_*` на локальный день. Клиентский UI чата и транспорт SSE на стороне приложения относятся к модулю `communicator`; расчёт астроданных — к `astro` / `daily_forecast`; усреднение калибровки по голосу без диалога v3 — к `calibration`.

## 2. Публичный контракт

Набор **HTTP API** на Vercel (`_legacy_web`), авторизация Bearer JWT Supabase.

### Монологи

- `**POST /api/ai/monologue`** (`_legacy_web/app/api/ai/monologue/route.ts`)
  - Тело: `{ scenario_id: string; variables?: Record<string, unknown> }`.
  - Резолвит строку `**scenarios**` по `scenario_id`, берёт активный промпт по `monologue_prompt_key`, подставляет переменные, вызывает Gemini JSON (`generateGeminiJson`).
  - Кеш: таблица `**scenario_cache**`, стратегия из сценария (`per_user_per_day`, `per_user_per_calibration`, `no_cache`). Утренний сценарий инвалидируется при смене модели или отсутствии `modelUsed` в кэше (`isStaleMorningCache`).
  - Специальные сценарии в коде:
    - `**morning_recommendation**` — собирает переменные из последнего `user_daily_forecasts`, натала, калибровки, пользователя; строит топ-3 планеты (`buildTopPetals`), `**math_level**` (`buildMathLevel`), голос автора, подсказку обращения (`address_form` → hint).
    - `**psychological_portrait**` — добавляет `portrait_target_chars` из `CONTENT_LENGTHS`.

Клиент: `**callMonologue(scenarioId, variables)**` в `services/aiClient.ts` → тот же endpoint.

### Диалог дня v3

- `**POST /api/ai/dialog**` — реэкспорт обработчика из `**POST**` `_legacy_web/app/api/communicator/v2/dialog/route.ts` (тот же код).
- `**POST /api/communicator/v2/dialog**` — помечен deprecated в логах (`warnDeprecatedDialogRoute`), поведение идентично для совместимости.
- `**practiceCardSummary.ts**` — сервер формирует **краткий** текст для карточки в `practice_picked`: сначала валидирует model-generated `**card_blurb`** из `[PRACTICE_PICK]` (длина/markup), и только если он отсутствует, невалиден или итоговая практика не совпала с маркером — уходит в fallback rules по `kind` (йога — чакры из `practice_chakras` + акцент на теле; медитация — статическое описание; дыхание — строки по `slug`). Источник каталожных описаний для fallback: `**modules/practices/core/catalog.ts`** (`**BREATH_CATALOG_DESCRIPTION_RU`**, `**STATIC_MEDITATIONS[].description`**); в серверном каталоге выбора практики те же kind имеют `**description`** у `**STATIC_MEDITATION`** / `**STATIC_COHERENT_BREATH`** в `practiceSelection.ts`.

Поведение `**POST`**:

- Тело: `scenario_id?`, `conversationId?`, `useCase?`, `entrySource`, `triggerMeta`, `userMessage`, `userTimezone`, опционально `turnHistory` (нормализуется в `dialogHelpers.normalizeTurnHistory`: сохраняет `practice_picked` / `practicePicked` и `turn_mode`, прочий `meta` отбрасывается).
- Реализованный путь v3/v5 сейчас обслуживает только `**daily_dialog**`; для него сервер грузит активный промпт `**dialog_system_v3**` из `public.prompts`, рендерит его из данных дня (`planet_of_the_day`, гармоничность, словари чакры, локальное время, обращение, **`tonal_register`** по планете дня из `**dialogTonalRegisters.ts**`, **`phase_time`**, **`branches`**, **`due_events`**, **`top3_planets`**, **`target_chakra`**, **`life_spheres_baseline`**) и передаёт в Gemini как `**systemInstruction**`.
- История сообщения + текущий ввод пользователя преобразуются в structured `**contents**` (`role: "user" | "model"`). Короткая инструкция из `**dialogArcOrchestrator.ts**` всегда кладётся **последним** сообщением `role: "user"` в `contents`, не сливается ни с `systemInstruction`, ни с пользовательским текстом; для инструкций с плейсхолдерами чакры/гармоничности и одноходовым флагом отказа (`final_recommendation`, `final_recommendation_with_validation_warning`, `**fast_track_final**`, `**inquiry**`, `**opening**`) в `**route.ts**` выполняется **`expandOrchestratorInstruction`** (`renderPrompt` по `{{chakra_label}}`, `{{chakra_label_accusative}}`, `{{harmoniousness_value}}`, `{{harmoniousness_label}}`, `{{practice_refusal_check}}`, `{{catalog_reconciliation}}`, `{{opening_day_question}}` из `openingDayQuestionForContext` в `dialogOpeningHints.ts`). Для `opening` действует жёсткое правило: первое сообщение должно быть простым человеческим приветствием без упоминаний чакр/планет/астрологии и без поэтических метафор; при `summarizing` вопрос привязывается к событию, которое пора подытожить, а при `planning` — к планам дня/завтра по фазе.
- Rule-based оркестратор `**decideTurnMode(history, iteration, maxDialogLength, pendingUserContent?, emitFastTrackDiagnostics?)**` выбирает режим `opening`, `inquiry`, `forced_final`, `**fast_track_final**`, `**final_without_practice**`, `post_recommendation` или `**practice_repick**` (явный отказ от практики на сессию через `userDeclinedPracticeInHistory` в `markers.ts` теперь мапится именно в общий финальный ход без карточки, а не в отдельный параллельный closing-flow); лимит ходов задаёт `**effectiveDialogMax(branches)**` из `dialogBranching.ts` (`MAX_DIALOG_PLANNING` / `MAX_DIALOG_SUMMARIZING` / `MAX_DIALOG_BOTH`, дефолты 9 / 6 / 13). Режим `**fast_track_final**` срабатывает не только на самом первом ходе, но и на **первом ответе ассистента после автоприветствия `opening`**, если в истории ещё нет пользовательских сообщений, первая содержательная реплика пользователя (`pendingUserContent`) даёт `validateHistoryHasDurationAndType(...).confident === true` (**тип и минуты согласованы** с диапазонами v6: медитация 1–5, дыхание 5–20, асаны 20–70; диапазон вроде `10-15 минут дыхания` нормализуется к среднему и тоже считается согласованным) **и** helper `**isPracticeOnlyFirstTurn(...)**` подтверждает, что реплика почти целиком про запрос на практику, без заметного жизненного контекста. Если в первой реплике есть богатый контекст дня (`важный разговор`, эмоции, ставки, планы и т.п.) плюс практика, оркестратор **не** уходит в `fast_track_final`, а остаётся на `inquiry`, чтобы затем вывести полноценный `final_recommendation`. Для `fast_track_final` модель **premium**, сразу `streamGeminiText` без standard-хода и без `[READY_FOR_RECOMMENDATION]`. Если в истории уже есть **любой** assistant-turn с `practice_picked` / `practicePicked` (не только последний — чтобы короткий `post_recommendation` между финалом и запросом замены не сбрасывал режим), оркестратор различает два пост-финальных сценария: обычный `**post_recommendation**` (короткий ответ на `спасибо`, общий follow-up без новой карточки) и `**practice_repick**`, когда пользователь явно просит другой вариант (`другая практика`, `не подходит`, `замени`). `practice_repick` идёт сразу в premium и обязан вернуть новый `[PRACTICE_PICK]` с коротким текстом без повторения длинного финала. Для режима `**inquiry**` оркестратор дополнительно считает подряд идущие `opening` / `inquiry`-ходы без уверенного ответа о длительности и типе; когда их число `>= getPracticeRefusalThreshold()` (env `PRACTICE_REFUSAL_THRESHOLD`, дефолт **1**), в инструкцию подставляется `{{practice_refusal_check}}` с прямым вопросом, нужна ли практика вообще — **только если пользователь ещё не назвал и тип, и длительность** (`userAnsweredPracticeRequest`). Если тип и длительность названы, но не согласованы с каталогом v6, подставляется `{{catalog_reconciliation}}` (`buildCatalogReconciliationInstruction`) — переспрос «сократить тип / выбрать альтернативу», без refusal-check (см. `prompts-reference.md` §2 `inquiry`). Если пользователь просит **короткую / минимальную** практику без числа минут, `markers.ts` подставляет нижнюю границу каталога для уже названного типа (медитация 1, дыхание 5, асаны 20), поэтому `inquiry` не должен вытягивать ещё один вопрос «сколько минут?`. В той же ветке `inquiry` промпт больше не должен добирать у planning-события сферу жизни / подтекст / состояние, если пользователь уже назвал конкретный эпизод со временем: такие детали относятся к `summarizing`, а не к первичному planning. Для generic формулировки `йога` / `практика йоги` с длительностью **>= 20 мин** `inquiry` должен считать тип уже определённым как **асаны** и не тратить дополнительный ход на переподтверждение; если в одной реплике упомянуты несколько типов, `markers.ts` ориентируется на последнее явное упоминание пользователя, а не на первое ключевое слово в фразе. `**final_without_practice**` закрывает сессию тем же финальным контрактом, что и остальные final-ходы, просто без карточки практики: рекомендация на день сохраняется, follow-up вопросы запрещены, а при активной ветке `summarizing` сервер всё так же repair-ит отсутствующий `[SUMMARIZE_EVENT]`, когда пользователь уже фактически описал итог единственного due-события.
- Первый проход идёт через `**standard**` модель буферно (`generateGeminiText`), **кроме** ходов с `**turnDecision.modelTier === "premium"`** (в т.ч. `forced_final` и `fast_track_final`), где сразу вызывается `**streamGeminiText**`. Если текст standard-ответа содержит только технический маркер `**[READY_FOR_RECOMMENDATION]**`, сервер валидирует историю (`validateHistoryHasDurationAndType`) и делает второй проход через `**premium**` модель потоково (`streamGeminiText`) с одной из двух финальных инструкций: `final_recommendation` или `final_recommendation_with_validation_warning`. Если на ходе `**inquiry**` маркера нет, но `validateHistoryHasDurationAndType` уже `confident: true`, `**shouldServerEscalateToFinalRecommendation**` запускает тот же premium-проход с `final_recommendation` (лог `[DIALOG_V3_DIAG] server-side ready escalation`). Дополнительно для чистой ветки `planning` сервер может **вообще пропустить standard-вопрос** и сразу уйти в premium `final_recommendation`, если user history уже даёт уверенную пару `тип + минуты`, а planning-эпизод извлекается из пользовательских реплик через `inferPlannedEventsFromUserHistory(...)` или уже лежит в открытых `planned_events` беседы (лог `[DIALOG_V3_DIAG] bypassing standard inquiry and escalating directly from history`). Для комбинированной ветки `summarizing + planning` есть ещё один repair-path: если единственное due-событие явно уже подытожено в пользовательской реплике, но standard-ответ не выдал `[SUMMARIZE_EVENT]`, `route.ts` делает повторный standard-вызов с `branchRepairInstruction(...)`, чтобы вернуть invisible summary marker до перехода к финальной рекомендации. Финальные инструкции (включая `forced_final` и `fast_track_final`) требуют маркер `[PRACTICE_PICK]` **первой строкой** ответа (до видимого текста) и не должны оставлять пользователю новых вопросов или просьб что-либо уточнить после рекомендации. Если `validation.confident === true`, сервер дополнительно подмешивает в финальную premium-инструкцию жёсткий lock на видимый `bridge-to-practice`: модель должна назвать **ровно** тот тип и ту длительность, которые уже валидировал backend, чтобы текст рекомендации не расходился с `practice_picked.overrides`. Если после premium-ответа маркер не обнаружен, выполняется retry-вызов Gemini (`temperature: 0.3`, `maxOutputTokens: 320`) для восстановления маркера; при неудаче — лог `[DIALOG_V3_DIAG] retry also failed to produce marker`. `route.ts` теперь также пытается использовать explicit provider-cache для **стабильного префикса диалога** (`systemInstruction + baseHistory`) через `ensureDialogCache(...)`, но только если текущая модель поддерживает provider-side cached content; для `deepseek-*` этот путь автоматически отключён. **`resolvePracticePublic`** при `validation.confident === true` выбирает практику через `choosePractice` **даже без маркера** (история пользователя — источник истины для типа/минут).
- Ответ: **SSE** — событие `orchestrator_decision`, затем `chunk`, затем **`complete`** (UI-поля, включая `practicePicked`, **до** `persistDialogArtifacts`), затем после записи assistant-row — **`turn_artifacts`** (`messageId`, `planningPersistence`, `relatedEventIds`, `skippedPlannedEvents`, `matrixCells`). UI остаётся в состоянии thinking до появления первого видимого текста; при стандартном буферном ходе сервер отправляет `chunk` только после полной готовности текста. Сервер теперь явно разводит два helper-контракта: финальный ход вообще (`final_recommendation`, `final_recommendation_with_validation_warning`, `forced_final`, `fast_track_final`, `final_without_practice`) и финальный ход, который **несёт карточку практики** (`final_recommendation`, `final_recommendation_with_validation_warning`, `forced_final`, `fast_track_final`, `practice_repick`). Поэтому поле **`practicePicked`** в `complete` (и **`practice_picked`** / `practicePicked` в persist `messages.meta`, а также `practicePublic` в `debugExport`) заполняются только для card-carrying режимов; на `opening`, `inquiry`, `post_recommendation`, `final_without_practice` — отсутствует / `null`. `planningPersistence` приходит в `turn_artifacts` и дублируется в `messages.meta`, но delayed step теперь общий для planning и summarizing: assistant-turn не пишет синхронно ни новые `planned_events`, ни итоговые summary-merge в `daily_matrices`, а складывает planning-candidates в `planningPersistence.queued` и summary-candidates в `planningPersistence.queued_summaries`; отдельный reconcile-step позже создаёт/обновляет канонические rows в `planned_events`, вычисляет `outcome_cells` для queued summaries и уже затем merge-ит `daily_matrices`. `GET /dialog` и `POST /dialog/reconcile-plans` умеют догонять уже просроченную очередь. Внутри `planningPersistence` backend различает `queued`, `queued_summaries`, `inserted`, `summarized`, `skipped`, `updated`, чтобы QA видел и отложенную канонизацию, и итоговый merge existing row.
- Маркеры ответа: `**[READY_FOR_RECOMMENDATION]`**, `**[PRACTICE_PICK: id="..." duration_min="..." chakra="..." reason="..." card_blurb="..."]**`, `**[CORRECT_RECOMMENDATION: ...]**`, `**[PLANNED_EVENT: ...]**`, `**[SUMMARIZE_EVENT: ...]**`, `**[PLAN_TOMORROW]**`, `**[MATRIX_CELLS: ...]**`. Сервер вырезает их из видимого текста, но использует для эскалации, выбора практики, коррекции `user_daily_forecasts`, постановки delayed planning/summary-candidates в `conversations.trigger_meta`, позднего обновления `planned_events` и `daily_matrices`, пересборки `profile_report_snapshots` и минимальных `conversation_summaries`. При активной ветке `planning` `route.ts` параллельно держит два среза открытых планов: `loadOpenPlannedEventsForConversation` для debug/export и refinement UX текущей беседы, и `loadOpenPlannedEventsForUserHorizon` для антидублей по всему пользователю на окне `today/tomorrow`. После парсинга маркеров `augmentPlannedMarkers` использует единый matcher из `plannedEventInference.ts`: `inferPlannedEventsFromUserHistory` извлекает timed-события только из последних user-turns (+ текущий ввод, сегменты через `splitEventSegments`, без practice-only ответов вроде «15 минут»), `mergePlannedEventMarkers` объединяет их с `[PLANNED_EVENT]` модели, `filterNewPlannedEvents` удаляет только уже существующие `same`-совпадения, а конфликт `same identity + same local day + другое explicit time` оставляет до persist-слоя как `ambiguous_time_conflict`. `hasRequiredBranchArtifacts` считает ветку `planning` закрытой, если есть маркер **или** уже существуют открытые rows user-wide horizon (`openPlannedEventCount > 0`) — это же условие блокирует server-side ready escalation и преждевременный `[READY_FOR_RECOMMENDATION]`.
- Практика выбирается сервером через `**choosePractice**` независимо от старых phase-условий; marker `id="default"` резолвится в когерентное дыхание на 10 минут с чакрой дня. Явный не-`default` маркер по каталогу учитывается только если **`id` после `.trim()`** непустой. Для такого маркера **сначала** ищется практика по `id` / `slug` в полном активном каталоге (все `kind`); эвристика `validateHistoryHasDurationAndType` (в т.ч. `practiceKind`) сужает выборку только если id не найден (лог `[PRACTICE_SELECTOR] marker_id_not_in_catalog`) или для пути без явного id. Если маркер найден в каталоге, но **`validateHistoryHasDurationAndType` даёт `confident: true`** и **`practiceKind` из истории** не совпадает с `kind` практики из маркера — **id маркера сбрасывается** для шага выбора: ранжирование и окно «недавних» идут по типу из истории (`historyKindConflictResolved` в результате `choosePractice`; в том же результате для диагностики логов — `markerCatalogPracticeKind`). Если `confident` **нет**, а маркер и эвристика по типу расходятся, по-прежнему используется **тип из маркера** для окна недавних (как защита от шумной эвристики). Подсказки из завершённых сессий (`practice_id` / `practice_slug`) и из `practice_picked` в истории нормализуются к **каноническому `id`** строки каталога (`**resolvePracticeKeyToCatalogId**`); `**selectPracticeCandidate**` исключает недавние практики **только по этому `id`**. Маркер (нормализованный к `id`) учитывается **только среди кандидатов, ещё не попавших в недавнее окно**; если маркер отброшен как «недавний» или иначе не попал в итоговый стек — лог `[PRACTICE_SELECTOR] marker_id_not_found`, в `meta.practicePicked` — `markerIdResolved: false`, берётся лучший допустимый кандидат. `choosePractice` всегда возвращает `chakraId` (из `planet_of_the_day`) и `preferredDurationMin` (из **всей** истории пользователя через `validateHistoryHasDurationAndType`). При извлечении минут `markers.ts` теперь предпочитает длительность, ближайшую к упоминанию практики, а не первое попавшееся время в реплике, поэтому фразы вроде «через полчаса вебинар, предложи три минуты медитации» не превращаются в ложный конфликт `30 мин meditation`, а ответы вида «ладно, пять минут медитации, раньше говорил три» фиксируют именно подтверждённые 5 минут. В `**resolvePracticePublic**` для **дыхания и медитации** поле `**overrides.durationMin**` берётся из истории при `confident: true` (маркер `duration_min` только если история **не** дала уверенной длительности); иначе — `marker.durationMin ?? preferredDurationMin`. Если перед клипом минуты всё ещё `null`, для не-йоги подставляется длительность из **`durationSec`** выбранной практики (в минутах), иначе дефолт **10** мин (дыхание) / **3** мин (медитация). Итоговые минуты **клипятся** к допустимому списку (`**assistantSelectableDurations.ts**`, те же шаги, что и в `PracticeCard`: дыхание 5–20, медитация 1–5). При клипе или при расхождении маркера с историей **сильнее** `PRACTICE_CARD_DURATION_MISMATCH_THRESHOLD_MIN` (2 мин) — `console.log` с тегом **`[PRACTICE_CARD_MISMATCH]`** (сервер: JSON с `markerDuration`, `historyDuration`, `markerKind`, `historyKind`, `finalDuration`, `finalKind`, `conversationId`, флаги `durationClipped`, `durationMismatchExceededThreshold`, `historyKindConflictResolved`; клиент **`PracticeCard`** при клипе добавляет **`source: "practice_card_client_sync"`**, **`conversationId`** там обычно `null`).
- После санитизации премиум-ответа сервер проверяет, что видимый текст не пуст; если `cleanText` оказался пустым (маркер без текста, полностью вырезанный контент и т.п.), бросается ошибка с логом `**[PREMIUM_EMPTY_RESPONSE]`** (включая `iteration`, `turn_mode`, `model_tier`, `raw_length`, первые 200 символов сырого ответа) — клиент получит ошибку вместо пустого пузыря.
- В `**messages.meta**` сохраняются `turn_mode`, `model_used` (`standard` / `premium`), `model_id`, `iteration`, `ready_marker_triggered`, `validation`, `practice_picked` (опционально `**overrides: { durationMin, chakraIndex }**` для **дыхания и медитации** — `durationMin` после `**resolvePracticePublic**`: приоритет уверенной истории, клип к шагам каталога; `chakraIndex` = маркер или `planet_of_the_day`; для **йоги (`kind: yoga`)** `overrides` **не** записываются: длительность и чакра — из каталога), `markerIdResolved`, `recommendationCorrected`, `insight_metrics`, опционально `**debug**` (`TurnDebugExport` при `isDebugDialogExportEnabled()`), а после ходов с matrix/planning markers — `dialog_branches`, `target_chakra`, `phase_time`, `related_event_ids`, `matrix_cells`. Для daily dialog `messages.content` больше не используется как источник текста: в БД остаются только служебные строки с `meta`, а сам текст хода живёт в клиентском `turnHistory` и локальном session-cache. Внутри `practice_picked` поле `**card_blurb`** хранит валидированный model-generated текст карточки (если он принят), а `**reason`** остаётся эффективным текстом карточки для UI: либо этот `card_blurb`, либо server fallback из `practiceCardSummary.ts`.

`**GET /api/ai/dialog`** / `**GET /api/communicator/v2/dialog**` — синхронизация сессии: TTL простоя — `sessionResumeTtlMs()` (сжатый в test mode при reopen). При query `**conversationId**` беседа возвращается только если сценарий совпадает **и** (`debugExport=1` **или** `ended_at` пустой и беседа не протухла по `isConversationExpired` + TTL); иначе ответ `reset: true`. Без `conversationId` — последняя открытая беседа по `entry_source` с тем же TTL-фильтром. Сообщения в ответе: полная `rawHistory` только при `debugExport=1`; иначе — только строки с `created_at` внутри окна TTL. Query `**debugExport=1**` при `isDebugDialogExportEnabled()` дополнительно добавляет `dialogStateAfter` (`buildDialogStateAfter` в `dialogDebugExport.ts`).

### Вспомогательные LLM-маршруты (тот же продуктовый контур)

- `**POST /api/communicator/v2/greeting**` — короткое приветствие без полного диалога (промпты + контекст профиля / прогноза).
- `**POST /api/communicator/v2/recommendation-text**` — генерация короткого/длинного текста по строке прогноза (`prompt_key` из БД).
- `**POST /api/communicator/v2/dialog/reconcile-plans**` / `**POST /api/ai/dialog/reconcile-plans**` — отдельный low-cost delayed reconcile pending dialog-artifacts после idle-дебаунса: сервер читает `conversations.trigger_meta.pending_planning_reconciliation`, где теперь лежат и `planning_candidates`, и `summary_candidates`. Planning и summarizing остаются в одном delayed pass, но summary-путь больше не является частью того же смешанного prompt-а: reconcile сначала сравнивает planning-очередь с текущими due/open plans и решает `create_new` / `update_existing` / `ignore` для `planned_events`, а queued summary-эпизоды обрабатывает отдельной двухшаговой цепочкой `normalize outcome -> classify outcome_cells` перед merge в `daily_matrices`. По умолчанию используется `AI_MODEL_LOW`, а если переменная не задана — `AI_MODEL_STANDARD`.

### Не входят в этот spec

- `**POST /api/ai/global-content**` — раздача прекомпутированного глобального контента по тарифу; связан с подпиской и утренним UX, но не является оркестратором ассистента.
- `**/api/calibration/extract**` — модуль `calibration` (extract / averaging), может использоваться параллельно голосовой калибровке.

### Типы решений оркестратора (сводка)

Используются поля из `_legacy_web/app/api/_utils/orchestrator.ts`: `next_phase`, `reasoning`, `information_completeness`, `information_density`, `user_signals`, опционально `**user_register**`, `should_close`, `close_reason`, `**responder_hints**` (в т.ч. `**tone**`, `**use_user_phrases**`, `**avoid_topics**`, опционально `**preferred_register**`, `**astrology_budget**`, `**chakra_budget**`, `**length_hint**`), опционально `**decision_source**` (`fresh`  `bypass_greeting`  `cache_reused`), `**cache_similarity**`, `**insight_metrics**` (пишется в объект решения и в логи событий).

Однократное предупреждение при старте Node — `logTestModeStartupWarning` из `instrumentation.ts`.                                                                                                                                                                                                                              |


Персистенция диалога: `**conversations**`, `**messages**`; в `**messages.meta**` для daily dialog v3 сохраняются режим хода, модель, маркеры валидации и `practice_picked`, без старого `orchestrator_decision`/`phase_id` из фазовой архитектуры. Сами тексты daily dialog на сервере не хранятся: `messages.content` остаётся пустым, а закрытие беседы (`closeConversation`) удаляет message-строки полностью. `**conversation_summaries**` после ходов с matrix/planning markers пишутся только для веток, отличных от `free`/`none`; `upsertConversationSummary` конфликтует по `conversation_id` (`onConflict`), чтобы повторные assistant-turn не падали с `23505`; поле `summary_text` — служебный тег `[branch:phaseTime]`, не полный текст реплики. Сборка профильного snapshot — `buildLifeMatrixReportSnapshot` в `lifeMatrix.ts`, persist/rebuild — `lifeMatrixPersistence.ts` (`PROFILE_REPORT_SNAPSHOT_VERSION`).

## 4. Конфигурация и параметры

- `**_legacy_web/config/contentLengths.ts**` — целевые длины слогана, короткого и длинного текста, портрета.
- **Переменные окружения (диалог v5):** `MAX_DIALOG_LENGTH`, `MAX_DIALOG_PLANNING`, `MAX_DIALOG_SUMMARIZING`, `MAX_DIALOG_BOTH`, `PRACTICE_REFUSAL_THRESHOLD`, `RANGE_GROUP_SIZE`, `LIFE_MATRIX_LOG_SMOOTHING_K`, `LIFE_MATRIX_OVERDEV_FACTOR`. При отсутствии берутся дефолты из `dialogConfig.ts`.
- **Режим тестирования интервалов (опционально):** `TEST_MODE_FAST_INTERVALS=1` сжимает anti-replan 4ч и `sessionResumeTtlMs()` для reopen/sync, но **не** сжимает реальное окно подытоживания/cleanup `planned_events` — expiry по `expected_at` остаётся обычные 36 часов. **TTL conversation внутри активного POST-диалога остаётся 2ч** (`sessionTtlMs()`). `TEST_MODE_TIME_DIVISOR` (дефолт 600); `TEST_MODE_FORCE_PHASE` (`morning` \| `day` \| `evening`) подменяет `phaseTime`, переменные приветствия в промпте (`local_hour`, `time_of_day`) и effective local hour для разбора пользовательских planning-time фраз внутри POST, а cutoff `dueEvents` в самом диалоге выравнивает по representative часу forced-phase, чтобы untimed/daypart-планы не выглядели уже прошедшими только из-за реального позднего часа устройства. `DEBUG_DIALOG_EXPORT=1` включает расширенную отладочную выгрузку диалога. Подробнее — `docs/04_reference/test_mode.md`.
- **LLM / cache:** модели через `AI_MODEL_STANDARD`, `AI_MODEL_PREMIUM`, `AI_MODEL_FALLBACK`, опционально `AI_MODEL_LOW` (если не задан — low-cost reconciliation берёт `AI_MODEL_STANDARD`). `generateGeminiJson` / `generateGeminiText` / `streamGeminiText` принимают либо старый строковый `prompt`, либо structured request (`systemInstruction`, `contents`, `cachedContent`); имя файла `gemini.ts` историческое, runtime уже работает и с DeepSeek через тот же wrapper. Fallback-цепочка: premium → standard → fallback или standard → fallback; повторяется при 503/429/timeout-подобных ошибках. `ensureDialogCache(...)` создаёт explicit cache на 600 c и переиспользует `cache.name` по ключу `dialog_cache:<conversationId>:<historyHash>`, но вызывается только для моделей, которые реально поддерживают provider-side cached content; для `deepseek-*` этот путь no-op.
- **БД:** `planned_events`, `daily_matrices`, новые поля `conversation_summaries.branch/phase_time/related_event_ids/matrix_cells` и `user_daily_forecasts.day_target_*` вводятся миграцией **`20260516132000_life_matrix_foundation.sql`**. Миграция **`20260525130000_profile_report_snapshots.sql`** добавляет `profile_report_snapshots` и индекс по `daily_matrices(user_id, source, local_date)`. После этого `daily_matrices` становятся каноническим compact day-rollup слоем для диалога и отчётов, а `profile_report_snapshots` — быстрым read-cache для двух profile reports. Миграция **`20260516150000_dialog_system_v3_v5.sql`** подготавливает `dialog_system_v3` v5 (`is_active = false`); **`20260519030000_dialog_system_v3_v5_activate.sql`** активировала v5 как промежуточную версию. Текущий runtime уже использует **`dialog_system_v3` v6** из **`20260521120000_dialog_system_v3_v6.sql`**: в проде активен prompt с усиленным отказом от практики и переспросом при конфликте тип/длительность. Монологи и legacy-фазовые prompts остаются в `public.prompts` для остальных маршрутов.

## 5. Известные ограничения

- Два URL диалога (`**/api/ai/dialog**` и `**/api/communicator/v2/dialog**`): клиент без `scenario_id` всё ещё использует старый путь (`services/communicator-client.ts`).
- `choosePractice` теперь предпочитает `user_daily_forecasts.day_target_chakra`, если она уже зафиксирована; fallback всё ещё идёт в `planet_of_the_day`.
- `day_target_chakra` фиксируется отдельно от `windows_of_opportunity`: полный пересчёт окон по новой цели дня в текущем коде пока не выполняется автоматически, если не пришёл явный `[CORRECT_RECOMMENDATION]` с `windows_correction`.
- Explicit Gemini cache сейчас хранится только в in-memory store процесса Node; меж-инстансного Redis/Upstash-контура в репозитории нет.
- Ошибка монолога `**morning_recommendation**` при `< 3` лепестков защитная; при нормальном прогнозе на 7 планет после ранжирования не возникает.
