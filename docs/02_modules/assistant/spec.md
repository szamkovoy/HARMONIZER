## 1. Назначение

Серверный слой **LLM-ассистента**: монологи (один запрос Gemini → JSON или текст) и диалог дня v3 с единым системным промптом `dialog_system_v3`, коротким rule-based оркестратором и двухступенчатой эскалацией `standard → premium` по маркеру `[READY_FOR_RECOMMENDATION]`. Клиентский UI чата и транспорт SSE на стороне приложения относятся к модулю `communicator`; расчёт астроданных — к `astro` / `daily_forecast`; усреднение калибровки по голосу без диалога v3 — к `calibration`.

## 2. Публичный контракт

Набор **HTTP API** на Vercel (`_legacy_web`), авторизация Bearer JWT Supabase.

### Монологи

- `**POST /api/ai/monologue`** (`_legacy_web/app/api/ai/monologue/route.ts`)
  - Тело: `{ scenario_id: string; variables?: Record<string, unknown> }`.
  - Резолвит строку `**scenarios**` по `scenario_id`, берёт активный промпт по `monologue_prompt_key`, подставляет переменные, вызывает Gemini JSON (`generateGeminiJson`).
  - Кеш: таблица `**scenario_cache**`, стратегия из сценария (`per_user_per_day`, `per_user_per_calibration`, `no_cache`). Утренний сценарий инвалидируется при смене модели или отсутствии `modelUsed` в кэше (`isStaleMorningCache`).
  - Специальные сценарии в коде:
    - `**morning_recommendation**` — собирает переменные из последнего `user_daily_forecasts`, натала, калибровки, пользователя; строит топ-3 планеты (`buildTopPetals`), `**math_level**` (`buildMathLevel`), голос автора, подсказку обращения (`address_form` → hint).
    - `**psychological_portrait**` — добавляет `portrait_target_chars` из `CONTENT_LENGTHS`.

Клиент: `**callMonologue(scenarioId, variables)**` в `services/aiClient.ts` → тот же endpoint.

### Диалог дня v3

- `**POST /api/ai/dialog**` — реэкспорт обработчика из `**POST**` `_legacy_web/app/api/communicator/v2/dialog/route.ts` (тот же код).
- `**POST /api/communicator/v2/dialog**` — помечен deprecated в логах (`warnDeprecatedDialogRoute`), поведение идентично для совместимости.
- `**practiceCardSummary.ts**` — сервер формирует **краткий** текст для поля `reason` в `practice_picked` (карточка в UI): правила по `kind` (йога — чакры из `practice_chakras` + акцент на теле; медитация — общий смысл; дыхание — строки по `slug` из семи практик каталога). Без дословной цитаты последнего сообщения пользователя в хвосте текста. Маркер `[PRACTICE_PICK]` по-прежнему задаёт **id** (и опционально поля в маркере); длинное поле `reason` в маркере **не** дублируется в карточку.

Поведение `**POST`**:

- Тело: `scenario_id?`, `conversationId?`, `useCase?`, `entrySource`, `triggerMeta`, `userMessage`, `userTimezone`.
- Реализованный путь v3 сейчас обслуживает только `**daily_dialog**`; для него сервер грузит активный промпт `**dialog_system_v3**` из `public.prompts`, рендерит его из данных дня (`planet_of_the_day`, гармоничность, словари чакры, локальное время, обращение, **`tonal_register`** по планете дня из `**dialogTonalRegisters.ts**`) и передаёт в Gemini как `**systemInstruction**`.
- История сообщения + текущий ввод пользователя преобразуются в structured `**contents**` (`role: "user" | "model"`). Короткая инструкция из `**dialogArcOrchestrator.ts**` всегда кладётся **последним** сообщением `role: "user"` в `contents`, не сливается ни с `systemInstruction`, ни с пользовательским текстом; для инструкций с плейсхолдерами чакры/гармоничности (`final_recommendation`, `final_recommendation_with_validation_warning`, `**fast_track_final**` и др.) в `**route.ts**` выполняется **`expandOrchestratorInstruction`** (`renderPrompt` по `{{chakra_label}}`, `{{harmoniousness_value}}`, `{{harmoniousness_label}}`).
- Rule-based оркестратор `**decideTurnMode(history, iteration, maxDialogLength, pendingUserContent?)**` выбирает режим `opening`, `inquiry`, `forced_final`, `**fast_track_final**` или `post_recommendation`; лимит ходов задаёт `**getMaxDialogLength()**` (`MAX_DIALOG_LENGTH`, дефолт 9). Режим `**fast_track_final**` — первый ход (`iteration === 1`), в истории ещё нет `practice_picked`, в сессии ровно **одна** пользовательская реплика до ответа ассистента, и по ней `validateHistoryHasDurationAndType` на одном сообщении вернул `confident: true`; модель **premium**, сразу `streamGeminiText` без standard-хода и без `[READY_FOR_RECOMMENDATION]` (см. `prompts-reference.md` §2 `fast_track_final`).
- Первый проход идёт через `**standard**` модель буферно (`generateGeminiText`), **кроме** ходов с `**turnDecision.modelTier === "premium"`** (в т.ч. `forced_final` и `fast_track_final`), где сразу вызывается `**streamGeminiText**`. Если текст standard-ответа содержит только технический маркер `**[READY_FOR_RECOMMENDATION]**`, сервер валидирует историю (`validateHistoryHasDurationAndType`) и делает второй проход через `**premium**` модель потоково (`streamGeminiText`) с одной из двух финальных инструкций: `final_recommendation` или `final_recommendation_with_validation_warning`. Финальные инструкции (включая `forced_final` и `fast_track_final`) требуют маркер `[PRACTICE_PICK]` **первой строкой** ответа (до видимого текста). Если после premium-ответа маркер не обнаружен, выполняется retry-вызов Gemini (`temperature: 0.3`, `maxOutputTokens: 200`) для восстановления маркера; при неудаче — лог `[DIALOG_V3_DIAG] retry also failed to produce marker`.
- Ответ: **SSE** — событие `orchestrator_decision`, затем `chunk`, затем `complete`. UI остаётся в состоянии thinking до появления первого видимого текста; при стандартном буферном ходе сервер отправляет `chunk` только после полной готовности текста.
- Маркеры ответа: `**[READY_FOR_RECOMMENDATION]`**, `**[PRACTICE_PICK: id="..." duration_min="..." chakra="..." reason="..."]**`, `**[CORRECT_RECOMMENDATION: ...]**`. Сервер вырезает их из видимого текста, но использует для эскалации, выбора практики и коррекции `user_daily_forecasts`. Поля `duration_min` и `chakra` обязательны в инструкции модели; парсер извлекает их опционально (если отсутствуют — `null`).
- Практика выбирается сервером через `**choosePractice**` независимо от старых phase-условий; marker `id="default"` резолвится в когерентное дыхание на 10 минут с чакрой дня. Явный не-`default` маркер по каталогу учитывается только если **`id` после `.trim()`** непустой. Для такого маркера **сначала** ищется практика по `id` / `slug` в полном активном каталоге (все `kind`); эвристика `validateHistoryHasDurationAndType` (в т.ч. `practiceKind`) сужает выборку только если id не найден (лог `[PRACTICE_SELECTOR] marker_id_not_in_catalog`) или для пути без явного id. Если маркер найден в каталоге, но **`validateHistoryHasDurationAndType` даёт `confident: true`** и **`practiceKind` из истории** не совпадает с `kind` практики из маркера — **id маркера сбрасывается** для шага выбора: ранжирование и окно «недавних» идут по типу из истории (`historyKindConflictResolved` в результате `choosePractice`; в том же результате для диагностики логов — `markerCatalogPracticeKind`). Если `confident` **нет**, а маркер и эвристика по типу расходятся, по-прежнему используется **тип из маркера** для окна недавних (как защита от шумной эвристики). Подсказки из завершённых сессий (`practice_id` / `practice_slug`) и из `practice_picked` в истории нормализуются к **каноническому `id`** строки каталога (`**resolvePracticeKeyToCatalogId**`); `**selectPracticeCandidate**` исключает недавние практики **только по этому `id`**. Маркер (нормализованный к `id`) учитывается **только среди кандидатов, ещё не попавших в недавнее окно**; если маркер отброшен как «недавний» или иначе не попал в итоговый стек — лог `[PRACTICE_SELECTOR] marker_id_not_found`, в `meta.practicePicked` — `markerIdResolved: false`, берётся лучший допустимый кандидат. `choosePractice` всегда возвращает `chakraId` (из `planet_of_the_day`) и `preferredDurationMin` (из **всей** истории пользователя через `validateHistoryHasDurationAndType`). В `**resolvePracticePublic**` для **дыхания и медитации** поле `**overrides.durationMin**` берётся из истории при `confident: true` (маркер `duration_min` только если история **не** дала уверенной длительности); иначе — `marker.durationMin ?? preferredDurationMin`. Если перед клипом минуты всё ещё `null`, для не-йоги подставляется длительность из **`durationSec`** выбранной практики (в минутах), иначе дефолт **10** мин (дыхание) / **3** мин (медитация). Итоговые минуты **клипятся** к допустимому списку (`**assistantSelectableDurations.ts**`, те же шаги, что и в `PracticeCard`: дыхание 5–20, медитация 1–10). При клипе или при расхождении маркера с историей **сильнее** `PRACTICE_CARD_DURATION_MISMATCH_THRESHOLD_MIN` (2 мин) — `console.log` с тегом **`[PRACTICE_CARD_MISMATCH]`** (сервер: JSON с `markerDuration`, `historyDuration`, `markerKind`, `historyKind`, `finalDuration`, `finalKind`, `conversationId`, флаги `durationClipped`, `durationMismatchExceededThreshold`, `historyKindConflictResolved`; клиент **`PracticeCard`** при клипе добавляет **`source: "practice_card_client_sync"`**, **`conversationId`** там обычно `null`).
- После санитизации премиум-ответа сервер проверяет, что видимый текст не пуст; если `cleanText` оказался пустым (маркер без текста, полностью вырезанный контент и т.п.), бросается ошибка с логом `**[PREMIUM_EMPTY_RESPONSE]`** (включая `iteration`, `turn_mode`, `model_tier`, `raw_length`, первые 200 символов сырого ответа) — клиент получит ошибку вместо пустого пузыря.
- В `**messages.meta**` сохраняются `turn_mode`, `model_used` (`standard` / `premium`), `model_id`, `iteration`, `ready_marker_triggered`, `validation`, `practice_picked` (опционально `**overrides: { durationMin, chakraIndex }**` для **дыхания и медитации** — `durationMin` после `**resolvePracticePublic**`: приоритет уверенной истории, клип к шагам каталога; `chakraIndex` = маркер или `planet_of_the_day`; для **йоги (`kind: yoga`)** `overrides` **не** записываются: длительность и чакра — из каталога), `markerIdResolved`, `recommendationCorrected`, `insight_metrics`. Поле `**reason`** внутри `practice_picked` — **краткое** описание для карточки (см. `practiceCardSummary.ts`), не дословный текст из маркера модели.

`**GET /api/ai/dialog`** / `**GET /api/communicator/v2/dialog**` — синхронизация сессии (история сообщений за окно ~2 ч).

### Вспомогательные LLM-маршруты (тот же продуктовый контур)

- `**POST /api/communicator/v2/greeting**` — короткое приветствие без полного диалога (промпты + контекст профиля / прогноза).
- `**POST /api/communicator/v2/recommendation-text**` — генерация короткого/длинного текста по строке прогноза (`prompt_key` из БД).

### Не входят в этот spec

- `**POST /api/ai/global-content**` — раздача прекомпутированного глобального контента по тарифу; связан с подпиской и утренним UX, но не является оркестратором ассистента.
- `**/api/calibration/extract**` — модуль `calibration` (extract / averaging), может использоваться параллельно голосовой калибровке.

### Типы решений оркестратора (сводка)

Используются поля из `_legacy_web/app/api/_utils/orchestrator.ts`: `next_phase`, `reasoning`, `information_completeness`, `information_density`, `user_signals`, опционально `**user_register**`, `should_close`, `close_reason`, `**responder_hints**` (в т.ч. `**tone**`, `**use_user_phrases**`, `**avoid_topics**`, опционально `**preferred_register**`, `**astrology_budget**`, `**chakra_budget**`, `**length_hint**`), опционально `**decision_source**` (`fresh`  `bypass_greeting`  `cache_reused`), `**cache_similarity**`, `**insight_metrics**` (пишется в объект решения и в логи событий).

## 4. Конфигурация и параметры

- `**_legacy_web/config/contentLengths.ts**` — целевые длины слогана, короткого и длинного текста, портрета.
- **Переменные окружения (диалог v3):** `MAX_DIALOG_LENGTH` — hard-cap числа ответов ассистента до `forced_final`; при отсутствии значения используется `9`. Лог `[DIALOG_V3_DEBUG_PROMPT]` (полный `systemInstruction` и `contents` в JSON) пишется, если `NODE_ENV !== "production"` **или** `DEBUG_DIALOG_PROMPT=1` **или** в URL запроса есть `?debug=prompt` **или** заголовок `X-Debug-Prompt: 1`. В **production** без этих флагов полный промпт в лог не выводится.
- **Gemini:** модели через `AI_MODEL_STANDARD`, `AI_MODEL_PREMIUM`, `AI_MODEL_FALLBACK`. `generateGeminiJson` / `generateGeminiText` / `streamGeminiText` принимают либо старый строковый `prompt`, либо structured request (`systemInstruction`, `contents`, `cachedContent`). Fallback-цепочка: premium → standard → fallback или standard → fallback; повторяется при 503/429/timeout-подобных ошибках. `ensureDialogCache(...)` создаёт explicit cache на 600 c и переиспользует `cache.name` по ключу `dialog_cache:<conversationId>:<historyHash>`.
- **БД:** активный системный prompt v3 задаётся миграцией **`20260513224500_dialog_system_v3_polish_pack_a_fix.sql`** (версия 3 — перенос секции «отказ от практики»; деактивирует v2). Ранее пакет «А»: **`20260513223000_dialog_system_v3_polish_pack_a.sql`** (v2), базовая v3 — **`20260511161000_dialog_system_v3.sql`**. Монологи и legacy-фазовые prompts остаются в `public.prompts` для остальных маршрутов.

## 5. Известные ограничения

- Два URL диалога (`**/api/ai/dialog**` и `**/api/communicator/v2/dialog**`): клиент без `scenario_id` всё ещё использует старый путь (`services/communicator-client.ts`).
- Выбор практики в `**choosePractice**` привязывает чакру к `**planet_of_the_day**`, тогда как утренний монолог опирается на топ-3 по importance — возможен продуктовый разрыв темы дня vs стека практики (зафиксировано в `history.md`).
- Explicit Gemini cache сейчас хранится только в in-memory store процесса Node; меж-инстансного Redis/Upstash-контура в репозитории нет.
- Ошибка монолога `**morning_recommendation**` при `< 3` лепестков защитная; при нормальном прогнозе на 7 планет после ранжирования не возникает.
