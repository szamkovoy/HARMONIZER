## 1. Назначение

Серверный слой **LLM-ассистента**: монологи (один запрос Gemini → JSON или текст) и **диалог дня на явном конечном автомате (FSM)**. С июня 2026 переусложнённый «мозг» (мега-промпт `dialog_system_v3` v7 + эвристический оркестратор `decideTurnMode` + история-инференс + двухмодельная эскалация по `[READY_FOR_RECOMMENDATION]` + отложенная reconcile-очередь) **заменён** на детерминированный автомат: сервер хранит, в какой ветке диалога он находится, и на каждый ход запускает **ОДНУ** ветку с **ОДНИМ** коротким промптом, парсит **ОДИН** тип маркера и переходит дальше детерминированно. Старый «мозг» удалён из активного кода (восстановим из git-истории; дословные v7-промпты — в `docs/05_archive/migrated/assistant/dialog_v7_prompts-reference.md`).

Три последовательные ветки: **summarizing** (подытоживание прошедших событий по одному), **planning** (сбор действий дня + общий фокус), **practice** (одна поддерживающая практика или отказ). Состояние автомата лежит в `conversations.trigger_meta.dialog_fsm` (`flow`, `branchIndex`, `branch`, `summaryAsked`, `planningFinalized`, `practiceDecided`, `noPractice`, `noGreeting`, `targetChakra`, `workingLocalDate`). Диалог держит **тексты беседы на клиенте**, а на сервере сохраняет действия в одной таблице `planned_events` (со статусами `planned` / `summarized`), дневные агрегаты в `daily_matrices`, кэш отчётов в `profile_report_snapshots`, минимальные `conversation_summaries` и `user_daily_forecasts.day_target_*` на локальный день. Клиентский UI чата и транспорт SSE — модуль `communicator`; астроданные — `astro` / `daily_forecast`; усреднение калибровки по голосу — `calibration`.

## 2. Публичный контракт

Набор **HTTP API** на Vercel (`_legacy_web`), авторизация Bearer JWT Supabase.

### Монологи

- `**POST /api/ai/monologue`** (`_legacy_web/app/api/ai/monologue/route.ts`)
  - Тело: `{ scenario_id: string; variables?: Record<string, unknown> }`.
  - Резолвит строку `**scenarios**` по `scenario_id`, берёт активный промпт по `monologue_prompt_key`, подставляет переменные, вызывает Gemini JSON (`generateGeminiJson`).
  - Кеш: таблица `**scenario_cache**`, стратегия из сценария (`per_user_per_day`, `per_user_per_calibration`, `no_cache`). Утренний сценарий инвалидируется при смене модели или отсутствии `modelUsed` в кэше (`isStaleMorningCache`).
  - Специальные сценарии в коде:
    - `**morning_recommendation**` — собирает переменные из последнего `user_daily_forecasts`, натала, калибровки, пользователя; строит топ-3 планеты (`buildTopPetals`), `**math_level**` (`buildMathLevel`), голос автора, подсказку обращения (`address_form` → hint).
    - `**psychological_portrait**` — добавляет `portrait_target_chars` из `CONTENT_LENGTHS`.

Клиент: `**callMonologue(scenarioId, variables)**` в `services/aiClient.ts` → тот же endpoint.

### Диалог дня — явный автомат (актуальная архитектура)

URL и SSE-контракт не изменились (клиент не трогали). Изменился **только «мозг»**.

- **Один ход — одна ветка — один промпт — один маркер.** `POST /dialog` грузит контекст дня (`loadDialogDailyContext`), читает/инициализирует FSM (`dialogFsm.ts`), строит **один** короткий промпт текущей ветки (`dialogBranchPrompts.ts`), делает **один** вызов `streamGeminiText` (всегда **premium**, без двухмодельной эскалации), парсит маркеры и детерминированно переходит дальше. История-инференс (`inferPlannedEventsFromUserHistory`), `decideTurnMode`, `[READY_FOR_RECOMMENDATION]`-эскалация и отложенная reconcile-очередь **не используются**.
- **Инициализация FSM** (`initFsmState`) по точкам входа: `dayTabMode='add'|'plan'` → `flow=['planning']` (без приветствия для `add`, без practice); `daySummaryRequested` → `flow=['summarizing']` (закрытие после резюме); обычный home-flow → `flow=[summarizing?, 'planning', 'practice']`. В home summarizing включается только если есть **незавершённые `planned_events` предыдущего локального дня**, а не просто любые `expected_at <= now`; текущий день не должен самопроизвольно открываться в summary из-за времени суток. Для `daySummaryRequested` backend грузит **все** неподытоженные rows с `planned_local_date <= workingLocalDate`, так что summary из вкладки `День` сначала добирает хвост прошлых дней и только потом переходит к событиям выбранного дня. `targetChakra` берётся из `user_daily_forecasts.day_target_chakra` и держится весь локальный день. Состояние пишется в `conversations.trigger_meta.dialog_fsm` (`writeFsmState`).
- **PLANNING** (`buildPlanningPrompt`): собираем только действия (без времени, без «в каком состоянии», без техдеталей), сохраняем порядок упоминания и не добираем лишние детали про первую/вторую половину дня. Ветка planning всегда относится к **текущему локальному дню из day-context**, поэтому prompt жёстко держит формулировку `сегодня`, а не `завтра`, если пользователь сам не просит планировать завтра. Финал — когда пользователь закончил: по каждому действию `[PLANNED_EVENT: desc(≤40, без «…») recommendation display_order spheres]` + общий `[CORRECT_RECOMMENDATION: short_text]`. Visible planning-final обязан явно назвать **каждое** действие и его рекомендацию, а не ограничиться абстрактным «вот ваши события». `persistPlanningFinalize` синхронно пишет `planned_events`, дедуплицирует и уже существующие rows (`samePlannedEventIdentity`), и повторы маркеров в одном assistant-turn, сохраняет `display_order` по порядку упоминания и sphere-only `cells`; `persistDayFocus` пишет `user_daily_forecasts.recommendation_short_text`. Затем FSM → `practice` (или `done` для day `add` / `plan`). В add-режиме приветствия и общего фокуса нет, practice не предлагается.
- **PRACTICE** (`buildPracticePrompt`): это отдельная ветка только про практику, без пересказа дня и без подмены типа практики. Модель либо коротко уточняет `kind + duration` одним вопросом, либо сразу завершает ветку маркером `[PRACTICE_PICK: id="" reason duration_min chakra card_blurb]`; карточку резолвит `resolvePracticeCard` (порт `resolvePracticePublic`, тот же `choosePractice`, верный `kind`, чакра дня, редактируемая длительность для дыхания/медитации). При отказе — `[PRACTICE_DECLINED]`, `turnMode=final_without_practice`, `shouldClose` (UI показывает кнопку «Выйти»).
- **SUMMARIZING** (`buildSummarizingPrompt`): строго по одному событию. Курсор детерминирован статусом в БД — текущее событие = первый `planned_events.status='planned'` рабочего окна summary: в home-flow это **последний незавершённый локальный день до сегодняшнего**, а в `daySummaryRequested` — весь хвост `planned_local_date <= workingLocalDate` по возрастанию даты и затем `display_order`. `summaryAsked[eventId]` ограничивает уточняющий вопрос одним; если пользователь явно говорит, что событие не состоялось, или после единственного уточнения lived-state всё ещё не собран, сервер закрывает событие без дальнейшего цикла и без `outcome_cells`. Решение о финале принимается по **остатку событий после закрытия текущего**, поэтому ветка не должна оставаться в `summarizing` без `currentEvent` и уходить в абстрактные follow-up вопросы. Если `daySummaryRequested` пришёл, но `dueEvents` уже пусты, backend не строит новое summary-opening без события, а сразу завершает ход коротким terminal-ответом, что неподытоженных действий не осталось. Prompt дополнительно требует выбирать `outcome_cells` по **буквальному домену события и явно названному состоянию**, а не по далёкой символической ассоциации: `sphere/chakra 7` допустимы только при прямом религиозном/духовном/смысловом контексте; переговоры и попытка понять другую сторону должны сначала рассматриваться как `sphere 3` с chakra `3/5/6`, а прогулка/сон/отдых/свежий воздух/природа — как `sphere 1/2` с chakra `1/2`, если пользователь явно не описал обучение/инсайт или духовную практику. Каждое закрытое событие → `[SUMMARIZE_EVENT: ref outcome outcome_cells]`, `persistSummarizedEvent` ставит этому же действию `status='summarized'`, записывает `summarized_at` / `outcome_text` / `outcome_cells` и, если есть `outcome_cells`, мержит вклад в `daily_matrices` с последующей пересборкой `profile_report_snapshots`. Такие `summarized` rows остаются видимыми до конца текущего локального дня, а при начале нового локального дня backend автоматически удаляет старые `planned_events.status='summarized'`, чтобы они не копились как мусор. Финал-резюме (последнее событие) даёт психологическую обратную связь по целевой чакре + наблюдения из Health/йоги строго по переданным данным; если в контексте есть практики или health-метрики, visible reply должен назвать **конкретные** практики/минуты/числа, а не ограничиться общим wellness-абзацем. В полном home-flow финал приглашает перейти к planning.
- **SSE без изменений**: `chunk` (стрим текста), `complete` (UI-поля: `fullText` sanitized, `shouldClose`, `turnMode`, `practicePicked`, `targetChakra`, `phaseTime`, `branches=[ветка хода]`, `recommendationCorrected`), затем `turn_artifacts` (`messageId`, `planningPersistence`), при ошибке — `error`. `turnMode` ∈ `opening|inquiry|final_recommendation|final_without_practice` (совместимо с клиентскими `turnModeCarriesPractice`/`isFinalLikeTurnMode`). Событие `orchestrator_decision` больше не шлётся (клиент трактует его как опциональное). Финал FSM убирает свои приватные сентинелы (`stripBrainSentinels`).
- **Кэширование под DeepSeek (важно):** для каждого хода `systemInstruction` = **только** стабильная общая преамбула (`sharedPreamble`, идентична на всех ходах и во всех ветках одного дня), а все ветко- и походо-зависимые инструкции уходят в финальное user-сообщение (`userInstruction`). Запрос — `[system(стабильный), …history(растёт), userMsg, directive]`, поэтому автоматический prefix-cache DeepSeek держит `system + history` «тёплым» на каждом ходе после первого. Явный Gemini-кэш (`ensureDialogCache`) к DeepSeek не применяется (`supportsExplicitLlmCache=false`) и FSM-маршрутом не используется. **Нельзя** возвращать походовые данные в преамбулу — это сбросит кэш на каждом ходе.
- **Карточка практики:** краткий текст карточки (`practice_picked.reason`) формирует `practiceCardSummary.ts` — сначала валидируется model-generated `card_blurb` из `[PRACTICE_PICK]`, иначе fallback по `kind`.
- **GET `/dialog`** — синхронизация сессии: TTL простоя `sessionResumeTtlMs()`; по `conversationId` или последней открытой беседе `entry_source`, фильтр по `isConversationExpired`; в ответе только сообщения внутри окна TTL, иначе `reset: true`. Исключение: `debugExport=1` вместе с явным `conversationId` разрешает прочитать уже закрытую/протухшую беседу для dev-export и дополнительно вернуть `dialogStateAfter` (`planning_created_in_this_conversation`, `planning_open_now`, `planning_closed_recent_48h`, relevant `daily_matrices`, forecast snapshot) даже если тексты сообщений уже были удалены при `closeConversation()`. При создании **новой** беседы без `conversationId` backend предварительно закрывает другие открытые беседы того же `entry_source` + `use_case`, чтобы fresh day/home-session не цеплялись за “висящую” старую conversation при последующей hydration/sync. Два URL (`/api/ai/dialog`, `/api/communicator/v2/dialog`) обслуживаются одним кодом.

> **Архив v7.** Прежний «мозг» (мега-промпт `dialog_system_v3`, `decideTurnMode`, история-инференс, двухмодельная эскалация, отложенная reconcile-очередь) удалён из активного кода. Дословные тексты v7-промптов и описание старого алгоритма — в архиве `docs/05_archive/migrated/assistant/dialog_v7_prompts-reference.md`; код восстановим из git-истории. В активном спеке держим только FSM-реальность выше.

### Вспомогательные LLM-маршруты (тот же продуктовый контур)

- `**POST /api/communicator/v2/greeting**` — короткое приветствие без полного диалога (промпты + контекст профиля / прогноза).
- `**POST /api/communicator/v2/recommendation-text**` — генерация короткого/длинного текста по строке прогноза (`prompt_key` из БД).
- `**POST /api/communicator/v2/dialog/reconcile-plans**` / `**POST /api/ai/dialog/reconcile-plans**` — **совместимый no-op**. FSM пишет `planned_events` / `daily_matrices` / day-focus синхронно на финале ветки (`dialogBrainPersistence.ts`), отдельной отложенной очереди больше нет. Клиент по-прежнему debounce-вызывает endpoint на close/unmount (и терпит его отсутствие), поэтому маршрут оставлен и просто отвечает `{ applied: false }`.
- `**GET/PATCH/POST /api/day**` — read/write endpoint вкладки «День`. `GET` теперь отдаёт не плоский список на один день, а **режим экрана** `mode = "empty_today" | "overdue_summary" | "current_day"` плюс `sections[]` по локальным датам. Если есть неподытоженные `planned_events.status='planned'` на датах `< today`, endpoint возвращает `mode="overdue_summary"`: только эти прошлые даты, по одной секции на дату (`actions`, практики, sphere-stats), сортировка секций — более свежая сверху, более ранняя внизу, `summaryTargetLocalDate` = верхняя overdue-дата, `hasOverdueSummary=true`, а текущий день в ответ **не подмешивается**. Если хвоста прошлых дней нет, endpoint возвращает один current-day section и отдельно `canSummarizeCurrentDay` для CTA `Подытожить этот день`; при полном отсутствии действий/практик/pending-practice — `mode="empty_today"`. Для current-day ветки Day tab по-прежнему берёт recommendation из `user_daily_forecasts` c fallback на последнюю доступную forecast-row пользователя, чтобы planning-corrected `recommendation_short_text` не исчезал из UI. В `actions[].cells` backend отдаёт только sphere-only набор `{ sphere, weight }`, без chakra-хвоста, потому что он используется только для day-diagram. PATCH редактирует/удаляет только неподытоженные planned rows и отменяет pending practice; POST заменяет одну pending practice на день.

### Не входят в этот spec

- `**POST /api/ai/global-content**` — раздача прекомпутированного глобального контента по тарифу; связан с подпиской и утренним UX, но не является оркестратором ассистента.
- `**/api/calibration/extract**` — модуль `calibration` (extract / averaging), может использоваться параллельно голосовой калибровке.

## 3. Внутренняя архитектура

**Индекс хранения daily dialog:** сводная таблица «что где лежит» — `docs/00_index/MAP.md` § «Где искать: хранение daily dialog». Клиентский канон текста — `communicator/spec.md` §3.1.

**Активный «мозг» (FSM, июнь 2026):**

| Компонент | Роль |
| --- | --- |
| `**dialogFsm.ts**` | Явная модель состояния в `conversations.trigger_meta.dialog_fsm`: `flow`, `branchIndex`, `branch` (`summarizing`/`planning`/`practice`/`done`), `summaryAsked`, `planningFinalized`, `practiceDecided`, `noPractice`, `noGreeting`, `targetChakra`, `workingLocalDate`. Хелперы `readFsmState`, `initFsmState` (выбор `flow` по точке входа), `advanceBranch`, `isLastBranch`, `bumpSummaryAsked`/`summaryAskedCount`, `writeFsmState`. |
| `**dialogBranchPrompts.ts**` | Три коротких фокусных промпта с английским ядром и русскими данными: `sharedPreamble`, `buildSummarizingPrompt`, `buildPlanningPrompt`, `buildPracticePrompt`. Общая преамбула дополнительно фиксирует time-of-day greeting, один вопрос за ход, запрет на псевдопоэзию/астро-метафоры/санскрит и ограничение «психологический» тон только на branch finals. `stripBrainSentinels` снимает приватные сентинелы из видимого текста, `containsPracticeDeclined` ловит `[PRACTICE_DECLINED]`. Заменяет мега-промпт `dialog_system_v3` для daily dialog. |
| `**dialogBrainPersistence.ts**` | Детерминированная синхронная персистенция: `persistPlanningFinalize` (insert/update `planned_events`, dedupe, `display_order`, sphere-only `cells`; в `dayTabMode='add'` новые rows получают хвостовой `display_order` после уже существующего списка дня), `persistDayFocus` (`user_daily_forecasts.recommendation_short_text`), `persistSummarizedEvent` (переводит это же действие в `status='summarized'`, пишет `summarized_at` / `outcome_text` / `outcome_cells`, при наличии `outcome_cells` мержит вклад в `daily_matrices`). Заменяет отложенную reconcile-очередь. |
| `**dialogPracticeCard.ts**` | `resolvePracticeCard` — порт `resolvePracticePublic`: тот же `choosePractice`, верный `kind`, чакра дня, редактируемая длительность для дыхания/медитации. |

## 4. Конфигурация и параметры

- `**_legacy_web/config/contentLengths.ts**` — целевые длины слогана, короткого и длинного текста, портрета.
- **Переменные окружения (диалог v5):** `MAX_DIALOG_LENGTH`, `MAX_DIALOG_PLANNING`, `MAX_DIALOG_SUMMARIZING`, `MAX_DIALOG_BOTH`, `PRACTICE_REFUSAL_THRESHOLD`, `RANGE_GROUP_SIZE`, `LIFE_MATRIX_LOG_SMOOTHING_K`, `LIFE_MATRIX_OVERDEV_FACTOR`. При отсутствии берутся дефолты из `dialogConfig.ts`.
- **Режим тестирования интервалов (опционально):** `TEST_MODE_FAST_INTERVALS=1` сжимает anti-replan 4ч и `sessionResumeTtlMs()` для reopen/sync, но **не** меняет persistence `planned_events`: auto-expiry по `expected_at` отключён, due-rows не удаляются автоматически. **TTL conversation внутри активного POST-диалога остаётся 2ч** (`sessionTtlMs()`). `TEST_MODE_TIME_DIVISOR` (дефолт 600); `TEST_MODE_FORCE_PHASE` (`morning` \| `day` \| `evening`) подменяет `phaseTime`, переменные приветствия в промпте (`local_hour`, `time_of_day`) и effective local hour для разбора пользовательских planning-time фраз внутри POST, а cutoff `dueEvents` в самом диалоге выравнивает по representative часу forced-phase, чтобы untimed/daypart-планы не выглядели уже прошедшими только из-за реального позднего часа устройства. `DEBUG_DIALOG_EXPORT=1` включает расширенную отладочную выгрузку диалога. Подробнее — `docs/04_reference/test_mode.md`.
- **LLM / cache:** модели через `AI_MODEL_STANDARD`, `AI_MODEL_PREMIUM`, `AI_MODEL_FALLBACK`, опционально `AI_MODEL_LOW` (если не задан — low-cost reconciliation берёт `AI_MODEL_STANDARD`). `generateGeminiJson` / `generateGeminiText` / `streamGeminiText` принимают либо старый строковый `prompt`, либо structured request (`systemInstruction`, `contents`, `cachedContent`); имя файла `gemini.ts` историческое, runtime уже работает и с DeepSeek через тот же wrapper. Fallback-цепочка: premium → standard → fallback или standard → fallback; повторяется при 503/429/timeout-подобных ошибках. `ensureDialogCache(...)` создаёт explicit cache на 600 c и переиспользует `cache.name` по ключу `dialog_cache:<conversationId>:<historyHash>`, но вызывается только для моделей, которые реально поддерживают provider-side cached content; для `deepseek-*` этот путь no-op.
- **БД:** `planned_events`, `daily_matrices`, новые поля `conversation_summaries.branch/phase_time/related_event_ids/matrix_cells` и `user_daily_forecasts.day_target_*` вводятся миграцией **`20260516132000_life_matrix_foundation.sql`** и follow-up миграциями. Миграция **`20260525130000_profile_report_snapshots.sql`** добавляет `profile_report_snapshots` и индекс по `daily_matrices(user_id, source, local_date)`. Миграция **`20260607183000_day_tab_foundation.sql`** расширяет `planned_events` полями `display_order`, `recommendation_text`, `explicit_time_text` и добавляет `day_practice_offers` для одной ожидающей практики на локальный день. Follow-up миграция **`20260608153000_allow_day_entry_source.sql`** расширяет `conversations_entry_source_check`, чтобы daily dialog реально принимал `entry_source = 'day'` от вкладки «День`, а не падал при создании `conversations`. Отдельная новая summary-таблица не используется: подытоженные действия остаются в `planned_events` со статусом `summarized` до конца текущего локального дня, после чего backend автоматически очищает старые `summarized` rows при следующей загрузке day/dialog-контекста. После этого `daily_matrices` становятся каноническим compact day-rollup слоем для диалога и отчётов, а `profile_report_snapshots` — быстрым read-cache для двух profile reports. Миграции `dialog_system_v3` (v5 → v7, `2026051..`/`20260608203000_dialog_system_v3_v7.sql`) остаются в `public.prompts` как история. **С июня 2026 daily dialog больше не рендерит DB-промпт `dialog_system_v3`**: «мозг» переехал на код-side промпты `dialogBranchPrompts.ts`, и активная строка `dialog_system_v3` в `public.prompts` для нового FSM-пути не используется. Монологи и прочие LLM-маршруты по-прежнему читают свои `prompt_key` из `public.prompts`.
- **Baseline-данные промптов:** `_legacy_web/data/life_spheres_baseline/{ru,en}.json` (загрузчик `lifeSpheresBaseline.ts`) — заголовки сфер 1–7 согласованы с `PLANET_THEME_LABELS_RU` в `_legacy_web/app/api/_utils/dto.ts`; `prompt_hint` расширены под домены отдыха, отношений, финансов, переговоров, духовности. `_legacy_web/data/chakra_states_baseline.json` — семантические маркеры для калибровки и matrix-classifier. `_legacy_web/app/api/_utils/dialogTonalRegisters.ts` — тональные регистры по планете дня (`tonalRegisterForPlanet` в `route.ts`).

## 5. Известные ограничения

- Два URL диалога (`**/api/ai/dialog**` и `**/api/communicator/v2/dialog**`): клиент без `scenario_id` всё ещё использует старый путь (`services/communicator-client.ts`).
- `choosePractice` теперь предпочитает `user_daily_forecasts.day_target_chakra`, если она уже зафиксирована; fallback всё ещё идёт в `planet_of_the_day`.
- `day_target_chakra` фиксируется отдельно от `windows_of_opportunity`: полный пересчёт окон по новой цели дня в текущем коде пока не выполняется автоматически, если не пришёл явный `[CORRECT_RECOMMENDATION]` с `windows_correction`.
- Explicit Gemini cache сейчас хранится только в in-memory store процесса Node; меж-инстансного Redis/Upstash-контура в репозитории нет.
- Ошибка монолога `**morning_recommendation**` при `< 3` лепестков защитная; при нормальном прогнозе на 7 планет после ранжирования не возникает.
