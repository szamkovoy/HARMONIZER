- **2026-06-18 (8):** Add-flow follow-up QA (`текст-48B3-BF3C-17-0`). Two polish fixes around the same root cause. First, the user reply `Non voglio affrontare niente` was semantically “I do not want to add anything else”, but `userSignalsPlanningDone` did not recognize that Italian shape, so `finalizeIntent` stayed false, the server kept the branch in gathering mode, `shouldClose` never flipped, and the just-added row stayed with `recommendation_text = null`. Second, the LLM-driven add-flow opening was left too loose: it knew `existingActionCount`, but it could still sound like “plan from scratch”. `buildPlanningPrompt` now explicitly requires the opening to acknowledge that the day already has something planned before asking what else to add, without forcing the exact count into the visible text every time. Tests: `dialogTurnGuards.test.ts`, `dialogBranchPrompts.test.ts`.

- **2026-06-18 (7):** Follow-up IT QA (`текст-4519-9F07-5F-0`, `текст-47B2-AE85-40-0`, `текст-4FD9-9683-79-0`). Root cause of the missing Day-tab exit button / gray mic after add-flow was not the client close button: the server never recognized the turn as a real add-flow final. `userSignalsPlanningDone` only understood RU/EN done-phrases, while visible-final salvage only accepted the locale-native `recommendationLabel`. In the failing dialog the user closed the plan in Italian (`Questo è sufficiente`, `NONO`, `Non c'è più niente da aggiungere`), but the model emitted an English `Recommendation:` label, so `finalizeIntent` stayed false, `shouldClose` never flipped, and new `planned_events` remained with `recommendation_text = null`, which is why the Day list later showed the placeholder instead of the per-action recommendation. Fix: `dialogTurnGuards.ts` now recognizes cross-locale planning-done signals (IT/FR/DE/ES/PT/NL + bare negation variants) and `extractPlanningMarkersFromVisibleFinalize()` accepts recommendation labels from all scaffold locales plus leaked English `Recommendation:` in any locale. `route.ts` adds one more backstop for add-flow: if the previous assistant turn already looked like a numbered add final, the next user ack retro-closes the FSM to `done` instead of reopening planning. In the same pass, summary prompt wording was tightened so simple lived-state phrases (`I liked it`, `it felt intense`, `I felt proud / good about myself`) are treated as sufficient without a second reductive clarifier, and health prompt formatting now sends sleep duration as hours+minutes instead of raw total minutes. Tests: `dialogTurnGuards.test.ts`; build verified with `npm --prefix _legacy_web run build`.

- **2026-06-18 (2):** Planning persistence переведена из «последний turn + marker fallback» в **накопительную каноническую схему по всей planning-ветке**. Корневая проблема после итальянского QA оказалась не только в invisible markers, а в том, что even improved fallback смотрел лишь на **текущую** пользовательскую реплику: если пользователь называл действия в нескольких сообщениях, финальный turn без `[PLANNED_EVENT]` мог сохранить только хвост, а детерминированный fallback не знал ни про более ранние действия, ни про их сферы, ни про уже отменённые пункты. Фикс в `route.ts`/`dialogTurnGuards.ts`: client `turnHistory` теперь сохраняет assistant `branches`, route через `collectPlanningBranchUserHistory()` вытаскивает все user-turns именно planning-ветки, `inferPlannedEventsFromUserHistory(...)` работает по накопленному planning-history, а не по одному сообщению, и `inferPlanningSpheresFromText()` детерминированно заполняет `cells` там, где модель их не дала. Дальше `persistPlanningFinalize` получает уже **канонический список всей ветки** и на каждом planning-ходе upsert-ит его целиком: обычный planning переписывает собственный список беседы (с чисткой stale rows этой беседы), add-flow по-прежнему только дописывает хвост после уже существующего дня. Отдельно накопительный fallback теперь уважает отмены: `dismissed` rows этой беседы исключаются из history-derived списка, чтобы отменённое действие не «воскресало» на следующем ходу. Тесты: `dialogTurnGuards.test.ts`, `route.test.ts`, `plannedEventInference.test.ts`, плюс `tsc -p _legacy_web/tsconfig.json --noEmit` — зелёные. Docs sync: `assistant/spec.md`, `assistant/history.md`, `00_index/CHANGELOG.md`.

- **2026-06-18:** QA итальянского planning-flow показал, что предыдущий FR-focused фикс был недостаточно фундаментальным: production уже шёл на новом deploy, но беседа `planning -> practice -> done` снова завершилась без новых `planned_events`, а Day-tab продолжал показывать старый французский `recommendation_short_text`. Разбор БД/production-логов показал две архитектурные хрупкости. **(1) Слишком сильная зависимость от invisible `[PLANNED_EVENT]` маркеров.** Если Flash на gathering-ходе не эмитил маркеры, сервер не сохранял действия вообще; если и planning-final приходил без маркеров, salvage по visible text мог не сработать, и тогда не писались ни `planned_events`, ни новый `recommendation_short_text`. Фикс: `route.ts` снова использует `inferPlannedEventsFromUserHistory(...)`, но **узко и детерминированно** — только как аварийный fallback для **текущей пользовательской реплики** на planning-ходе без `[PLANNED_EVENT]`. Это даёт серверу независимый от модели путь сохранить план уже на первом перечислении действий. **(2) Слишком агрессивная очистка орфанов на финале.** Раньше основной финал (`appendToExisting=false`) удалял все `planned`-строки беседы, которых текущий финал не коснулся. Если модель на финальном wrap-up случайно выкидывала одно из ранее названных действий (как с «лечь спать пораньше»), такой пункт стирался из БД, даже если был сохранён на предыдущем ходе. Фикс: `persistPlanningFinalize` получил `deleteOrphans`; route включает его только когда на финале реально пришли **явные marker-backed** `[PLANNED_EVENT]`. Visible/user-fallback финал теперь не считается достаточно авторитетным, чтобы удалять уже собранные действия. Дополнительно, если финал пришёл без явных маркеров, route после persist перечитывает `planned_events` этого `conversation_id` за текущий день и строит deterministic visible-final уже по реально сохранённому набору действий, а не по потенциально урезанному free-text wrap-up модели. Параллельно `plannedEventInference.ts` получил более точный coordinated-action splitter для перечислений вроде «посмотреть лодку в магазине, сходить в кино и пораньше лечь спать», чтобы fallback не схлопывал несколько дел в одно. Тесты: `plannedEventInference.test.ts`, `dialogTurnGuards.test.ts`, плюс `tsc -p _legacy_web/tsconfig.json --noEmit` — зелёные. Docs sync: `assistant/spec.md`, `assistant/history.md`, `00_index/CHANGELOG.md`.
