## 1. Назначение

Модуль **communicator** — клиентский слой диалога с ассистентом: UI чата (голос и текст), локальное состояние сессии, разбор SSE-ответа сервера, dev-export диалога и карточка предложенной практики. Серверные промпты, structured Gemini request, оркестратор и выбор практики описаны в `docs/02_modules/assistant/`; здесь зафиксировано только то, что выполняет приложение Expo.

## 2. Публичный контракт

### UI

- `**Communicator**` (`modules/communicator/ui/Communicator.tsx`)  
`export function Communicator(props: CommunicatorProps): JSX.Element`
  Основные пропсы:
  - `systemPrompt: string` — передаётся на сервер внутри `triggerMeta` вместе с остальными метаданными.
  - `useCase?: DialogueUseCase` — по умолчанию `"daily_dialog"`; для других сценариев см. `services/communicator-client.ts`.
  - `entrySource?: DialogueEntrySource` — по умолчанию `"home"`.
  - `startFreshSession?: boolean` — если `true`, компонент при первом boot этого mount не делает session-resume по `entrySource`, очищает local session-cache для этого ключа и стартует новую беседу с пустой лентой. Повторные rerender внутри того же открытого чата **не должны** снова сбрасывать ленту. Используется Home-кнопкой `Что делать?` и day-modal flow (`plan` / `add` / `summary`), чтобы вкладка `День` всегда открывала отдельный чистый диалог под текущий режим, а не resume старой day-сессии. На вкладке `День` родитель (`app/(tabs)/day.tsx`) держит **замороженный** `AssistantSession` (рабочая дата, `dayActions`, `dayPractices`, health) и стабильный `key` на время одного открытого модального чата; фоновый `refresh()` плана дня во время открытого ассистента не выполняется, чтобы смена `summaryTargetLocalDate` после подытоживания не перемонтировала `Communicator` и не сбрасывала ленту.
  - `triggerMeta?: Record<string, unknown>` — произвольный контекст для бэкенда (на главном экране туда кладут поля прогноза дня).
  - `conversationId?: string | null` — начальное значение; после ответа может обновиться из события `complete`.
  - `history?: CommunicatorHistoryMessage[]`, `memoryWindow?: number` — начальная история и ограничение числа последних пар для синхронизации/отображения (`sliceHistoryForWindow`).
  - `autoSendInitialMessage?: string` — один раз после локального восстановления/инициализации сессии отправляет текст как пользователя (см. ref-guard в коде).
  - `onMessage?: (msg: CommunicatorHistoryMessage) => void` — колбэк на каждый коммит сообщения в ленту. Home (`app/(tabs)/index.tsx`, `assistantMessageTriggersDayPrefetch`) использует его для **pre-warm** вкладки «День»: при assistant-ходе с `planningPersistence.inserted/updated/summarized`, `recommendationCorrected` или `turnMode=final_without_practice` запускается `loadDayPlan()` → `storePrefetchedDayPlan()` (зеркало `day.tsx` `handleAssistantMessage`), чтобы к закрытию диалога контент «Дня» уже был в памяти.
  - `onPracticeOffered?: (practice: PracticeSummary) => void | Promise<void>` — срабатывает сразу при появлении assistant `practicePicked` в `complete` / hydration, ещё до нажатия пользователем `Начать`; внешняя поверхность может сохранить pending practice-card (например в `day_practice_offers`).
  - `onPracticeLaunchStart?: () => void` — сразу при нажатии «Начать практику», **до** `launchPractice` / `router.push`; Home/Day заменяют чат на **`AssistantPracticeHandoffCover`** внутри Modal.
  - `onPracticeLaunchAbort?: () => void` — если `launchPractice` вернул `false`, откат handoff-cover (overlay остаётся открытым).
  - `onPracticePicked?: (practice: PracticePicked) => void | Promise<void>` — вызывается после успешного `launchPractice(...)` и сигнала готовности экрана практики (`signalAssistantPracticeScreenMounted`); модальные поверхности используют его как side-effect закрытия оверлея/refresh без промежуточного flash вкладки под ним.
  - `onRequestClose?: () => void` — колбэк явного выхода из диалога; используется, когда финальный assistant-turn завершает разговор без карточки практики и UI показывает кнопку `Выйти из диалога` прямо под последним сообщением.
  - `onError`, `onAbort`, `onStateChange`, `onEmotionSegment` — см. `CommunicatorProps` в коде.
  - `locale`, `initialMode`, `mode` — локаль строк (`getCommunicatorStrings(locale)`) и политика VOICE/TXT (часть режимов завязана на флаг `COMMUNICATOR_TEXT_MODE_ENABLED` в `modules/ui/testMode`). Хост-экраны (Home, Day, Breath) передают `locale` из **`useAppLocale()`** (`@/modules/i18n`), а не `profile.locale` и не хардкод `"ru"`.
- Локальной карточки практики в `communicator` больше нет: используется общий `**modules/practices/ui/PracticeCard.tsx**` через адаптацию `PracticePicked → PracticeSummary`.

### Inline practice interpretation (`POST /api/communicator/v2/practice-interpretation`)

- Маршрут принимает Bearer-authenticated JSON `{ outcome, subjectiveMood?, responseLocale? }`, где `outcome` совместим с `outcomeToCommunicatorPayload(...)` из `modules/breath/core/practice-io.ts`; для breath results клиент может дополнительно вложить `seriesInsights` (сжатые start/mid/end + min/max summaries по pulse / coherence / RMSSD / stress / RSA), не меняя persist-контракт `practice_sessions.metrics`.
- Сервер выбирает язык через `resolveResponseLocale(user.locale, body.responseLocale)`, вызывает `STANDARD`-модель (`getModelByHint("standard")` + `generateGeminiText`) и возвращает короткий текст `{ text, modelUsed, responseLocale }`.
- Клиентский helper: `services/breathPracticeInterpretation.ts`. Он не открывает `Communicator`, а используется локально внутри results-modal дыхательной практики. Таймаут клиента (**120s**) и сбои сети нормализуются в **`AppUserError`** (`timeout` / `network` / `auth`) — UI показывает только локализованный `resultsInterpretationError`, без сырого RU/EN `Error.message`. После client timeout — **один** тихий повтор запроса. `CoherenceBreathScreen` показывает кнопку `Интерпретация` только когда сессия действительно дала биометрические метрики; camera guidance-only results и BLE-сессии без пригодной биометрии вместо этого остаются в локальном results UI без LLM-запроса.

### Локализация (`modules/communicator/i18n/communicator.ts`)

- `getCommunicatorStrings(locale)`, тип `CommunicatorStrings` (в т.ч. **`voiceUserBubblePending`** — строка для доступности плейсхолдера голоса; **`holdToRecordAccessibilityLabel`** — «Нажмите или удерживайте для записи» / «Tap or hold to record»; **`voiceTranscribeFailedBubble`** — нейтральный текст в пузыре при сбое расшифровки, без обещания кнопки inside-bubble; **`transcriptionReviewHint(confidence?)`** — locale-native подсказка на экране правки транскрипта для всех 8 локалей; **`emptyAssistantReplyFallback`** / **`practiceCard.closedWithoutPractice`** — вместо хардкода RU в `Communicator.tsx`).

### Голосовой пайплайн (`modules/communicator/core/voiceTurnPipeline.ts`)

- `transcribeVoiceRecording({ uri, language?, signal? })` — до **`VOICE_TRANSCRIBE_MAX_ATTEMPTS`** (3) попыток по **`VOICE_TRANSCRIBE_ATTEMPT_MS`** (10 с) каждая; внутри вызывает `transcribeCommunicatorAudio` с `{ useNetworkRetry: false }`. В обычном режиме `Communicator.tsx` даёт STT language-hint из **`getTranscribeLocale()`** (активная/profile locale), и reply language остаётся profile-driven. При `EXPO_PUBLIC_I18N_TEST_MODE` язык-hint, наоборот, опускается, Whisper авто-определяет речь, и voice-turn может временно отправиться с override `inputLocale` + `responseLocale`, равным детектированному поддержанному языку, не меняя системную локаль UI.
- `deleteVoiceRecordingFile(uri)`, тип **`RetainedVoiceRecording`** (URI, длительность, опционально `transcribedText`, `pendingVoiceId`).

### Voice turn locale (`modules/communicator/core/voiceTurnLocale.ts`)

- **`resolveVoiceTurnLocales({ detectedLanguage?, responseLocale, testMode })`** — pure helper: coerces Whisper `detectedLanguage` через `asContentLocale`; вне test mode возвращает profile `responseLocale`, в test mode при поддержанном detected locale временно подменяет `responseLocale` на язык речи для текущего voice-turn.

### Ошибки сети и UX (`services/userFacingErrors.ts`, `modules/ui/i18n/userErrors.ts`)

- Транзиентные `Network request failed` в API-клиентах: до **2** скрытых повторов (`withTransientNetworkRetry`), затем Alert с текстом из **`getUserErrorStrings(locale)`** (ru/en) — без URL в UI.
- `AbortError` / `Aborted` в communicator-контуре больше не показываются пользователю как сырой generic-текст. Они нормализуются к retryable timeout-copy, логируются через `console.warn`, а не как красный generic `console.error`.
- Классификация **`timeout`** (сообщения transcribe/стрима с `timed out` и т.п.) → **`timeoutTitle`** / **`timeoutMessage`**, retryable.
- **`Communicator`**: кнопки **Повторить** / **Закрыть** при сетевых и 503/429 ошибках; повтор вызывает последний `initiateDialog` или `submitDialogTurn` без дублирования пузыря пользователя.
- Технические детали — только в `console` через `logErrorForDevelopers`.

### Очистка видимого текста ассистента (`modules/communicator/core/dialogTextCleanup.ts`)

- **`stripDialogScaffoldMarkdown(text): string`** — экспорт; зеркалит серверный одноимённый helper в `_legacy_web/app/api/_utils/markers.ts`.
- **`stripStreamingMarkers`** в `Communicator.tsx` — локальный regex `MARKER_RE` вырезает из видимого стрима `[STATE_PROPOSAL|PRACTICE_PICK|CORRECT_RECOMMENDATION|PLANNED_EVENT|SUMMARIZE_EVENT|MATRIX_CELLS:…]` и bare sentinels `[PLAN_TOMORROW]` / `[PRACTICE_DECLINED]` до применения `stripDialogScaffoldMarkdown`.

### Гидрация `complete` из session sync (`modules/communicator/core/dialogTurnHydration.ts`)

- **`isFinalLikeTurnMode(turnMode)`** — `fast_track_final`, `final_recommendation`, `final_recommendation_with_validation_warning`, `forced_final`, `practice_repick`, `final_without_practice` (и legacy `practice_declined` для старых session-meta).
- **`turnModeCarriesPractice(turnMode)`** — финалы, для которых клиент обязан ждать `practicePicked`: `fast_track_final`, `final_recommendation`, `final_recommendation_with_validation_warning`, `forced_final`, `practice_repick`.
- **`needsAssistantTurnHydration(complete)`** — `true`, если `complete` отсутствует, в нём нет `turnMode` / `modelTier` / `modelUsed` / `iteration`, либо card-carrying режим пришёл без `practicePicked`.
- **`sessionAssistantMatchesTurn({ currentText, currentMessageId?, sessionText, sessionMessageId? })`** — совпадение по `messageId` или по trimmed-тексту (пустой `currentText` считается совпадающим).
- При session hydration в `Communicator.tsx`: если server `content` пустой, но `turnMode` финальный и локальный `currentText` непуст, гидрация считается успешной. Для card-carrying финалов дополнительно требуется `meta.practicePicked`; для `final_without_practice` это поле не нужно.
- **`mergeCompleteWithSession({ complete, sessionMeta, sessionText, sessionMessageId? })`** → `DialogCompleteEvent` — дополняет пропущенные поля из `meta` последнего assistant-сообщения сессии.
- Тип **`SessionAssistantTurnMeta`** — подмножество полей `complete` / `meta` для merge (в т.ч. `planningPersistence`, `relatedEventIds`, `skippedPlannedEvents`, `matrixCells`).

`Communicator.tsx` вызывает эти helpers в `commitAssistantTurn` на success-path (когда текст есть, а `complete` неполон) и при восстановлении после обрыва SSE.

### Слияние local/server снимка для dev-export (`modules/communicator/core/dialogExportMerge.ts`)

- **`mergeExportMessageMeta(localMeta, syncedMeta)`** — объединяет `meta` assistant-хода; приоритет synced для `planningPersistence`, `relatedEventIds`, `matrixCells`, `skippedPlannedEvents`, а также `insightMetrics`, `validation`, `practicePicked`, `targetChakra`, `recommendationCorrected`, `debug`.
- **`mergeExportMessages({ localMessages, syncedMessages })`** — сопоставляет local и server сообщения по **порядковому индексу роли** (ordinal внутри `user` / `assistant`), в т.ч. когда server `content` пустой; server `id`, `createdAt`, `rawMeta` подмешиваются к local тексту.
- **`reconcileExportPlanningPersistence(messages, dialogStateAfter)`** — если ни один assistant-ход не имеет `planning_persistence.inserted`, последней assistant-строке подставляет `planning_created_in_this_conversation` из `dialog_state_after`.
- Типы **`ExportMessageSnapshot`**, **`ExportMessageMeta`**, **`PlanningPersistenceExport`** — контракт merge/export.

`Communicator.tsx` вызывает merge перед dev-export JSON; `dialogExportMerge.test.ts` покрывает merge при пустом server `content` и reconcile fallback.

### Поток чата без прямого импорта `sendDialogMessage` в UI

- `**useCommunicatorStream()**` — обёртка состояния стрима (thinking/typing, текст, решение оркестратора); без колбэка `onError`. При исключении после частичного SSE возвращает salvaged-чанк, если уже есть `complete` или непустой агрегат текста; иначе пробрасывает ошибку.
- `**runCommunicatorStream**` (`modules/communicator/api/communicator-stream.ts`) — агрегирует колбэки `sendDialogMessage` в чанки для UI.

### Транспорт (`services/communicator-client.ts`)

Экспортируемые функции и типы, с которыми работают UI и другие экраны:

- `sendDialogMessage(params: SendDialogMessageParams): Promise<SendDialogMessageResult>` — POST с телом JSON, ответ читается как **SSE**: на **web** — `fetch` + потоковое чтение `body`, на **iOS/Android** — `**XMLHttpRequest**` с инкрементальным `responseText` (иначе RN часто отдаёт весь поток одним куском в конце). JSON-ошибки с object-valued `error/message/details` сериализуются в читаемый текст, чтобы dev LogBox не показывал `[object Object]`. `DialogueEntrySource` включает `"day"` для модального ассистента вкладки «День»; этот источник использует тот же daily dialog, но передаёт `triggerMeta.dayTabMode`, `workingLocalDate`, `daySummaryRequested`, `dayActions`, `dayPractices` и, при summary-ветке, временный `dayHealthContext`. После June 10 day-flow больше не опирается на один плоский `DayPlan`: overdue summary из вкладки `День` берёт `workingLocalDate = summaryTargetLocalDate` верхней overdue-секции, передаёт в `dayActions/dayPractices` агрегат всех отображённых прошлых дат, а `dayHealthContext` собирает только для целевой summary-даты. Верхняя overdue-кнопка `Подытожить` теперь отправляет `dayTabMode="plan"` и `daySummaryRequested=false`, чтобы после подытоживания прошлых действий продолжить planning/practice как Home `Что делать?`; нижняя current-day CTA `Подытожить этот день` отправляет `daySummaryRequested=true` и остаётся summary-only. Day modal во всех режимах (`plan` / `add` / `summary`) стартует assistant-first через обычный `initiateDialog`. Home может передавать `workingLocalDate` + `dayPractices` + начальный yoga-only `dayHealthContext` snapshot при overdue auto-summary с главной (не только при `daySummaryRequested` с вкладки «День») — **без** второго native Health query: единственный `startSummarizingHealthCollection` владеет `Communicator`. `Communicator` бутстрапит Health в `useLayoutEffect` при `daySummaryRequested` / parent `dayHealthContext` / первом ответе с веткой `summarizing` (не на bare `workingLocalDate` у Day planning). Модалка summary открывается **сразу**; native Apple/Google Health грузится в фоне с начала summarizing. Каждый POST передаёт `getSnapshot()` без soft-wait/`await whenReady()`; к FINAL за время ответов пользователя snapshot обычно уже с метриками. `health_debug` в meta/export включает `collectionTrace` (startedAt/finishedAt/durationMs, range, per-query method/ok/parsed/rawPreview/error). Для summary-ветки backend ведёт пользователя по одному due-событию за ход. `Communicator` также отдаёт `onPracticeOffered(PracticeSummary)` при появлении assistant `practicePicked`. Если финальный ход завершает разговор **без** карточки, компонент показывает под последним сообщением явную кнопку выхода и перед закрытием делает best-effort `reconcileDialogPlans({ force: true })` (серверный endpoint — совместимый no-op с FSM).
- `reconcileDialogPlans({ conversationId, force? })` — отдельный POST на `/api/ai/dialog/reconcile-plans`; вызывается debounce-таймером после паузы в диалоге. **С июня 2026 серверный «мозг» — явный FSM (`assistant/spec.md`), который пишет `planned_events`/`daily_matrices` синхронно на финале ветки**, поэтому отложенная reconcile-очередь больше не наполняется, и этот вызов остаётся совместимым no-op/catch-up; клиентский код не менялся.
- `fetchDialogSession({ useCase, entrySource, scenarioId?, conversationId?, debugExport?, signal? })` — GET синхронизации сессии; при монтировании `Communicator` вызывается **вместе** с локальным cache для проверки `reset` и очистки устаревшего cache; при восстановлении ленты приоритет у local cache с совпадающим `conversationId`, иначе — сообщения из GET, иначе — seed из пропсов. На mount `conversationId` в GET передаётся **только** из пропа `Communicator` (id из local cache в query не подмешивается). Дополнительно — гидрация `complete`, dev-export и debug-снимок; **не** канонический источник текста, если valid local cache совпадает с серверной беседой. Опционально `debugExport: true` → query `debugExport=1`; теперь `dialogStateAfter` приходит по такому запросу всегда, а не только при server test/debug mode, поэтому JSON-export может показывать закрытые summarized rows и их `outcome_cells`. Если одновременно передан `conversationId`, debug-export может подтянуть и **уже закрытую** беседу: даже при пустом `messages` (они очищены на сервере) клиент получает `dialogStateAfter` и строит export по локальному тексту + серверным артефактам. Закрытая или протухшая беседа без `debugExport=1` даёт `reset: true` (см. `assistant/spec.md` GET). При ошибке «нет эндпоинта» для старых серверов возвращается пустая сессия с `reset: true`.
- `transcribeCommunicatorAudio(req, options?: { useNetworkRetry?: boolean })` — POST на `/api/communicator/v2/transcribe` (тело `{ audio: { mimeType, base64 }, language? }`); таймаут одной попытки **12 с** (`TRANSCRIBE_TIMEOUT_MS`). По умолчанию — `withTransientNetworkRetry`; голосовой пайплайн передаёт `useNetworkRetry: false` (повторы на уровне `transcribeVoiceRecording`).
- `extractCalibration(req)` — используется экраном калибровки, не `Communicator.tsx`.

Типы: `DialogueUseCase`, `DialogueEntrySource`, `PracticePicked`, `OrchestratorDecision`, `DialogCompleteEvent`, `DialogTurnArtifactsEvent`, `SendDialogMessageParams` (колбэк `onTurnArtifacts`), `SendDialogMessageResult` (в т.ч. опциональный `streamError?: string` при SSE `error`), `DialogTurnHistoryItem`, и др. — см. файл. `**buildClientTurnHistory**` / `DIALOG_TURN_HISTORY_LIMIT` (40) собирают `turnHistory` из локальной ленты перед POST; для assistant-turn туда подмешивается минимальный `meta`: `practicePicked` (если карточка уже показана), плюс `branches` / `dialog_branches` (если ветка известна из `complete` или session-meta), чтобы серверный FSM/route при lean storage видел контекст карточки и мог через `collectPlanningBranchUserHistory` восстановить user-turns planning-ветки.

`**PracticePicked**` — `Partial<PracticeRecommendation> & Pick<PracticeRecommendation, "id">` (реэкспорт контракта каталога практик).

`**DialogCompleteEvent**` / `**DialogTurnArtifactsEvent**` — SSE **`complete`** (до `persistDialogArtifacts`) несёт UI-поля: `fullText`, `turnMode`, `practicePicked`, `branches`, `phaseTime`, `targetChakra`, `validation`, `insightMetrics`, `recommendationCorrected`, `debugExport`, `conversationId` и др.; **`messageId`**, **`planningPersistence`**, `relatedEventIds`, `skippedPlannedEvents`, `matrixCells` приходят в **`turn_artifacts`** после persist и сливаются в агрегат `state.complete` в `handleSseEvent`. С FSM (июнь 2026) сервер пишет planning/summary синхронно на финале ветки (`dialogBrainPersistence.ts`), поэтому `planningPersistence` больше не наполняет отложенные `queued`/`queued_summaries`; debounce `reconcileDialogPlans` остаётся на клиенте как совместимый flush к no-op endpoint. Клиент сохраняет объединённые поля в `messages.meta` и dev-export (см. `assistant/spec.md`).

## 3. Внутренняя архитектура

1. **Жизненный цикл сессии** — `Communicator` монтируется → параллельно загружает current-day session-cache (`services/dialogSessionCache.ts`) по ключу `userId + useCase + entrySource` и вызывает `fetchDialogSession({ signal })` без `conversationId` из cache (`AbortController` при unmount). Если сервер сообщает `reset` или нет `conversationId`, локальный cache очищается, `initiateFiredRef` сбрасывается, лента — seed из пропсов. Иначе при совпадении `conversationId` cache↔server и непустом cache восстанавливается локальная лента; иначе — сообщения из GET (если есть); иначе — seed из пропсов. Если передан `startFreshSession`, этот resume-path пропускается: компонент сначала очищает local cache для `entrySource`, выставляет пустую ленту/`conversationId = null` и стартует новый диалог с нуля. Закрытый диалог (`shouldClose`) удаляется из cache при sync. Dev-сброс дня на главном (`postDevDayContentReset`, scope по тарифу) перед refresh вызывает `clearHomeDailyDialogCache(authUser.id)` — очистка SecureStore/localStorage для `daily_dialog` + `entrySource: home`. `fetchDialogSession` дополнительно — гидрация `complete`, dev-export. Отдельно после каждого изменения ленты `Communicator` запускает debounce-таймер (`~10 мин`, в client test mode укорочен до ~1.5 c) и по нему вызывает `reconcileDialogPlans(...)`; новый пользовательский или assistant-turn сбрасывает таймер. С FSM сервер уже канонизировал planning/summary на финале ветки, поэтому этот вызов — совместимый no-op; клиентский debounce/force-flush сохранён для обратной совместимости. При закрытии чата, кнопке `Выйти из диалога` или запуске практики с карточки компонент по-прежнему делает best-effort force reconcile до close / unmount / launch.
2. **Голос** — … **Жест микрофона** (`core/micGesture.ts`, `resolveMicPressIn` / `resolveMicPressOut`): два режима — **`tap_toggle`** (тап → запись, повторный тап → стоп/отправка) и **`hold`** (удержание → запись, отпускание → стоп). Визуал кнопки — `MicRecordButton` (белый глиф из `assets/icons/microphone.svg` на круге `#0d74f1`; при recording/arming диаметр +20% и soft aura по metering); busy/cancel — `MicCancelButton` (белый `cancel.svg` на круге `#a8a8a8`, **inert** — не abort’ит стрим). Mic доступен после SSE/`pendingRevealGoal`, не дожидаясь полного `resetChatStream`. Unmount снимает `Audio.Recording` и сбрасывает audio mode (иначе iOS держит зелёный mic и следующий open падает на prepare). На **Android** mic — `Pressable` из `react-native-gesture-handler` (`GestureHandlerRootView` в `app/_layout.tsx` и **внутри** `AssistantModalShell` — Modal вне app root, иначе GH не получает тачи); RN `Pressable` на Samsung/One UI + Fabric часто сразу шлёт `onPressOut` после `onPressIn` и ломает hold. На **iOS** — RN `Pressable`. Пока палец на кнопке (`micFingerDownRef`), Pressable **не** remount-ится (`micPressResetKey` / `bumpMicPressReset` no-op) — иначе iOS теряет `onPressOut` и hold-to-talk «залипает». При старте нативного рекордера режим выставляется через `captureModeWhenRecordingStarts(fingerDown, pendingMode)`. При сбое расшифровки пузырь остаётся с нейтральным текстом `voiceTranscribeFailedBubble`; Alert **Повторить** повторно отправляет тот же файл (в т.ч. при Groq **`invalid media file`** через `isInvalidTranscriptionMediaError`). После успешного `commitAssistantTurn` временный файл удаляется (`deleteVoiceRecordingFile`). При сбое диалога после расшифровки **Повторить** вызывает только `submitDialogTurn` с сохранённым текстом. Запись отправляется только если длительность **≥ `MIN_VOICE_MS`** (450) и файл не слишком мал (`isVoiceRecordingFileTooSmall`, порог **`MIN_VOICE_FILE_BYTES` = 256**). Сразу в `processVoiceFromUri` в `messages` добавляется строка пользователя с `**meta.voiceTranscribing: true**` и пустым `content`: `**UserBubble**` показывает только `**ActivityIndicator**` (для доступности — `**voiceUserBubblePending**` без видимого текста); после успешной расшифровки та же строка заменяется текстом. Если расшифровка сорвалась, сообщение помечается `**meta.voiceTranscribeFailed: true**`, а `buildClientTurnHistory()` исключает и этот failed-bubble, и живой transcribing-placeholder из `turnHistory`, чтобы client-side ошибка не уходила на сервер как будто это реальная реплика пользователя. `**scrollToIndex**` к этому пузырю с `**viewPosition ≈ 0.24**` срабатывает при **инкременте** `voiceAnchorTick` (плейсхолдер и финальный текст); вызов откладывается до измерения layout у `**FlashList**` (двойной `requestAnimationFrame` + короткая задержка) и **повторяется** по `Promise` при отказе (без `scrollToEnd` в `catch`); эффект **не** блокируется `streamBusy`. Повтор на каждый чанк стрима не помечается успешным (`lastVoiceLayoutScrollTickRef` только после успешного скролла). Пока `voiceUserAnchorMessageIdRef` задан, `**onContentSizeChange**` не вызывает `scrollToEnd`, чтобы «догон низа» не перебивал якорь. При `**streamBusy**` авто-`**scrollToIndex**` к строке стрима ассистента **не** вызывается (`suppressStreamAnchorScroll`), чтобы окно не уезжало при длинном ответе; флаг **сбрасывается**, когда `streamBusy` переходит из **`true`** в **`false`**, чтобы следующий стрим снова мог якориться к пузырю стрима. `**stripLegacyPracticeCardReason**` в `Communicator.tsx` обрезает устаревшие хвосты в `**practicePicked.reason**` (в т.ч. из сохранённой сессии). После расшифровки строки, совпадающие с известными **галлюцинациями Whisper** на тишине (например субтитровые шаблоны), отбрасываются в `transcriptionGuard.ts` — плейсхолдер **удаляется**, в чат текст не попадает. При низкой уверенности распознавания плейсхолдер снимается и показывается экран правки текста (`pendingTranscript` + `transcriptionReviewHint`; detected locale сохраняется для resend).
3. **Стрим ответа** — `runCommunicatorStream` → `sendDialogMessage` парсит SSE-блоки (`parseSseBlock`) и для событий `orchestrator_decision`, `chunk`, `complete`, `turn_artifacts`, `error` обновляет состояние; событие `error` завершает стрим с user-facing сообщением (сервер больше не рвёт HTTP pipe через `controller.error`). На нативных платформах чанки чаще приходят по мере генерации (**XHR** + polling `responseText`); при `xhr.onerror` после закрытия сокета клиент **финализирует** буфер и **resolve**, если уже есть `complete` или непустой `fullText` (типичный iOS/RN артефакт при успешно принятом теле). При unmount `Communicator` вызывает `abortChatStream()`, чтобы не оставлять висящий POST на сервере. Список сообщений — `**@shopify/flash-list` (`FlashList`)**; активный стрим — последняя строка данных `kind: "stream"`. Пока текста нет — в пузыре `**ActivityIndicator**`; с первого символа после `stripStreamingMarkers` + `**stripDialogScaffoldMarkdown**` (убирает `---`, **целиком** блоки `**…**` и bare internal markers вроде `[CORRECT_RECOMMENDATION]`) — `**StreamingAssistantLines**`: строки по `\n` с лёгким `**FadeIn**` (`react-native-reanimated`), последний незавершённый сегмент обновляется по мере чанков; курсор **▍** при `streamStatus === "typing"` и непустом хвосте. Финальный коммит в историю — через **`commitAssistantTurn`** (общий для `submitDialogTurn` и `initiateDialog`). **Добавление финального сообщения в `messages` и `resetChatStream()` откладываются** до совпадения stripped-текста с целевой строкой (`pendingRevealGoal`) + короткая задержка в компоненте, иначе карточка практики и финальный пузырь «съедали» бы анимацию. Этот отложенный путь включается только если агрегат стрима **`mergedText`** после trim **непуст**, ответ **не** восстановлен через session hydration, длина после strip > **14**, в **`complete` нет `practicePicked`**, и ход **не** закрывает диалог (`shouldClose !== true`); если **`practicePicked` пришёл** или финал уже terminal — коммит **сразу**. Перед отложенным коммитом **`syncDisplayText(finalText)`** выравнивает live-стрим с sanitized `complete.fullText`, иначе `stripTarget` (сырые SSE-чанки) и `revealGoal` (серверный sanitized) расходятся и flush не срабатывает; fallback timeout сокращён до **8 с** вместо старых 60 с. Очень короткие ответы (порог после strip, **14** символов) коммитятся сразу. Если `complete` отсутствует, неполон или не содержит `practicePicked` на финальном ходе, клиент делает несколько попыток `**fetchDialogSession**` (backoff ~0.7/1.4/2.6/4.2 s), сверяет последнюю assistant-реплику с локальным текстом и догидрирует `turnMode`, `modelTier`, `modelUsed`, `iteration`, `practicePicked`, `branches`, `phaseTime`, `targetChakra`, `planningPersistence`, `relatedEventIds`, `skippedPlannedEvents`, `matrixCells`, `debug`. Тот же механизм используется и после исключения стрима. При `complete` итог — `complete.fullText` (sanitized); иначе агрегат SSE после `stripStreamingMarkers` + `stripDialogScaffoldMarkdown`. Если текст всё равно не восстановился, клиент больше не показывает общий ложный пузырь `emptyAssistantReplyFallback`: после карточки практики допускается мягкий `postPracticeReplyFallback`, для terminal no-card закрытия — `strings.practiceCard.closedWithoutPractice`, а в остальных случаях ошибка поднимается в обычный retry/error UX вместо фальшивой реплики ассистента.
  **Скролл:** при старте стрима выполняется `**scrollToIndex**` к строке стрима с `viewPosition ≈ 0.3` (если **не** включён `**suppressStreamAnchorScroll**` после голосового ввода), чтобы верх пузыря оказался в верхней трети вьюпорта («статичный якорь»). Пока `streamBusy`, **автоскролл в конец при росте контента отключён** (пользователь читает без «погони» за низом). Вне стрима при росте контента и если пользователь не ушёл вверх — как раньше догон вниз через `onContentSizeChange` + `scrollToEnd`; кнопка «Scroll Down» при ручном скролле вверх.
4. **Карточка практики** — `Communicator` рендерит общий `modules/practices/ui/PracticeCard.tsx`, переводя серверный `PracticePicked` в `PracticeSummary`. Текст описания в карточке берётся из `**practicePicked.card_blurb`** (если сервер прислал валидированный model-generated blurb или fallback summary) либо из `**reason`** как legacy fallback; новый серверный контракт держит `reason` как текст связи практики с днём, а `card_blurb` как текст карточки о самой практике. Для **йоги** `overrideDurationMinutes` / `overrideChakraIndex` **не** передаются (значения каталога); для breath/meditation пользователь может переопределить duration/chakra перед запуском; **`PracticeCard`** клипит `overrideDurationMinutes` к допустимым шагам каталога (см. `assistantSelectableDurations.ts`, тот же контракт, что и сервер в `resolvePracticePublic`). Адаптеры `practiceToSummary` / `summaryToPractice` для **дыхания** round-trip'ят breath launch-поля `sensorMode`, `deviceId`, `deviceName`, `provider`, `capabilityTier`, `connectionHint`, `autoReconnect` (и legacy `usePulseSensor`) между `PracticePicked.launch.params` и `PracticeSummary.launch`, чтобы assistant/day pending-карточка и фактический `launchPractice` совпадали с выбором источника пульса в каталоге. При нажатии `Начать практику`: `onPracticeLaunchStart` → `launchPractice(..., { launchSource: 'assistant' })` (при `false` — `onPracticeLaunchAbort`); `onPracticePicked` — через `scheduleAssistantOverlayDismiss` (`modules/practices/ui/assistantPracticeOverlayDismiss.ts`) как side-effect закрытия overlay/refresh: callback срабатывает после `signalAssistantPracticeScreenMounted()` из route-обёрток практики (`useAssistantPracticeOverlayDismiss`, `launchSource=assistant`) **и** min-delay **200 ms**, либо по fallback timeout **2500 ms**. Родительский Modal (Home/Day) между launch и dismiss показывает **`AssistantPracticeHandoffCover`** вместо чата. Home `CommunicatorOverlay` держит overlay смонтированным (`communicatorMounted`) отдельно от видимости (`Modal.visible` + `animationType`: `"none"` при старте практики, `"slide"` при обычном закрытии); `onDismiss` размонтирует overlay после анимации. Если navigation не удалась, callback вызывается сразу как fallback. `practiceToSummary` запекает `practicePicked.overrides.durationMin` в pending `PracticeSummary` для дыхания/медитации (отложенная карточка на вкладке «День» показывает выбранную длительность, а не каталожный дефолт).
5. **Dev export** — при **`HARMONIZER_TEST_MODE`** показывается кнопка `Export dialog to JSON`, которая собирает `day_context` из `triggerMeta`, верхнеуровневый блок `conversation` (`conversation_id`, `use_case`, `entry_source`) и метаданные сообщений (`turnMode`, `modelTier`, `validation`, `practicePicked`, `branches`, `phaseTime`, `targetChakra`, `insightMetrics`, **`planning_persistence`**). Каноническим источником видимого текста считается **локальный current-day session-cache**, а server session sync через `fetchDialogSession({ debugExport: true })` — источник `meta` и `dialog_state_after`; **`mergeExportMessages`** сливает local текст с server `meta`/`rawMeta` по role-ordinal (пустой server `content`), затем **`reconcileExportPlanningPersistence`** подставляет `planning_created_in_this_conversation`, если на ходах нет `inserted`. Export сохраняет **весь видимый текст диалога**, даже если на сервере тексты не лежат в `messages.content`. `dialog_state_after` по debug-export теперь доступен не только в server test/debug mode, а всегда; кроме того, верхнеуровневые блоки `summary_events_applied_to_matrix` и `summary_events_closed_without_matrix` собираются из `planning_closed_recent_48h`, который backend формирует из `planned_events.status='summarized'` и поэтому продолжает показывать реальные `outcome_cells` по каждому подытоженному действию до конца текущего дня.

Готовые реплики ассистента в списке истории рендерятся `**AssistantBubble**` без служебной строки фазы оркестратора (ранее `phaseLabel` из `turnMode`).

События SSE обрабатываются в `handleSseEvent` (`services/communicator-client.ts`): `complete` → `DialogCompleteEvent`; `turn_artifacts` → merge в `state.complete` + колбэк `onTurnArtifacts`; `error` → `streamError` и reject на клиенте.

## 3.1. Хранение и сброс daily dialog

**Ключевые слова для поиска в репозитории и docs:** `dialogSessionCache`, `turnHistory`, `clearHomeDailyDialogCache`, `lean dialog storage`, `local session cache`, `profile_report_snapshots` (серверные отчёты — модуль `assistant` / `profile`).

| Слой | Что хранится | Где |
| --- | --- | --- |
| **Устройство (канон текста)** | До 40 последних сообщений ленты, `conversationId`, ключ по локальному календарному дню | `services/dialogSessionCache.ts` — SecureStore (native) / `localStorage` (web); ключ `harmonizer.dialog.session.{userId}.{useCase}.{entrySource}` |
| **POST на сервер** | Контекст ходов для LLM | `buildClientTurnHistory` → поле `turnHistory` (лимит 40); assistant-turn может нести `meta.practicePicked` и `meta.branches`/`dialog_branches`; сервер предпочитает его над пустым `messages.content` |
| **Сервер (не текст)** | `messages.meta`, `planned_events` (`planned` + текущие `summarized`), rollup `daily_matrices`, snapshot `profile_report_snapshots` | `docs/02_modules/assistant/spec.md` |
| **GET sync** | Проверка `reset`, гидрация `complete`, dev-export | `fetchDialogSession`; на mount **без** `conversationId` из local cache (только проп `Communicator`) |

**Восстановление после перезапуска приложения:** local cache (если тот же день и `conversationId` совпал с сервером) → иначе сообщения GET → иначе seed из пропсов. Серверный `reset: true` или отсутствие `conversationId` **очищает** local cache.

**Сброс диалога:**

1. **Кнопка «Обновить»** на главном (`HARMONIZER_TEST_MODE`, `app/(tabs)/index.tsx`) — `clearHomeDailyDialogCache(authUser.id)` **до** `postDevDayContentReset("both")` (`POST /api/ai/dev-day-reset` с `resetScope: "both"`: чистит и персональные кэши дня — `scenario_cache` `morning_recommendation`/`global_content_i18n`, `user_daily_forecasts`, закрытие open `home`-бесед — и shared `global_daily_content` + regen), затем `refresh({forceRefresh:true})` регенерирует рекомендацию активного тарифа на текущую дату (free — глобальная, paid — по наталу), и `assistantRemountKey++` для чистого `Communicator`.
2. **Закрытый диалог** (`shouldClose` в meta) — `clearDialogSessionCache` при sync.
3. **Протухшая / закрытая беседа** — GET без `debugExport` → `reset: true` → клиент очищает cache (см. `assistant/spec.md` GET).

Из `**complete**` (`DialogCompleteEvent`) в UI и метаданные сообщения попадают как минимум:

- `fullText`, `shouldClose`, `modelUsed`, `modelTier`, `turnMode`, `iteration`, `readyMarkerTriggered`, `validation`, `insightMetrics`
- `branches`, `phaseTime`, `targetChakra` — дополнительный контекст ветвления/фазы, который клиент сохраняет в `meta` и dev-export
- `planningPersistence`, `relatedEventIds`, `skippedPlannedEvents`, `matrixCells` → `meta` и dev-export (`planning_persistence`, `related_event_ids`, `matrix_cells`, `skipped_planned_events`)
- `debugExport` → `meta.debug` в истории (при серверном test/debug режиме)
- `messageId`, `conversationId` — обновление id сообщения и активной беседы
- `practicePicked` → `meta.practicePicked` и общий `PracticeCard`; для **дыхания/медитации** в DTO может быть `**overrides: { durationMin, chakraIndex }**` (`durationMin` после приоритета истории при `confident` и клипа на сервере; см. `assistant/spec.md`); для **йоги** сервер `**overrides`** не присылает — `Communicator` не прокидывает override-пропсы в `PracticeCard`. Опционально `markerIdResolved: false` (если model-generated id не найден в каталоге). Поле `**card_blurb**` — валидированный model-generated текст карточки; `**reason**` остаётся эффективным текстом карточки для UI и legacy-кэша.
- `recommendationCorrected` → `meta.recommendationCorrected`

Поля `**chunk**`: JSON с `text` и опционально `modelUsed`.
