## 1. Назначение

Модуль описывает **продуктовый контур дневного прогноза на главном экране**: загрузка и кэширование данных дня, ветвление free vs персональный прогноз, обогащение текстами и связь UI (важность, планета дня, окна, чакра) с остальным приложением. Числовой движок активации, важности и окон живёт в пакете `modules/daily-engine` и на сервере (Next.js и Edge); этот spec фиксирует **контракт потока данных и интеграций**, а не пересказ формул.

## 2. Публичный контракт

### Клиентские типы (реэкспорт из `modules/daily-engine`)

- `DailyEngineInput` — вход движка: `natalProfile`, `calibration | null`, `forecastDate`, `userLocation`, `recentPlanetsOfDay`.
- `DailyForecast` — результат: `date`, `importance`, `activation`, `rankedPlanets`, `planetOfTheDay`, `isAlternativeChoice`, `alternativeReasonText?`, `todayPlanetState`, `windowsOfOpportunity`, `transitChart`, `computedAt`, `cacheValidUntil`, опционально `recommendationShortText`, `recommendationLongText`, `slogan`, `mathLevel`, `isGlobal?`. Для `windowsOfOpportunity.exactAspect` контракт включает `time`, `aspectType`, `toNatalPlanet`, `transitPlanet`. На уровне БД строка `user_daily_forecasts` теперь дополнительно хранит `day_target_chakra`, `day_target_reason`, `day_target_fixed_at`, которые фиксируются сервером daily dialog на локальный день.
- Вспомогательные типы: `Planet`, `TodayTone`, `CalibrationLike`, `TransitChart`, и др. из `modules/daily-engine/core/types.ts`.
- Суточная кривая высоты планеты (клиент/UI): `planetAltitudeAt`, `samplePlanetAltitudeForDay`, `interpolateDiurnalAltitude`, `dayFractionFromIso`, `computeDiurnalWindowTimes`, тип `DiurnalAltitudeSample` — `modules/daily-engine/planetDiurnalCurve.ts`, реэкспорт из `modules/daily-engine/index.ts`; восход/кульминация в `freeWindows.ts`, `AstronomiaTransitProvider` (`ephemeris.ts`) и маркеры на карточке home — через `computeDiurnalWindowTimes` (та же дискретизация суточной кривой, по умолчанию 96 шагов/сутки, что и график).

### Хук и состояние главного экрана

- `useDayContent(options?)` → `UseDayContentResult` (`modules/home/useDayContent.ts`):
  - `forecast: DailyForecast | null`, `accessMode`, `modelUsed`, `source` (`"cache" | "computed" | "global"`), `status`, `loading`, `error`, **`homeTextsLoading`** (LLM-слой slogan/recommendation/math ещё догружается), **`locationIssue: LocationAcquireFailureReason | null`** (причина сбоя авто-GPS; см. `modules/location/acquireAndPersistUserCoordinates.ts`), **`userLocation: DayContentUserLocation | null`** (`{ lat, lng, timezone }` из профиля при наличии координат), `refresh(opts?)`. Экспорт типа **`DayContentUserLocation`**. Опции **`refresh`** типизированы экспортом **`DayContentRefreshOptions`**: `forceRefresh?`, **`localeChange?`** (смена языка — фоновый refresh без blocking splash), `accessModeOverride?`, `accessTierOverride?`, **`blockingReload?`** (при `true` — стартовый оверлей до готовности дня после смены натала с другого экрана; см. `services/homeDayContentReloadRequest.ts` + **`useFocusEffect`** на главном в `app/(tabs)/index.tsx`). При смене локали хук подписан на **`subscribeAppLocale`**: сразу сбрасывает locale-specific LLM-поля через **`stripHomeLlmTexts`**, инвалидирует ключи monologue/hydration и вызывает `refresh({ localeChange: true })` без тотальной очистки дневного кэша. Если locale-refresh не удался, home сохраняет уже показанный structural forecast на экране и откатывается к локализованным deterministic fallback-текстам, вместо перехода в красный `status="error"`. **`scopeKey`** локального кэша включает активную локаль (`natalScope:locale` / `global:locale`); monologue вызывается с `responseLocale`.
  - **`stripHomeLlmTexts(forecast)`** (`modules/home/stripHomeLlmTexts.ts`) — обнуляет `slogan`, `recommendationShortText`, `recommendationLongText`, `mathLevel` перед перезагрузкой locale-specific copy.
  - **`NatalBirthDataModal`** (`modules/home/ui/NatalBirthDataModal.tsx`): ввод даты **`YYYY-MM-DD`** и времени **`HH:MM`**; опционально **`initialDate` / `initialTime`**; при сабмите — **`timeMode: "precise"`**, **`location`** = экспорт **`NATAL_BRIDGE_DEFAULT_LOCATION`** (M1: Москва, `Europe/Moscow`).
  - Локальный календарный день: `Intl` + `forecastDate` в IANA-зоне из профиля/геолокации.
  - Free: `fetchGlobalContent` + URL из `getAiGlobalContentUrl()`; premium/trial: `fetchDailyForecast` + `getDailyForecastUrl()` (Vercel `/api/astro/daily-forecast` или Supabase Function — определяется `communicatorConfig`).
  - Перед первым `refresh()` главный экран (`app/(tabs)/index.tsx`) для персонального режима ждёт готовность **birth-fields из `useAuth().profile`** (`birth_date` как признак наличия персональных данных), а `fetchActiveNatalProfileCached(profile.id, { expectedBirthFingerprint })` использует только для дополнительного UI (`ModalMathLevel` → карта); fingerprint собирается из текущих `users.birth_*`. Поэтому сбой клиентского fetch `user_natal_charts` не должен переводить Home в `need_birth_data`. После успешного `createNatalProfile` на Home: если `refresh({ forceRefresh: true })` падает, UI показывает partial-success alert (birth-data сохранены, прогноз догружается) вместо полного отката.
  - Персональный режим больше не держит первый рендер до полной LLM-генерации: если базовый `DailyForecast` валиден, home может открыться сразу. На обычной загрузке **`POST /api/astro/daily-forecast`** подмешивает готовый `morning_recommendation` из `scenario_cache` (cron pre-warm) в `forecastPayload`; клиент показывает его в первом paint без deterministic fallback-flash. Если cache ещё пуст (cold user / cron miss), карточка показывает **`recommendation.loading`**, а фоновый `callMonologue("morning_recommendation")` догружает тексты (cache hit → без LLM). `forceRefresh` / locale-change по-прежнему могут форсировать regen через `ensureMorningRecommendation` на сервере или monologue на клиенте.
  - **`DailyRecommendationCard`**: пока LLM-слой догружается после cache-miss, карточка показывает **`recommendation.loading`**, а не deterministic fallback «Сегодня держите фокус…»; fallback остаётся только при ошибке/таймауте hydration. При cron hit тексты приходят уже в первом `daily-forecast` ответе.
  - Цепочка explainer-модалок на Home (`DailyRecommendationCard` → `ModalLongExplanation` → `ModalMathLevel` → `ModalAstroChart`) живёт в **одном** RN `Modal` (`HomeExplainerLevel`: `long` | `math` | `chart`). Первый уровень (`Подробнее`) всплывает native `animationType="slide"`; math и chart — **`SlideUpModalLayer`** поверх статичного предыдущего слоя (тот же slide-up, ~320 ms). `Закрыть` на любом уровне сбрасывает stack в `none` → один dismiss на главную, без каскада через промежуточные экраны. Free-path chart — **transit-only**; paid-path — natal+transit с домами только при `precisionMode="precise"`. Видимые recommendation-тексты проходят через **`normalizeRecommendationText`** (server + client display).

### Сервисы транспорта и кэша

- `fetchDailyForecast(req: DailyForecastRequest): Promise<DailyForecastResult>` (`services/dailyForecastClient.ts`) — POST с JWT; тело: `forecastDate?`, `userLocation`, `recentPlanetsOfDay?`, `forceRefresh?`, **`responseLocale?`**; нормализация snake_case ↔ camelCase. Серверный `forecastPayload` для paid-path теперь может сразу включать cron/monologue-тексты (`slogan`, `recommendationShortText`, `recommendationLongText`, `mathLevel`) без второго HTTP-запроса.
- **Устойчивость free-пути к сбою LLM/крона:** free-экран открывается даже когда cron не прогрел `global_daily_content` и Gemini недоступна. `ensureGlobalDailyContentRow` (сервер) считает структурный прогноз + `math_level` детерминированно и **всегда** записывает строку: при ошибке Gemini — с fallback-текстами и `llm_model = null` (не бросает; `globalContentNeedsRefresh` остаётся истинным → тексты сами до-генерируются). `POST /api/ai/global-content` отдаёт пригодную строку немедленно; устаревание (в т.ч. fallback-строка с `llm_model = null`) догоняет **блокирующий** `await ensureGlobalDailyContentRow` (Vercel держит функцию живой, пока handler awaits — fire-and-forget здесь умирало после ответа), `export const maxDuration = 120` даёт запас над ~90s цепочкой DeepSeek→Gemini; block-synth (`writeStructuralGlobalRow`, без LLM) — только когда пригодной строки нет (safety net + concurrent-dedup); строка прошлого дня — последний fallback. Клиент рендерит такую заглушку через `isFreeDayContentRenderable` и НЕ кэширует её (см. выше). `morning_recommendation` на клиенте (`callMonologue`) имеет клиентский таймаут **`MONOLOGUE_TIMEOUT_MS` = 105s**, чтобы paid-хидрация не висела вечно на «Загружаю текст рекомендации на этот день», а откатывалась к детерминированному fallback.
- **Cron pre-warm LLM router (shared):** `precompute-global-recommendations` и `precompute-daily-forecasts` (Supabase Edge, Deno) генерируют тексты через общий `supabase/functions/_shared/llm.ts` `generateGeminiJson({ prompt, modelHint, temperature, maxOutputTokens, backgroundRetryPrimary, logTag })`. Роутер модель-агностичен и зеркалит Vercel-сервер (`_legacy_web/app/api/_utils/{gemini,deepseekOpenAi}.ts`): `resolveGeminiModelIdFromTierEnv(modelHint)` → primary (`AI_MODEL_PREMIUM`/`STANDARD`); если id `deepseek-*` — зовётся DeepSeek OpenAI-compatible `/chat/completions` (`DEEPSEEK_API_KEY`/`DEEPSEEK_BASE_URL`, `response_format: json_object`, `thinking: disabled`, 60s timeout), иначе — Gemini API (`GEMINI_API_KEY`). Fallback на `AI_MODEL_FALLBACK` срабатывает на **любом** сбое primary (retryable — до `BACKGROUND_PRIMARY_ATTEMPTS=3` с `BACKGROUND_PRIMARY_RETRY_DELAY_MS=60s`, затем fallback; non-retryable — fallback немедленно), а не только на retryable — это и чинило «крон пишет 0 строк»: раньше non-retryable 404 (deepseek-id на Gemini API) бросал до fallback, а отсутствующий секрет `AI_MODEL_FALLBACK` валил всё ещё до LLM. Требуемые Edge-секреты: `GEMINI_API_KEY`, `AI_MODEL_PREMIUM`, `AI_MODEL_STANDARD`, `AI_MODEL_FALLBACK` (обязательно), и при `deepseek-*` primary — `DEEPSEEK_API_KEY`/`DEEPSEEK_BASE_URL`. Крон регенерирует yesterday/today/tomorrow последовательно; одна дата ≈ одно Edge-timeout окно, поэтому за один прогон могут успеть не все 3 — `contentNeedsRefresh` пропускает уже-real строки, и следующие часовые прогоны добирают.
- `fetchGlobalContent` (`services/globalContentClient.ts`) — собирает `DailyForecast`-совместимый объект для free-режима (в т.ч. `computeWindowsForFreeUser` из `daily-engine`); POST `/api/ai/global-content` передаёт **`responseLocale`** (default `getResponseLocale()`); сервер отдаёт тексты из `global_daily_content.text_i18n` по локали (при отсутствии перевода — **`pickGlobalTexts`** отдаёт canonical RU сразу, а недостающая локаль догоняется **фоновым** `backfillGlobalTextI18n`, без блокировки HTTP-ответа). Canonical RU `long_explanation` для free-path остаётся **transit-only**, но теперь должен следовать той же literal-структуре explainer-модалки, что и paid-path: шесть секций `§1…§6`, без chakra-лексики в подробном тексте. `global-content` route и cron precompute считают legacy-строки без этой структуры или с chakra-упоминаниями **устаревшими** и регенерируют их, даже если `llm_model` не поменялся. Locale-aware `math_level` для free-path теперь пересобирается из `structured.chart_mode="transit_only"` / `planet_scores` / `main_aspects`, поэтому тот же precomputed payload питает и markdown-экран, и free transit chart. Клиентский transport: HTTP к route ограничен **`GLOBAL_CONTENT_TIMEOUT_MS` = 25s**; при сбое или таймауте route — отдельное fallback-чтение `global_daily_content` через Supabase SDK (**`GLOBAL_CONTENT_DIRECT_FALLBACK_TIMEOUT_MS` = 8s**) **для любой локали** с выбором `text_i18n` на клиенте (при отсутствии перевода — RU canonical). В direct fallback клиент дополнительно нормализует chakra-имена до номерной формы, локально пересобирает free `math_level.markdown` из structured transit payload и отбрасывает legacy `long_explanation`, чтобы formulas/chart path и modal body не откатывались к сырому старому RU/EN тексту при таймауте server route. При таймауте fallback клиент повторно бросает исходную route-ошибку.
- `loadDayContentCache` / `saveDayContentCache` / `peekDayContentCache` / **`peekDayContentCacheRelaxed` / `loadDayContentCacheRelaxed`** / `pruneDayContentCache` / `clearDayContentCache` (`services/dayContentCache.ts`) — локальный кэш дня (SecureStore / web storage + manifest), ключ: user + `accessMode` + `accessTier` + `forecastDate` + `scopeKey`; strict-пути дополнительно сверяют координаты записи с текущими, **relaxed** — читают сохранённый день и **`location` из записи** без lat/lon в профиле (offline/stale fallback на home).
- `loadDayPlan()` / `renameDayAction` / `deleteDayAction` / … (`services/dayPlan.ts`) — GET `/api/day` с Bearer из **`getSupabaseAccessSession()`** (`services/supabase.ts`); после успешного fetch **`saveCachedDayPlan`** по `userId` + **`getResponseLocale()`**.
- `peekCachedDayPlan` / `loadCachedDayPlan` / `saveCachedDayPlan` / `clearCachedDayPlan` / `isDayPlanCurrent` (`services/dayPlanCache.ts`) — persisted кэш **`DayPlan`** (memory + SecureStore chunked / `localStorage`), ключ `harmonizer.dayPlan.v1.{userId}.{locale}`; запись валидна, пока `plan.currentLocalDate` совпадает с локальной датой в `plan.timezone`. Вкладка «День» **не** рисует SecureStore при focus (после restart иначе 1–2 с виден вчерашний контент); кэш только fallback при ошибке сети. `recordPracticeSession` вызывает `markDayPlanStale` + `clearCachedDayPlan`.
- Валидация полноты прогноза (`services/dayContentIntegrity.ts`): `isBaseForecastValid` — минимальный набор полей для рендера; **`isFreeDayContentRenderable`** — облегчённый gate рендера free-экрана (base + `slogan` + `recommendationShortText` + `mathLevel`; `recommendationLongText` **не обязателен**), чтобы детерминированная заглушка (LLM недоступна) с необнулённым `long_explanation` всё равно рисовалась, а карточка показывала client-side detail fallback вместо красной ошибки; `isDayContentReadyForHome` — достаточен ли forecast для показа home (paid — базовый слой; free — `isFreeDayContentRenderable`); `isDayContentCacheable` — можно ли сохранить в локальный кэш (**строго**: paid — base valid, free — `isDayContentComplete`), поэтому free-заглушка **не кэшируется** и самозалечивается при следующем fetch; `isDayContentComplete` — полная проверка, включая `slogan`, `recommendationShortText`, `recommendationLongText`, `mathLevel`. Для free-path `mathLevel` тоже обязателен, потому что из него открываются и формульный экран, и transit-only chart.
- `loadOpportunityWindowsExplanation` (`services/opportunityWindowsExplanation.ts`) — формирует человекочитаемый текст help-модала в `OpportunityWindows` из локализуемых шаблонов `opportunityWindows.help.*` (`getHomeStrings` / typed overlays). Ветвление по `accessMode`: **free** — упрощённый текст (планета дня, восход, кульминация); **paid** — один opening-абзац (`paidOpening`: натальная + транзитная планета) и точный аспект в форме «{aspect} {transitPlanet} и {natalPlanet}» (без склонений). Оба пути завершаются `closing` и `remindersHint` (колокольчик напоминаний под графиком). Все 8 локалей.

### Серверные эндпоинты (персональный прогноз)

- `POST _legacy_web/app/api/astro/daily-forecast/route.ts` — Node: кэш `user_daily_forecasts`, загрузка натала, активной калибровки, `recentPlanetsOfDay`, расчёт через `computeDailyForecastWithAstronomia`, upsert строки прогноза. Ответ **`forecastPayload`** для Home дополняется **`loadCachedMorningRecommendation`** (read-only `scenario_cache`; без LLM на обычном load) или **`ensureMorningRecommendation`** при `forceRefresh`. Planning-поля `recommendation_short_text` в строке прогноза сохраняются для вкладки «День», но не подменяют Home LLM-слой в payload.
- `POST supabase/functions/daily-forecast/index.ts` — Edge-аналог (общий расчётный слой в `supabase/functions/_shared/dailyForecast.ts`).
- Фоновый контур: `supabase/functions/precompute-daily-forecasts/index.ts` — предрасчёт для пользователей с сохранёнными координатами и personal-forecast access; под локальную полночь пользователя пишет базовый forecast и заранее греет `scenario_cache` сценария `morning_recommendation` в locale пользователя. Фоновый прогрев отключается для пользователей без активности за последние **3 дня**.

## 3. Внутренняя архитектура

1. **Движок (чистая математика + адаптер эфемерид):** `modules/daily-engine` — `computeDailyForecast` / `computeDailyForecastFromTransits`, активация и важность через `effectiveNatalParams` (при `calibration == null` используются только `S_initial` / `H_initial` из натала), ранжирование и `chooseFinalPlanet`, опционально окна через `TransitProvider.computeWindowsOfOpportunity`. `cacheValidUntil` в основном пути: конец локального календарного дня прогноза (`endOfForecastDateUtc` в `computeDailyForecast.ts`).
2. **Сервер:** загрузка `NatalProfile`, `CalibrationLike | null` из `user_calibrations`, чтение `recentPlanetsOfDay` из `user_settings.preferences`, запись/чтение `user_daily_forecasts`. Для HARMONIZER v2 эта же строка теперь получает `day_target_*` из ассистента; home и profile читают её без отдельной таблицы-прокладки. Вкладка `День` берёт рекомендацию сначала по точному `forecast_date = localDate`, а если такой строки нет — из последней доступной `user_daily_forecasts` строки пользователя, чтобы planning-corrected day focus не пропадал из UI. Инвалидация строк прогноза при успешной калибровке — см. `docs/02_modules/calibration/dependencies.md` и `docs/02_modules/astro/caching_strategy.md`.
3. **Клиент:** `useDayContent` orchestrates профиль → **`loadCachedUserCoords`** (`modules/location/userLocationProfileCache.ts`) → **async `loadDayContentCacheRelaxed`** (на native `peek*` не читает SecureStore синхронно) → геолокация (`acquireAndPersistUserCoordinates`: last-known, таймаут **`LOCATION_ACQUIRE_TIMEOUT_MS` = 12s**, structured failure; координаты используются в сессии даже при сбое записи в `users`) → strict cache → HTTP; при stale cache + сбое GPS home может открыться в **`stale_ready`** с предупреждением о геолокации. Главный экран (`app/(tabs)/index.tsx`) рендерит skeleton при `loading`, карточки и **`ChakraFlower`** (`forecast`, `strings`, `accessMode`, опционально **`natalProfile`**): блок «**Архетипы дня**» — подзаголовок **`captionFree`** / **`captionPersonal`** из `getHomeStrings` по тарифу; лепестки и точки легенды — цвета **`CHAKRA_SEGMENT_COLORS`** (`charts`); в центре всегда процент силы (`S_initial` при наличии натала, иначе нормализованная `importance`; при `todayTone === "dissonant"` — `-N%`) + подпись **`strings.planetLabels[planetOfTheDay]`** (`numberOfLines=1`, `adjustsFontSizeToFit`); внутренний круг **68** / белое кольцо **82** design px; легенда — **`planetLabels`** в порядке Sun → Saturn (не `chakraShortLabelDisplay`); canvas 214×214 (масштаб от design 248). Для **`need_location` / `stale_ready` + `locationIssue`** — «Повторить» и при **`permission_denied`** — **`Linking.openSettings()`** (`resolveLocationErrorMessage` в `modules/home/i18n/home.ts`). При **`EXPO_PUBLIC_HARMONIZER_TEST_MODE`** на home показывается dev-ряд с кнопкой **«Обновить»**: сначала `clearHomeDailyDialogCache` (локальная лента ассистента), затем `postDevDayContentReset(devResetScopeForAccessMode(...))` → `POST /api/ai/dev-day-reset` с `resetScope`: **`global`** (free) — удаление `global_daily_content` на локальную дату + LLM regen; **`personal`** (paid/trial) — `user_daily_forecasts`, `scenario_cache` (`morning_recommendation`, `global_content_i18n`), закрытие open `home`-бесед без затрагивания shared global row; timeout клиента **120s**), `refresh({ forceRefresh: true })` и remount `Communicator`. Полный контракт сброса диалога — `communicator/spec.md` §3.1; индекс темы — `MAP.md` § «Где искать: хранение daily dialog`. Маппинг планета → чакра — **`getPlanetChakraMap(locale)`** (`modules/home/planetChakra.ts`) + `data/planet_chakra_map.json` (номер/ключ/цвет); localized `shortLabel`/`chakraName` через **`modules/chakra/i18n.ts`** (в других home-блоках, не в легенде цветка); падежные формулировки в рекомендациях — **`chakraLabelGenitive(locale, …)`** в `modules/home/i18n/home.ts` и `DailyRecommendationCard.tsx`. Баннер планеты дня: RU `planetBanner.chakraLine` показывает только `chakraName` из meta (без дублирующего префикса «N чакра ·»), EN — `Chakra ${chakraNumber}`. **`OpportunityWindows`** — заголовок «Окна возможностей» / locale plural; help `?` на строке заголовка без внешней круглой кнопки. **Free:** подзаголовок `subtitleTemplate` («Главная тема: {planet}»). **Paid:** одна фраза `paidIntroTemplate` (натальная + транзитная планета, без склонений); точный аспект — `exactAspectDetailTemplate` («{aspect} {transitPlanet} и {natalPlanet}»). Волна «неба» из `samplePlanetAltitudeForDay` + `interpolateDiurnalAltitude` (`graphPlanet` из sunrise/culmination или `planetOfTheDay`); кривая — `react-native-svg` `Polyline`, цвет по чакре; штрих «сейчас» — `Line` (`strokeDasharray="2 4"`). Доля суток и «сейчас» — `dayFractionFromIso` в `userLocation.timezone`. Для paid-пути базовый forecast теперь считается достаточным для первого paint, а вторичные тексты и math-level hydrates отдельным фоновым проходом. Free-path теперь тоже получает полноценный math-layer и transit-only chart: `ModalMathLevel` открывает транзитный круг без натала, асцендента и домов, а `AstroChartSVG` использует единые цвета аспектов (harmonic = green для trine/sextile/conjunction, challenging = blue для square/opposition). Вкладка `День` (`app/(tabs)/day.tsx`) поверх `/api/day` рендерит три явных продукта состояния; блоки «Психо-практики» и «Йога-практики» имеют help «?» (`SurfaceCardTitleRow` + `SurfaceHelpModal`, тексты в `getDayStrings`): `empty_today` (пустой текущий день с CTA `Что делать` и `Выбрать практику`), `overdue_summary` (одна верхняя кнопка `Подытожить` и секции прошлых локальных дат с неподытоженными действиями, более ранние даты ниже) и `current_day` (текущая дата, фокус дня, действия текущего дня, add/practice CTA и `Подытожить этот день`). В `overdue_summary` верхняя CTA запускает полный day-start dialog (`summarizing → planning → practice`), как Home `Что делать?`; в `current_day` нижняя CTA `Подытожить этот день` остаётся summary-only для текущего списка действий. Home прогревает вкладку «День» в два этапа: (1) **во время финала planning** — `Communicator.onMessage` (`assistantMessageTriggersDayPrefetch`) запускает `loadDayPlan()` → `storePrefetchedDayPlan()` сразу после хода с сохранёнными действиями/рекомендацией; (2) **при закрытии overlay** — `router.push("/day")` вызывается **до** dismiss модалки (без мелькания «Главной»), а повторный `loadDayPlan()` идёт фоновым catch-up, не блокируя навигацию. Snapshot кладётся в `services/dayPlanReloadRequest.ts`; вкладка `День` при фокусе сначала применяет prefetched plan, затем memory/web cache, затем persisted cache `services/dayPlanCache.ts`, и только после этого делает background refresh. Это даёт instant-open even when bearer refresh for `/api/day` temporarily stalls, and background failures stay silent if a previous plan is already on screen. Под диаграммой сфер `/api/day` возвращает короткий `sphereHint` только когда последние 7 активных дней действий выглядят узко или средне: текст называет сильные и недостающие сферы; при достаточно разнообразном распределении hint = `null`, и над кнопкой «Добавить» ничего не выводится. Server-side `GET /api/day` локализует `sphereStats`, `sphereHint` и practice-log titles по `users.locale` (`getLifeSphereTitle`, `getDayStrings`, `getCoherenceBreathStrings`). Фоновые ошибки refresh вкладки `День` не показывают красный retry-блок, если предыдущий план уже отрисован; UI сохраняет текущий список и логирует сбой. Если одновременно есть текущие планы и неподытоженный хвост прошлых дней, UI намеренно показывает только overdue-секции до завершения summary. Home `Что делать?` открывает коммуникатор (а не вкладку «День»), если на текущий день нет planned/summarized actions — одна pending practice-card без actions не short-circuit'ит диалог. `app/(tabs)/day.tsx` держит стабильный `refresh`/`useFocusEffect` через refs; пропуск refresh и focus-scroll только если открыт assistant modal **и** план уже на экране (`planRef.current`) — начальная загрузка и recovery после failed load при открытом модале не блокируются. Scroll-to-top — при возврате фокуса на вкладку или закрытии assistant modal (с тем же guard). **`services/dayPlan.ts`**: client bearer is taken from a usable in-memory/persisted Supabase session snapshot before falling back to `auth.getSession()`, `fetchDayJson` принимает опциональный `timeoutMs` (default **`DAY_PLAN_FETCH_TIMEOUT_MS` = 45s**); abort → **`Error("DAY_PLAN_TIMEOUT")`**; вкладка «День» мапит этот код на `dayStrings.loadDayError`.

Стратегия серверного и клиентского кэша, таблицы и TTL описаны **краткой ссылкой** в `docs/02_modules/astro/caching_strategy.md` (без дублирования содержимого здесь).

Вне контура прогноза на главном экране после `HomeHeader` рендерятся **`StoriesRing`** (кольцо сторис) и **`LatestPostBanner`** (анонс новейшей публикации; заменил захардкоженную заглушку `AnnouncementBanner`) — оба из модуля `author_presence`: самодостаточные блоки, при отсутствии контента — `null`, к данным дня не привязаны.

## 4. Конфигурация и параметры

- **Режим доступа:** `subscription` / `useAccess` на главном экране задаёт, нужен ли натал и какой URL/пайплайн вызывать; `useDayContent` вычисляет `AccessMode` через общий **`accessModeFromRow`** из `modules/access/core/paidAccess.ts` (единая точка правила premium/trial, включая `membership_expires_at`; вопрос о консолидации закрыт 2026-07-08).
- **`scopeKey` дня (в кэше):** `${natalFingerprint | "global"}:${AppLocale}` — отпечаток birth-полей + активная локаль контента (`getResponseLocale()`); для free база `"global"`, для paid — fingerprint натала. Локаль в ключе отделяет RU/EN (и будущие enabled-локали) в `dayContentCache` и monologue hydration.
- **`recentPlanetsOfDay`:** до двух планет `[день−1, день−2]` в `user_settings.preferences`; сервер подставляет из БД, если клиент не передал массив в теле запроса. Текущий клиентский путь `useDayContent` → `fetchDailyForecast` **не передаёт** `recentPlanetsOfDay`, поэтому на практике используется только то, что уже лежит в `preferences` (если пусто — в движок уходит пустой список и альтернативная логика `chooseFinalPlanet` не активируется по «недавности»).
- **`precisionMode` натала:** влияет на демпфирование лунных вкладов в активации (`approximate` / `unknown`) — детали в reference, не здесь.
- **Таймауты транспорта:** `DAILY_FORECAST_TIMEOUT_MS` в `dailyForecastClient.ts`; для free-ветки `GLOBAL_CONTENT_TIMEOUT_MS` (**105s** — даёт блокирующему роут-генератору на холодном заходе дописать настоящий LLM-текст вместо таймаута и flashing-fallback; cache-hit от крона отвечает мгновенно) ограничивает HTTP к `global-content`, `withTransientNetworkRetry` зовётся с `attempts: 1` (чтобы hard-failure не умножал ~113s × 3), а при fallback — `GLOBAL_CONTENT_DIRECT_FALLBACK_TIMEOUT_MS` (**8s**) на direct-read `global_daily_content` (любая локаль); **`DAY_PLAN_FETCH_TIMEOUT_MS` = 45s** в `services/dayPlan.ts` для GET `/api/day`; авто-GPS на home — **`LOCATION_ACQUIRE_TIMEOUT_MS`** в `modules/location/acquireAndPersistUserCoordinates.ts`.

## 5. Известные ограничения

- **Edge fallback и `cacheValidUntil`:** в Edge-функции для части fallback-ответов TTL может задаваться как `now + 24h`, что расходится с timezone-aware правилом Node-движка; зафиксировано в `docs/04_workspace/open_questions.md` и в `caching_strategy.md` — в продуктовом spec не дублировать детали, только признать класс риска.
- **`day_target_chakra` vs `windowsOfOpportunity`:** day-target уже фиксируется в `user_daily_forecasts`, но полный пересчёт `windows_of_opportunity` под новую цель дня пока не автоматизирован отдельным серверным шагом; home продолжает использовать текущие поля строки как есть.
- **Дублирование реализации M2:** формулы поддерживаются в Node (`modules/daily-engine`) и в Deno (`supabase/functions/_shared/dailyForecast.ts`); есть **частичный** parity-тест (см. ниже и open questions).
- **Parity-тест:** `supabase/functions/_shared/daily-engine-parity.test.ts` сравнивает Node и Deno для `effectiveNatalParams`, `computeActivation`, `computeImportance` (включая ветки `precisionMode`); не покрывает целиком `chooseFinalPlanet`, ранжирование после изменений в одной ветке без зеркала, ни полный `computeDailyForecast` с реальными окнами.
- **Регрессии окон и Солнца (клиент/Node):** `modules/astro-core/solar-ephemeris.test.ts` (гладкость долготы Солнца на 10‑минутных шагах); `modules/daily-engine/windows-of-opportunity.test.ts` (восход/кульминация для `primaryPlanet: "Sun"` в `Europe/Moscow` — утренние часы); `modules/daily-engine/planet-diurnal-curve.test.ts` (непрерывность суточной кривой; согласованность восхода с X графика).
