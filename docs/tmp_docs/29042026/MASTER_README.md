# Astro-Yoga App: общая архитектура

## Что это

Мобильное приложение (React Native / Expo) для рекомендации йога-практик на основе персональной астрологической карты пользователя. Каждый день определяет, какая из 7 чакр пользователя нуждается в гармонизации, и предлагает соответствующую практику с использованием Orchestrator-Driven Dialogue для естественного общения.

## Философия алгоритма (одной фразой)

**Натальная карта — инструмент с 7 струнами, транзитное небо — смычок. Задача алгоритма — определить, какая струна сегодня звучит громче всех, и предложить практику для её настройки.**

## Архитектура из 4 модулей

```
┌──────────────────────┐         ┌──────────────────────────┐
│ M1: ASTRO-CORE       │ ──────→ │ M2: DAILY-ENGINE         │
│ Натальный профиль    │         │ Importance + планета     │
│ S, H каждой планеты  │         │ дня + окна возможностей  │
└─────────┬────────────┘         └────────────┬─────────────┘
          │                                   │
          ↓                                   ↓
┌──────────────────────┐         ┌──────────────────────────┐
│ M3: CALIBRATION      │ ──────→ │ M4: AI-ASSISTANT         │
│ S_calibrated +       │         │ Orchestrator-Driven      │
│ states_map +         │         │ Dialogue (calibration    │
│ user_lexicon         │         │ + daily_dialog)          │
└──────────────────────┘         └──────────────────────────┘
```

### M1 — Astro-Core
Один раз при регистрации рассчитывает натальный профиль: S_initial, H_initial для 7 планет. Поддерживает три режима точности: precise / approximate / unknown (всё считается на клиенте через JS-эфемериды).

### M2 — Daily-Engine
Каждый день рассчитывает Importance каждой натальной планеты, выбирает планету дня и определяет три «окна возможностей» (восход, кульминация, точный аспект транзита). Считается на клиенте, кешируется в БД для сегодняшнего дня.

### M3 — Calibration
Адаптирует алгоритм под самовосприятие пользователя:
- Корректирует S и H через усреднение «60% натальное + 40% обратная связь» (или 50/50 для авто).
- **States Map** — семантические маркеры по каждой чакре (что человек переживает).
- **User Lexicon** — лингвистические паттерны (как человек об этом говорит).

Голосовая обратная связь → Groq Whisper-v3 (быстрая STT) → Gemini для извлечения дельт → детерминированное усреднение.

### M4 — AI-Assistant (Orchestrator-Driven Dialogue)
Двухуровневая архитектура: **Orchestrator** решает, какая фаза диалога сейчас уместна (на основе плотности информации, time of day, сигналов пользователя). **Responder** генерирует видимый текст в стиле пользователя.

Use cases:
- **calibration** — диалог калибровки (welcome → listen → optional deepen → close).
- **daily_dialog** — обсуждение рекомендации (greeting → collect → optional deepen/insight → ask intent → suggest practice → close).

Отличается от классических конечных автоматов: количество и порядок фаз адаптируются под пользователя. Болтливому хватает 1-2 итерации. Молчаливому — больше уточнений.


## Распределение вычислений: клиент vs сервер

| Задача | Где | Почему |
|---|---|---|
| Натальный расчёт (M1) | Клиент (один раз при регистрации) | Без нагрузки на сервер; данные приватные |
| Дневные транзиты (M2) | Клиент через JS-эфемериды | Без бэкенда; ~50 мс на устройстве |
| Окна возможностей (M2) | Клиент | Зависит от текущей локации |
| Голосовая транскрипция | Сервер (Groq Whisper-v3) | Быстро (300мс/мин), дёшево ($0.04/час) |
| Извлечение дельт калибровки (M3) | Сервер (Gemini) | Контроль ключей, аналитика расходов |
| Orchestrator (M4) | Сервер (Gemini-flash) | JSON-структурированный output |
| Responder (M4) | Сервер (Gemini-flash, streaming) | Естественный диалог |
| Кеш forecast/calibration | Supabase Postgres | Cross-device sync |

**Бэкенд:** Next.js App Router в `_legacy_web` (Vercel deployment).
**База:** Supabase Postgres + Auth + RLS.
**LLM:** Gemini для генерации, Groq Whisper-v3 для STT.

## Обработка трёх режимов точности натальной карты

Пользователь может указать время рождения как:
- **Precise** — точное время или интервал ≤30 минут. Все формулы доступны.
- **Approximate** — интервал 30 минут — 4 часа. Дома считаются с пометкой «возможна погрешность 1 знак».
- **Unknown** — пользователь не знает. Считаем на полдень местного времени; используем «солнечные дома» (знак Солнца = 1-й дом). Луна имеет погрешность до ±6° — её участие в формулах ослабляется.

Каждый модуль обязан корректно работать во всех трёх режимах.

## Ключевая идея: Orchestrator-Driven Dialogue

Это **самое важное архитектурное решение** проекта.

Вместо жёстко прописанных стадий (как делают многие чат-боты), у нас:

1. **Цель вместо последовательности** — каждый use case определяет «оси информации», которые нужно заполнить (например, для daily_dialog это user_state, context, insight_offered, practice_intent).
2. **Оркестратор как мета-уровень** — отдельный LLM-вызов после каждого сообщения пользователя решает, какая фаза должна быть следующей. Видит: сколько информации собрано, насколько плотно отвечает пользователь, какое время суток, не затянулся ли диалог.
3. **Адаптация к пользователю** — болтливый получает 1-2 итерации, молчаливый — 4-5. Утром предлагается одно, вечером другое — сам ИИ решает в момент общения.
4. **Soft cap, не hard cap** — после 4-6 итераций оркестратор предпочитает закрытие, но не рубит на полуслове.

Все промпты, фазы и оси информации хранятся в БД. Можно тюнить через админ-панель без передеплоя.

## Последовательность реализации (от Cursor)

1. **Миграции БД** (1 день) — создать 7 новых таблиц.
2. **JSON-константы** (0.5 дня) — статические файлы.
3. **M1: Astro-Core** (3-5 дней) — на клиенте через JS-эфемериды. Тестируется unit-тестами.
4. **M2: Daily-Engine** (3-5 дней) — на клиенте + кеш в БД.
5. **Backend skeleton** (2 дня) — JWT auth, rate limiting, prompts loader, Gemini/Groq обёртки.
6. **Seed промптов и фаз** (1 день) — наполнение `prompts` и `dialogue_phases`.
7. **M3: Calibration** (3-5 дней) — endpoints transcribe / extract / portrait + frontend UI.
8. **M4: AI-Assistant** (5-7 дней) — endpoint dialog с оркестратором + responder + SSE стрим + UI.
9. **Удаление legacy кода** (0.5 дня) — старый /api/communicator route и transcript-parser.
10. **Главный экран** (5-7 дней) — Flower SVG, график окон, колокольчики, баннеры.
11. **Cron jobs** (1-2 дня) — auto-calibration, precompute forecasts.
12. **Тестирование** (5-7 дней) — все тестовые сценарии из ТЗ.

**Всего: ~6-8 недель работы для одного разработчика с использованием Cursor.**

## Каждый модуль работает независимо

Архитектура спроектирована так, чтобы каждый модуль можно было запустить и тестировать отдельно:

- M1 работает без M2/M3/M4 — даёт натальный профиль.
- M2 работает на M1 без M3 (использует S_initial, H_initial).
- M3 не обязателен — без него M2 продолжает работать на натальных данных.
- M4 имеет fallback на шаблонные тексты, если Gemini недоступен (для калибровки и для дневных рекомендаций).

Это позволяет инкрементально внедрять и поэтапно тестировать.
