**P3 — backlog**

Пункты, которые в аудите упомянуты, но **не блокируют** работу:

- Race conditions в cron при нескольких воркерах — для MVP с одним воркером не актуально, но взять на заметку.
- Полное извлечение `daily-engine-core` как shared package — после P0/P1.
- Замечание про `is_evergreen` фолбэк в digest без LLM — мелкое, обсудим отдельно.

## Что важно после исправлений

### Регрессионные тесты (один раз создать, потом гонять в CI)

Эти тесты должны быть в CI на каждый PR:

1. **`calibration.test.ts`** — 60/40 vs 50/50, кламп дельт.
2. **`dialog.test.ts`** — загрузка истории в правильном порядке, decision cache на длинных диалогах.
3. **`timezone.test.ts`** — `todayLocalDate()` для разных TZ.
4. **`engine-parity.test.ts`** — Node ↔ Deno формулы идентичны.
5. **`rls.test.ts`** — пользователь не может писать в защищённые таблицы.
6. **`proposal.test.ts`** — `isPendingProposal()` корректно обрабатывает все варианты.
7. **`dto.test.ts`** — все DTO респектят бюджеты.

### Дашборды для мониторинга

После всех патчей завести в Grafana / Metabase / Supabase Logs:

- **LLM tokens per endpoint** (PATCH 7): тренд, средние, p95.
- **LLM cost per user per day** (PATCH 7): с алертом на спайки.

## Что я НЕ предлагаю делать

- **Не делать** массовую миграцию существующих калибровок к новому 60/40. Пользователи «доедут» естественным путём за 7-14 дней.
- **Не делать** разделение на `daily-engine-core` shared package сейчас. Parity-теста хватит. Вернуться к этому после стабилизации.
- **Не делать** EN-локализацию regex сейчас — отложить до момента, когда подтвердится, что приложение пойдёт мультиязычным.
- **Не делать** advisory locks в cron для защиты от race conditions. В MVP один воркер, проблема невозможна.
- **Не делать** реализацию ИИ-обогащения states_map (`ai_proposed`) сейчас. Структура БД готова, но фичу включаем когда соберём первые 100 диалогов реальных пользователей.
