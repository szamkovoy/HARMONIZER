## 1. Что такое миграция модуля

Миграция модуля - это разовое наполнение папки `docs/02_modules/<module>/` по текущему коду, а не перенос старых текстов "как есть". Цель процесса - зафиксировать рабочий контракт модуля, его реальные зависимости и ключевые решения так, чтобы следующий агент читал не архивные идеи, а актуальное состояние системы.

## 2. Что читать перед началом

Перед любыми правками обязательно прочитать в таком порядке:

1. `docs/00_index/MAP.md`  
   Нужны строка целевого модуля, его `code_refs`, зависимости и потребители.
2. Целевую папку модуля `docs/02_modules/<module>/`  
   Прочитать все уже созданные файлы и сохранить YAML-заголовки. Если файл уже не пустой, не пересоздавать его, а обновлять содержимое, `version` и `updated`.
3. `docs/_proposal.md`  
   Прочитать раздел плана миграции и найти все старые источники, которые "переезжают" в этот модуль.
4. Код по `code_refs` из `MAP.md`  
   Прочитать точки входа и всё, что они импортируют в пределах домена модуля, пока не станет ясен фактический runtime contract.
5. Старые источники документации по модулю  
   Читать полностью, но использовать их как исторический материал, а не как источник истины.

Минимальный порядок проверки на примере `audio`:

```text
MAP.md -> docs/02_modules/audio/* -> _proposal.md -> modules/mandala-sound/* -> docs/modules/mandala_sound.md -> docs/tmp_docs/Мандала/Звук.txt
```

## 3. Что наполняется в модуле

Во всех файлах модуля YAML-заголовок сохраняется. Если файл был заглушкой, при наполнении поднять `version` до `1.1` и обновить `updated`.

### `spec.md`

Обязательная структура:

1. `## 1. Назначение`  
   2-3 предложения о роли модуля в системе. Не пересказывать старый brief. Нужно ответить на вопрос: зачем модуль существует в runtime.
2. `## 2. Публичный контракт`  
   Список экспортируемых наружу функций, классов, провайдеров, хуков и типов с сигнатурами. Писать только то, чем реально может пользоваться соседний модуль.  
   Референс формата из `audio`:
   ```text
   - `class ExpoMandalaSoundEngine implements MandalaSoundEngineControls`
     `start(chakra: number): Promise<void>`
     `update(frame: MandalaSoundSyncFrame): Promise<void>`
     `stop(): Promise<void>`
   ```
3. `## 3. Внутренняя архитектура`  
   Короткое описание главных сущностей и их взаимодействия: кто управляет жизненным циклом, кто собирает данные, кто исполняет runtime-логику, кто отдаёт данные наружу.
4. `## 4. Конфигурация и параметры`  
   Все внешние входы, пресеты, режимы, таймлайны, feature-параметры, asset-наборы и зашитые runtime-constants, которые реально влияют на поведение.
5. `## 5. Известные ограничения`  
   Производительность, платформенные ограничения, отсутствие web/native parity, дискретные режимы вместо непрерывных, технические долги.

### `dependencies.md`

Обязательная структура:

1. `## 1. Зависит от`  
   Для каждой зависимости из `MAP.md` описать:
   - какой именно контракт используется;
   - в каком файле кода;
   - в каком runtime-сценарии.  
   Недостаточно писать "зависит от biofeedback". Нужно писать в стиле:
   ```text
   - `biofeedback`
     `modules/mandala-sound/ui/MandalaSoundProvider.tsx` подписывается на канал `"beat"` через `useBiofeedbackSubscribe()` ...
   ```
2. `## 2. От него зависят`  
   Для каждого потребителя из `MAP.md` описать:
   - какой контракт модуля он использует;
   - в каком файле;
   - в каком сценарии.  
   Если потребитель использует только provider/hook/type, это нужно назвать явно.
3. `## 3. Контрактные точки риска`  
   Перечень мест, где изменение модуля может незаметно сломать соседей: типы, события bus, thresholds, провайдер props, shape DTO, симметричные импорты из соседних модулей.

### `history.md`

Обязательная структура:

1. Заголовок `## Decision Log`.
2. Хронологический список записей в формате:  
   `**YYYY-MM:** Что решено. Почему. Что изменилось.`  
   Если дату определить нельзя: `**Не датировано:** ...`
3. Источники для записей:
   - старая документация модуля;
   - история коммитов по коду модуля;
   - расхождения между старой документацией и текущим кодом.
4. Минимум `3` содержательные записи, если материал есть.
5. Если содержательных решений действительно нет, написать одну строку:  
   `На момент миграции содержательных решений для фиксации не обнаружено`

Референс формата из `audio`:

```text
- **2026-05:** Для v1 выбран `expo-av` loop-based движок вместо AudioWorklet/JSI DSP...
```

Если в скелете модуля уже есть дополнительные файлы, их тоже наполнять в той же логике: от кода к контракту, без расширения работы на соседние модули.

## 4. Правило источника истины

Источник истины - код. Если старая документация, brief или временный `.txt/.md/.pdf` источник противоречит текущей реализации, в активные файлы модуля записывается то, что подтверждено кодом.

Само противоречие не теряется: его нужно зафиксировать в `history.md` как отдельное решение или как зазор между историческим ТЗ и текущей реализацией. Пример из `audio`: старое ТЗ ожидало AudioWorklet/JSI DSP и большую библиотеку слоёв, но в коде реализован `expo-av` loop-based runtime; в каноне оставлен кодовый вариант, расхождение отмечено в `history.md`.

## 5. Что обновляется снаружи

При миграции одного модуля разрешены только три внешние точки обновления:

1. `docs/00_index/MAP.md`  
   Обновлять только если реально уточнились `code_refs`, зависимости или потребители. После правки обязательно проверить симметрию: если модуль A зависит от B, в строке B модуль A должен появиться в колонке `От него зависят`, если это соответствует фактическому коду.
2. `docs/00_index/CHANGELOG.md`  
   Обновляется всегда. Формат записи:
   ```text
   - YYYY-MM-DD: миграция модуля `<module>`. Источники: `<old file 1>`, `<old file 2>`. Перенесены в архив: `<archive path 1>`, `<archive path 2>`.
   ```
3. `docs/04_workspace/open_questions.md`  
   Обновляется только если в ходе миграции остались неразрешимые вопросы: непонятный код, конфликтующие контракты, структурные расхождения с `_proposal.md`, отсутствующие части системы. Вопросы выносить отдельным разделом по имени модуля.

`03_rules/change_protocol.md` не дублировать и не переписывать в рамках обычной миграции модуля: это другой документ, про изменения в коде после миграции, а не про первичное наполнение документации.

## 6. Архивация старых источников

После наполнения новых файлов все старые источники по модулю переносятся в:

`docs/05_archive/migrated/<module>/`

Правила:

- подпапку создать, если её ещё нет;
- старые источники переносить, а не удалять без следа;
- в `CHANGELOG.md` перечислить и источники, и архивные пути;
- в активном слое не оставлять дубли, если источник уже перенесён в архив.

## 7. Запреты

Во время миграции одного модуля запрещено:

- трогать другие модули, даже если по пути нашлись улучшения;
- трогать `docs/01_foundation/`;
- трогать `docs/03_rules/`, кроме чтения `migration_protocol.md` и случаев, когда отдельная задача явно просит изменить rule-файлы;
- задавать вопросы пользователю в чат по рабочим неясностям; их место в `docs/04_workspace/open_questions.md`;
- выдумывать даты в `history.md`;
- переносить в активную документацию неподтверждённые идеи из старых briefs как факт;
- пересоздавать YAML-заголовки вместо точечного обновления существующих файлов.

## 8. Критерии готовности модуля

Миграция считается завершённой, если:

- прочитаны `MAP.md`, целевая папка модуля, релевантный раздел `_proposal.md`, код по `code_refs` и старые источники;
- заполнены `spec.md`, `dependencies.md`, `history.md` по шаблону выше;
- в `spec.md` зафиксирован реальный публичный контракт модуля;
- в `dependencies.md` связи описаны двусторонне и конкретно, а не общими словами;
- в `history.md` есть содержательные записи или явно зафиксировано их отсутствие;
- при расхождениях старой документации с кодом в каноне оставлен кодовый вариант, а расхождение отмечено в `history.md`;
- `MAP.md` обновлён только при необходимости и после проверки симметрии;
- `CHANGELOG.md` обновлён обязательно;
- все старые источники перенесены в `05_archive/migrated/<module>/`;
- нерешённые вопросы, если они есть, вынесены в `open_questions.md`, а не оставлены в чате.
