# Documentation Update Rules

Когда сработал любой из триггеров в `.cursorrules`, следуй этим правилам.

## Принципы

- **Канон — код.** Документация описывает то, что код делает СЕЙЧАС, не то, что должен делать.
  Если ТЗ или прошлый spec расходятся с кодом — фиксируем код, расхождение в `history.md`.
- **Минимализм.** Только триада `spec.md` / `dependencies.md` / `history.md` на модуль.
  Не создавать новые сущности (intent.md, rationale.md, components.md и т.п.) даже если кажется, что «так логичнее».
- **Инкрементальные правки.** Никогда не переписывать spec.md целиком. Только точечные правки в затронутый раздел.
- **Reference автономен.** `04_reference/` НЕ синхронизируется с кодом. Из spec.md только ссылки, не дублирование.

## Что обновлять при каком триггере

### Триггер: изменился публичный API модуля

(экспорты пакета, сигнатуры функций, контракт endpoint, query/body параметры)

→ Обновить `docs/02_modules/<module>/spec.md`, раздел «Публичный контракт».
→ Если изменение намеренно расходится с прошлым описанием — короткая запись в `history.md`.

### Триггер: добавлена/убрана зависимость между модулями

(новый импорт из другого `modules/*`, новый вызов API, новая запись/чтение чужой таблицы БД)

→ Обновить `dependencies.md` обоих модулей (§1 у потребителя, §2 у поставщика).
→ Обновить `docs/00_index/MAP.md` (колонки «Зависит от» и «От него зависят»).
→ Проверить парность: связь должна быть описана с обеих сторон.

### Триггер: изменилась таблица БД или миграция

→ Обновить раздел «Известные ограничения» или «Конфигурация и параметры» в spec.md модуля,
  который владеет таблицей.
→ Если миграция меняет контракт constraint (например, расширяет CHECK) и это не отражено
  в коде клиента — пункт в `open_questions.md`.

### Триггер: добавлен/удалён модуль

→ Создать или удалить папку в `02_modules/` целиком (триада).
→ Обновить `MAP.md` (новая строка или удаление).
→ Обновить парные `dependencies.md` всех соседей в графе.

Для миграции нового модуля следовать `docs/03_rules/migration_protocol.md`.

### Триггер: намеренное расхождение с прошлым ТЗ

→ Запись в `history.md` модуля: что было, что стало, почему.

### Триггер: замечен тех. долг или нерешённый вопрос

→ Пункт в `docs/04_workspace/open_questions.md`, в раздел соответствующего модуля.
→ Формат: **Контекст** (где в коде проявляется), **Проявление** (что это даёт пользователю или разработчику), **Действие** (что нужно решить или сделать в будущем).

## После любого изменения документации

→ Запись в `docs/00_index/CHANGELOG.md`. Один-два предложения с указанием:
  что изменилось, в каких файлах, почему.

## Что НЕ делать

- ❌ Не переписывать spec.md модуля «с нуля под текущий код» — только точечные правки.
- ❌ Не дублировать содержимое reference в spec.md.
- ❌ Не создавать новые типы файлов в папке модуля сверх триады.
- ❌ Не описывать в spec.md планируемую функциональность как существующую.
- ❌ Не править историю CHANGELOG задним числом — только добавлять новые записи.

## Сомневаешься?

Если не уверен, что подходит правило — НЕ менять документацию. Лучше написать пользователю
«я заметил, что X, возможно, требует обновления Y — подтвердить?», чем сделать неверную
правку, которая потом будет распространяться.
